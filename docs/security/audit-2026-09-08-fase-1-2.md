## 1. Executive Summary

All eight findings from the first pass are closed and each is now held closed by a test that fails without the fix. The pipeline verifies what it previously only described: the corpus is checked against the hash recorded for it, the pool is checked against both its own content and the manifest, and the embedding model is fixed to a commit whose identity is recorded alongside every result.

This second pass was not a formality, and it found two things the first one had not — one of them introduced by the fix itself. `cmd_fetch` gained hash verification on the branch where the corpus already exists, and did not gain it on the branch where the corpus is re-assembled: deleting the corpus while keeping its manifest would have walked straight past the new check. Separately, `load_pool` was made to verify its units without being made to verify that each question's gold ids still resolve to one, which is the half of that artifact the metrics are actually scored against. Both are now fixed and tested.

The result that matters most for a research project: the entire evaluation was re-run twice against the corrected pipeline, and all 60 recorded metrics reproduce the values in `1.results.md` exactly. The Phase 1 numbers survive the fixes intact.

One gap is unchanged and remains declared rather than closed: no dependency CVE scan has been run, because `pip-audit` is not installed locally. The CI job that would run it is now capable of doing so, but has not yet.

## 3. Findings

### 3.1 [SEC-009] The fix verified one branch of `cmd_fetch` and not the other — **Low (fixed during this pass)**

- **File:** [cli.py:73-88](../../src/concept_embeddings_rag/cli.py#L73-L88)
- **CWE:** CWE-354 (Improper Validation of Integrity Check Value)
- **OWASP:** A08 — Software and Data Integrity Failures
- **Confidence:** Confirmed
- **Tool:** manual review of the fix

**Description**

The SEC-001 fix added verification to the branch where `hotpot_raw.json` already exists. The `else` branch — corpus absent, so re-assemble it from the API — wrote the result and fell through to the manifest rewrite without ever comparing the new digest against the `expected` value it had already loaded. Deleting the corpus while keeping its manifest, which is exactly what someone does to free disk space or to force a refetch, walked past the new check entirely and re-froze whatever the API returned.

This is the original finding surviving in the half of the function the fix did not cover, which is the characteristic way an integrity fix fails.

**Impact**

Same as SEC-001 and bounded the same way: no code execution, but a corpus that no longer matches the one every recorded number was produced from would be adopted silently, and the manifest rewritten to certify it. More likely to fire in practice than the original, because upstream datasets do get revised and a re-fetch is a routine action.

**Remediation applied**

Both branches now converge on one check:

```python
# src/concept_embeddings_rag/cli.py:79-88
    digest = sha256_of_file(raw_path)
    # Both branches end here, and both must be checked. A corpus deleted while its
    # manifest survives comes back through the branch above, and accepting whatever
    # the API returns at that point would reopen exactly the hole this closes.
    if expected is not None and digest != expected:
        raise CorpusIntegrityError(
            f"assembled corpus has hash {digest}, manifest expects {expected}; "
            "the upstream dataset has changed - delete the manifest to refreeze it "
            "deliberately, and treat every recorded number as belonging to the old corpus"
        )
```

Regression test: `test_fetch_refuses_a_reassembled_corpus_that_contradicts_the_manifest`.

### 3.2 [SEC-010] `load_pool` verified its units but not that each question's gold resolved — **Low (fixed during this pass)**

- **File:** [pool.py:186-196](../../src/concept_embeddings_rag/corpus/pool.py#L186-L196)
- **CWE:** CWE-345 (Insufficient Verification of Data Authenticity)
- **OWASP:** A08 — Software and Data Integrity Failures
- **Confidence:** Confirmed
- **Tool:** manual review of the fix

**Description**

`build_pool` guarantees, through `_resolve_gold`, that every question's two gold paragraphs exist in the pool — the HU-2 criterion that a question with unresolvable gold is an error and never a silent drop. The SEC-003 fix made `load_pool` re-verify the units, and did not make it re-verify the questions. A `pool.json` whose gold ids pointed at nothing loaded cleanly.

**Impact**

Data integrity, in the direction that is hardest to notice: a gold id resolving to no unit is not a retrieval failure, but every metric scores it as one. Gold Recall, Full Support and Precision would all read low, and the system would look worse than it is with nothing in the output to explain why. Given that Phase 4's entire argument rests on comparing these numbers, a silent downward bias is a genuine risk to the conclusion.

**Remediation applied**

```python
# src/concept_embeddings_rag/corpus/pool.py:186-196
    # build_pool guarantees this when it constructs the pool; loading has to prove it
    # again, because gold ids are what every metric is scored against. A gold pointing
    # at nothing is not a retrieval failure, but it would be counted as one.
    known = {unit.unit_id for unit in units}
    for question in questions:
        missing = [uid for uid in question.gold_unit_ids if uid not in known]
        if missing:
            raise GoldResolutionError(
                f"question {question.qid}: gold {missing} is not in the pool; "
                f"{path} is inconsistent - rebuild it with 'build'"
            )
```

Regression test: `test_loading_a_pool_whose_gold_points_at_nothing_is_refused`.

### 3.3 [OBS-003] `resolved_revision()` proves less than its name suggests — **Info**

- **File:** [backend.py:57-72](../../src/concept_embeddings_rag/embeddings/backend.py#L57-L72)
- **Confidence:** Confirmed

With `revision` pinned to a commit sha, `snapshot_download(name, revision=sha)` can only ever return that sha, so the recorded `resolved_revision` confirms the Hub served the requested commit rather than independently discovering which one was used. Its value is real but narrow: it distinguishes a run that reached the Hub from one that did not, and it would catch a drifting revision if the pin were ever loosened back to a branch.

The `except Exception` is deliberately broad so that an offline run degrades to reporting the pin instead of failing. The cost is that a genuinely rejected revision — a commit deleted upstream — is not reported here; it surfaces later when `_load()` fails, which is acceptable but is a different error message than the one the reader would expect.

No change recommended. Recorded so the next reader does not over-trust the field.

### 3.4 [OBS-004] `_check_pool_against_manifest` fails open by design — **Info**

- **File:** [cli.py:238-256](../../src/concept_embeddings_rag/cli.py#L238-L256)
- **Confidence:** Confirmed

The check returns silently when the manifest is absent or when `unit_set_hash` is still `None`. This is necessary — `cmd_build` is what first writes that field, so `embed` and `evaluate` must tolerate its absence on a pipeline that has not reached that point — but it does mean the guard can be disabled by deleting the manifest rather than by defeating the check.

Given OBS-002 (anyone who can write `data/` can write both artifacts), this adds no exposure. Recorded because "verification that can be skipped by removing its input" is worth stating out loud rather than discovering later.

- **File:** `data/cache/embeddings-a28365b7ed90ed10.{npz,json}`
- **Confidence:** Confirmed

Pinning the model revision changed the cache key from `a28365b7ed90ed10` to `bacd74e7f468f0d4`.
