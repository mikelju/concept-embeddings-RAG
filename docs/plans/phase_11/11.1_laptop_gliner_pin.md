# Deviation 11.1: the laptop cannot produce the Phase 9 GLiNER configuration digest

> Status: **closed 2026-09-25, option 1 chosen by the author.** Found at S1, before any question
> entity was extracted and before any Phase 11 measurement.

## Context

S1 extracts the entities of the 7,405 dev and 5,000 `test-11` questions with the Phase 9 GLiNER.
The spec asks for two things S1 cannot satisfy together:

- **R1**: everything runs on the laptop, with no rented compute;
- **R5**: the question extractor is the Phase 9 one, "pinned by revision and configuration
  digest" (`PHASE_9_GLINER_CONFIGURATION_DIGEST = 2f7864661b8ce7ff`).

## Problem

On the laptop the extractor's configuration digest is **`390d0d8ae603fd1d`**. The digest covers
the library versions, and one of them differs:

| | Phase 9 (RunPod, RTX 4090) | Laptop (Snapdragon X Elite) |
|---|---|---|
| model, revision, labels, threshold, parameters, weights | pinned | identical |
| gliner / transformers / tokenizers / huggingface-hub / safetensors | 0.2.29 / 5.16.1 / 0.23.1 / 1.29.0 / 0.8.0 | identical |
| torch | `2.13.0+cu126` | `2.13.0+cpu` |
| device | CUDA | CPU |

## Root cause

`pyproject.toml` selects `pytorch-cu126` on Linux x86_64 and `pytorch-cpu` everywhere else, so
no laptop install can carry the `+cu126` build string. The spec was written without noticing
that the digest pins the torch build as well as the version.

## Evidence gathered (exploratory, no question read)

1,000 FullWiki paragraphs drawn with `random.Random(11)` were re-extracted on the laptop exactly
as Phase 9 read them (same windows, spans unioned per paragraph, same record rule) and compared
with the Phase 9 records (`data/phase11/gliner-equivalence/`, result SHA-256
`17484e16b4c4c487…`, 956 s):

- **998 / 1,000 records identical**, entity by entity and in order;
- the 2 others differ by one entity each: `winamac` only on the pod, `american` only on the
  laptop. This is the signature of a span score sitting at the 0.5 threshold and falling on
  either side depending on the hardware.

## Options

1. **Pin the laptop extractor (recommended).** R5 is read as the Phase 9 extractor with the same
   model, revision, labels, threshold, parameters, weights and library versions, and the
   question extraction is pinned to the laptop digest `390d0d8ae603fd1d`. Both question sets are
   extracted by this one extractor, so the fit and the pass read spans produced the same way,
   and the D7 latency is a laptop figure, as the spec intends. The equivalence check above is
   recorded in the results as the measured cost of the change: about 0.2 % of corpus records
   differ by one entity.
2. **Extract the questions on a rented CUDA pod** with the exact Phase 9 stack. This keeps the
   digest but breaks R1 (a small spend, under 1 USD), and the GLiNER time D7 reports would be a
   GPU figure beside a laptop retrieval latency.

## Adopted solution

Option 1, chosen by the author on 2026-09-25. `config.PHASE_11_GLINER_CONFIGURATION_DIGEST` is
set to the laptop digest `390d0d8ae603fd1d`, and `cer p11-entities` refuses any other digest. Every question entity of
Phase 11, dev and `test-11`, comes from this extractor on the laptop.

## Propagation

On a decision: add `PHASE_11_GLINER_CONFIGURATION_DIGEST` to `config.py` (option 1) or the pod
procedure to S1 (option 2), note the decision in `11.0_entity_use.md` and in the limitations of
`11.results.md`.
