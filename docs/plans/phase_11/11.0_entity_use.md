# Phase 11: a better use of the entities at FullWiki scale — implementation plan

> Functional spec: [`11.spec.md`](11.spec.md), approved 2026-09-24, **amended 2026-09-25 (DF cap
> instead of rarest k), **re-approved 2026-09-25 and frozen**, together with this plan. This plan
> decides HOW; a change to any spec rule is a written deviation `11.Y_*.md`.
>
> Simplification rule: one question, **seven steps**, no `11.tasks.md`, reuse before
> generalization. Everything runs on the laptop; no money is spent.

## Objective

> Does a better use of the same entity signal — P1's entities without its hubs, entities read from
> the question, or both — retrieve the full multi-hop evidence more often than P10-C at FullWiki
> scale?

Primary endpoint: Full Support @2,048 on `test-11` (5,000 HotpotQA train `hard` questions), P11
against frozen P10-C, one two-sided exact McNemar test, α = 0.05. Preregistered secondary: P11
against P10-B, same test; it cannot change the label. Terminal states: `ENTITY_USE_SUPPORTED`,
`ENTITY_USE_NOT_SUPPORTED`, `ENTITY_USE_REGRESSION`, `DEV_STOP`.

## Author stop points

1. **Before the held-out pass (S6).** It opens `test-11`. It runs once, after `fit.json` is
   committed, and only on explicit authorization.
2. A D3 reproduction miss (S4), `DEV_STOP` (S5), or two attempts without progress.

## Implementation steps

- [ ] **S1 — `cer p11-entities` (laptop CPU).**
  - Add the Phase 11 constants to `config.py`: `PHASE_11_DIR`, the set names (dev, `test-11`), the
    DF caps `(1_000, 3_000, 10_000, 30_000, None)` with `None` = no cap, the grid step, the P10-C reference weights
    and its dev count 4,801, the dev margin 37 (gate 4,838), the system names and the terminal
    states.
  - Load the Phase 9 GLiNER extractor through `local_extraction.gliner_extractor` and refuse it
    unless its configuration digest equals `PHASE_9_GLINER_CONFIGURATION_DIGEST`.
  - Extract each question **one at a time** (batch 1), timing each call, for dev and then
    `test-11`. Batch 1 is used for both sets so the spans the fit reads are produced exactly as
    the spans the pass reads, and so the time is a per-query figure for D7.
  - Normalize each span with the Phase 9 `normalize` and match it to the entity node of that form
    in the Phase 9 index (`ENTITY_HOP_TYPES`); unmatched spans are kept and flagged.
  - Write `data/phase11/question-entities-<set>.json` once: extractor pin, per question (qid,
    spans, matched node ids, seconds), digest. Only the question text is read: no gold, no
    answer, no title.
  - `test-11` is loaded through a new `phase11.load_test_11`, which reuses a private loader split
    out of `phase10.load_set`; `phase10.load_set` keeps refusing `test-11` exactly as today.
  - → `config.py`, `evaluation/phase11.py` (new), `evaluation/phase10.py` (loader split only),
    `cli.py`.
  - Test: `tests/evaluation/test_phase11.py`: span-to-node matching (normalized, entity type
    only, unmatched kept); the digest refusal; a second write is refused; `phase10.load_set`
    still refuses `test-11`.

- [ ] **S2 — `cer p11-embed` (laptop CPU).**
  - Encode `test-11` with the pinned BGE backend into `data/phase11/cache/questions/`, under a
    `question_cache_key` that includes the set name (the `question_cache_key` gotcha), and write
    `data/phase11/embed.json` with the model, revision and seconds. It reuses the body of
    `cmd_p10_embed`. Dev keeps the Phase 9 vectors, which are not re-encoded.
  - → `cli.py`.
  - Test: the key differs from the Phase 9 and Phase 10 keys.

- [x] **S3 — The two entity components and the four-component fusion.**
  - `second_hop.seeded_hop_columnwise(index, weights, columns, *, seeds, read, depth)`: the body
    of `node_hop_columnwise` with the seed nodes given instead of read from P1. The Phase 9
    function is **not modified**.
  - `CappedEntityHopStage(index, weights, cap)` in `retrieval/entity_hop.py`: every entity node of
    P1 whose DF (`concept_support` of the index, the `df` behind the weights) is at most `cap`,
    all of them when `cap is None`, through `seeded_hop_columnwise`. Same dense-order check, `read(q)` exclusion, depth and memo
    as the Phase 9 stage; it records `positives`.
  - `QuestionEntityHop(index, weights, nodes_by_question)`: reads the frozen node ids of the
    question text it is handed (a text it has no record for is refused), excludes `read(q)` from
    Dense's list, and hops through the same function. No match gives an empty list.
  - `QuadFusedRetriever(dense, bm25, p1_stage, question_hop, weights)` in `retrieval/fusion.py`:
    fixed order Dense, BM25, P1 hop, question hop, each at `top_k`, fused with the existing
    `fuse_lists`. `describe()` records the four weights and the cap. `TripleFusedRetriever` and
    `FusedRetriever` are unchanged.
  - → `evaluation/second_hop.py`, `retrieval/entity_hop.py`, `retrieval/fusion.py`.
  - Test: `tests/retrieval/test_entity_use.py`:
    - with the seeds P1's full entity set, `seeded_hop_columnwise` equals `node_hop_columnwise`
      bit for bit on fixtures, and `CappedEntityHopStage(cap=None)` equals
      `ColumnwiseEntityHopStage`;
    - the cap keeps every node with DF ≤ cap, the boundary included, and drops the rest;
    - the question hop excludes `read(q)` and returns nothing when no node matched;
    - `QuadFusedRetriever.retrieve` equals `fuse_lists` over its four lists, and with
      `w_question = 0` the question list still enters the union as `fuse` defines it.

- [ ] **S4 — `cer p11-lists` and the D3 reproduction (laptop).**

## Technical notes

- **Reuse.** `_phase_9_inputs` (corpus, BM25, vectors, index, token counts, SEC-034), the Phase 10
  dev lists, `fuse_lists`, `ReplayRetriever`, `supported`, `gold_recall_sum`,
  `measure_system`, `write_run`, `latency_summary`, `exact_two_sided_p`,
  `_p10_fit_is_committed`, `_p10_write_once` and the `cmd_p10_embed` body.
- **Why a new hop function instead of editing the Phase 9 one.** `node_hop_columnwise` is behind
  published Phase 9 and 10 results. The seeded version is new code, held equal to it by a unit
  test and, on the real index, by the D3 list check.
- **`w_question = 0` and the union.** With a zero weight the question list still adds its units
  to the union at `ABSENT_FLOOR = 0.0`, where they tie with the other zero-scored tail units and
  sort by unit id. They could only matter below the 2,048-token budget if a question had very
  few scored units. D3 measures this exactly on dev; it is not assumed away.
- **P10-C on dev in D3** is rebuilt from the Phase 10 dev lists, because Phase 10 recorded the
  count (4,801 in its `fit.json`) but no per-question dev outcomes for P10-C.
- **Author decisions of 2026-09-25 (plan review).** GLiNER reads the questions one at a time
  (batch 1) in both sets. A zero-weighted component stays in the fusion and D3 measures that it
  changes nothing. The P1 candidate is a DF cap, not a count cut (spec amendment of that date).
- **Question spans.** GLiNER receives the raw question, which fits inside `GLINER_MAX_LEN`, so no
  windowing is needed. The exploratory diagnostic batched 64 questions; Phase 11 does not reuse
  its spans.
- **Time (projection, not measurement).**
  - S1: the diagnostic took 2,474 s for 7,405 questions in batches of 64 (0.33 s per question);
    batch 1 is slower, so about 1-1.5 h for dev and 45-60 min for `test-11`.
  - S2: minutes.
  - S4: hops only, six lists per dev question, about 1-2 h.
  - S5: Phase 10 re-fused 66 points in about 10 minutes, so 1,430 points take about 3-4 h.
  - S6: four systems × 5,000 questions, about 2-3 h.
- **Memory.** The Phase 10 pass ran on the laptop within its 31.6 GB. S4 holds the index and the
  lists but not the vectors; the Phase 11 stages never run at the same time.
- **No new dependencies.**
