# Phase 5: Text-derived concepts — navigation pilot

> Functional spec: [`5.spec.md`](5.spec.md)
> This plan implements the requirements defined there. Sixteen implementation steps, so the atomic
> breakdown lives in [`5.tasks.md`](5.tasks.md).

## Objective

Answer, with a gate written before any number exists, whether a hop from dense's first paragraph
over **entities and concepts extracted from the text** finds a paragraph dense missed better than
BM25 on the question — and whether the concepts add anything the entities do not. The outcome is
GO (open Phase 6), NAMES ONLY or STOP.

What changes is the representation the hop walks over, and nothing else: the corpus, pool, indexing
unit, embedding model, dense and BM25 retrievers, splits and seed are those of Phases 1-4, and the
second-hop protocol is the one `scripts/second_hop_diagnostic.py` already defines.

## Success criteria

Mapped 1:1 from the acceptance criteria of the spec.

**HU-1 — the pilot population is frozen by rule**
- [ ] The rule is exactly: every dev question with at least one gold paragraph outside dense's top-10;
      no sampling, no manual inclusion or exclusion
- [ ] The artifact lists ids, missing paragraphs, `p1`, the read top-10, the rule, the pool hash and a
      digest, verified on load
- [ ] Rebuilding it from the frozen pool and cached embeddings yields the identical artifact
- [ ] It holds 152 questions and 158 missing paragraphs, or the discrepancy is explained first
- [ ] It is written and committed before the first extraction result is read by any hop

**HU-2 — offline extraction of the whole corpus**
- [ ] The extractor receives only a paragraph's indexable text
- [ ] The output is constrained to a schema with `entities` and `concepts` only
- [ ] Every response is validated and bounded; a failing response is a recorded failure, never repaired
      or dropped
- [ ] Every response is cached by model, prompt digest and paragraph id; nothing is paid twice
- [ ] The prompt is frozen before the full run, after a schema check on a sample chosen by rule
- [ ] A cost estimate is printed first and the run refuses to start above 25 USD; actual cost, calls,
      cached calls and failures are recorded
- [ ] Failures above 1% are reported as a finding before any hop is measured

**HU-3 — deterministic normalization, measured fragmentation**
- [ ] Normalization is a pure function of the string, with no model and no embedding
- [ ] Entities and concepts are separate namespaces
- [ ] A paragraph's node set has no duplicates
- [ ] The node index is written with its digest, normalization version and source extraction, and
      verified on load
- [ ] Fragmentation is reported per type: distinct nodes, singleton share, paragraphs per node (mean,
      median, maximum), nodes per paragraph, paragraphs with no node
- [ ] Unresolved synonymy is declared as a limitation against the concept arm

**HU-4 — three arms**
- [ ] Arms E, C and EC
- [ ] One scoring form for all three, no fitted parameter: the rarity-weighted count of nodes shared
      with `p1`, over binary incidence
- [ ] Positive scores only, ties by paragraph id, read top-10 excluded
- [ ] Nothing about the arms changes after a hop result has been seen

**HU-5 — one run, the same questions**
- [ ] E, C, EC measured beside continue-dense, BM25-on-question (comparator), dense neighbours of
      `p1`, BM25 on `p1`'s text, and the K = 512 pooled-embedding concept hop as reference
- [ ] hit@10 and hit@100 per question as the share of its missing paragraphs found
- [ ] Rates per question and per paragraph; the four non-concept hops reproduce the diagnostic exactly
- [ ] New relevant retrievals counted per arm
- [ ] Candidate concentration per arm
- [ ] The exactly-one-gold-read subgroup reported, deciding nothing
- [ ] Every result records the pilot, node-index and prompt digests, extraction model, pool hash,
      embedding model and revision, and code version

**HU-6 — traces**
- [ ] Every found missing paragraph within top-100 carries rank, score and every shared node with its
      type, form and contribution
- [ ] Contributions sum to the score
- [ ] Traces are bound to the run's digests and verified on load
- [ ] The report reads a declared number of traces per arm, chosen by rule

**HU-7 — the gate**
- [ ] The three tests computed by code, the outcome written with wins, losses, ties and p-values
- [ ] NAMES ONLY never assigned unless "E beats BM25-on-question" passed
- [ ] Ambiguous patterns that reach STOP recorded as anomalies
- [ ] No other comparison enters the decision; "C beats BM25-on-question" reported only
- [ ] Secondary figures never change the decision
- [ ] The gate is never re-run with a different metric, test, threshold, comparator or set

**HU-8 — contamination**
- [ ] No code of this phase reads a test-split question; a test question is refused
- [ ] The prompt and its cache hold no question text, answer or gold annotation, asserted on the cache
- [ ] The extracted set does not depend on the gold
- [ ] `p1` and the read top-10 are computed without the gold
- [ ] The report declares what was known before the phase

**HU-9 — recorded either way**
- [ ] `5.results.md` reads every figure from an artifact, with its command, and states the gate
- [ ] GO opens Phase 6 in the master plan; NAMES ONLY or STOP records the stop and does not
- [ ] The founding decisions table changes only on GO

## Technical notes and decisions

Every decision below is taken before a number is measured. None of them may be revisited after a
hop result has been seen (HU-4, HU-7).

### D1 - Four stages, one package, nothing new in the retrieval path

`cer pilot` freezes the population, `cer extract` reads the corpus (the second stage after `label`
that spends money), `cer nodes` normalizes and indexes, and `cer navigate` runs every hop over the
pilot and computes the gate. Extraction and node-building live in a new `nodes/` package; the
evaluation pieces sit beside the Phase 3-4 ones in `evaluation/`. No `Retriever` is added and the
harness is not touched: this phase measures one navigation step over a frozen population, not a
system at a context budget (spec anti-goal).

### D2 - One paragraph per request, through the Message Batches API

Each request carries exactly one paragraph. Several paragraphs per request would cut the prompt
overhead, but it lets one paragraph's content shape another's extraction and makes failures and
the cache per request rather than per paragraph. The Batches API runs the same requests at half the
price, asynchronously, which an offline extraction can afford.

Request shape: the frozen prompt, `thinking` disabled (as in `label`: extraction needs no reasoning
budget, and thinking would be billed as output), structured output with the D3 schema, and a
`max_tokens` of 1,024 as a ceiling rather than an expectation. Prompt caching is not used: the
instructions are far below Sonnet 5's 1,024-token minimum cacheable prefix.

**The cost estimate moves.** The spec's ~13 USD assumed several paragraphs per request. One per
request pays the instructions 19,366 times, and the plan's rough figure becomes about **19 USD** at
batch rates — still under the 25 USD ceiling, and measured rather than assumed in D4 before any
money beyond the sample is spent.

### D3 - The prompt and the schema, and what may enter a request

The request is a pure function of two things: the frozen prompt template and
`IndexingUnit.indexable_text`. The builder's signature takes a unit and nothing else, so a
question, an answer or a split cannot reach it by construction, and HU-8 tests the property.

The prompt defines **entities** as specific named things — people, organizations, places, works,
events — and **concepts** as general topics or notions that other paragraphs could share, not proper
names, each as a short noun phrase in its most common general wording and singular form. It asks for
nothing else, and gives no example drawn from the pilot's questions.

The schema is an object with two required string arrays and `additionalProperties: false`. Length
and count constraints are not supported by structured outputs, so they are enforced client-side:
**at most 50 items per list and 120 characters per item**. Unlike `label`, which truncates, an
answer outside the bounds is a **failure**, because the spec forbids silent repair. A refusal, a
`max_tokens` stop, non-JSON or a schema mismatch are failures too.

### D4 - Sample first, then an estimate from the sample, then a checkpoint

`cer extract --sample` runs synchronously on the **20 paragraphs with the lowest unit ids** — a rule
that knows nothing about any question — with the exact request of the full run, and caches them
under the same key, so the full run reuses them. It checks schema compliance and measures the mean
input and output tokens per request, and reports the sample's paragraph lengths beside the corpus's
(mean, median, minimum, maximum), so whether 20 paragraphs represent the corpus can be judged rather
than assumed.

The estimate for the full run is the sample's mean input tokens times the number of uncached
paragraphs, plus **1.5 times** the sample's mean output tokens times that number, at batch rates. The
margin is there because the Phase 2 labelling ran 45% over its forecast. `cer extract` refuses to
start without a sample on disk and refuses above the ceiling.

After the sample, the prompt is frozen and committed, and **the full run waits for the author** to
see the measured estimate. The spec approved a ceiling; spending is still confirmed by a person.

### D5 - Running the batches

Paragraphs are submitted in batches of **5,000**, so an expired or cancelled batch costs a fraction of
the run. Every batch id is written to disk before polling starts, so an interrupted stage resumes by
reading the ids rather than paying again. Results are written to the per-paragraph cache as they
are read. A server-side error or an expired request is resubmitted **once**; an invalid request, a
refusal, a validation failure, or a second transient failure is a recorded failure. The actual cost
is computed from each response's `usage` at batch rates.

The aggregate extraction artifact records calls, cached paragraphs, resubmissions, failures by
reason, tokens, estimated and actual cost, model, prompt digest and the non-reproducibility note that
`label` already carries. If failures exceed 1% of the pool, `cer extract` ends with a `[WARN]` naming
the rate and the reasons, and step 13 stops there: the finding is written, and no `cer nodes` or
navigation run is allowed. Nothing retries it away.

### D6 - Normalization v1

A pure function, applied identically to both types, in this order: Unicode NFKC; strip diacritics
(NFKD, drop combining marks); casefold; typographic quotes and apostrophes to ASCII; hyphens,
underscores and slashes to spaces; strip surrounding punctuation; drop a leading `the`, `a` or `an`;
collapse whitespace. A form that becomes empty is dropped and counted.

**Plural folding is deliberately absent.** A rule-based singularizer turns `physics`, `series`,
`news` and `Paris` into wrong forms, and a list of exceptions is a curated vocabulary the spec rules
out. The prompt asks for singular forms instead, and whatever variation remains is measured by the
fragmentation figures. The version string `normalization-v1` travels in every artifact built on it.

### D7 - The node index, and what is versioned

`NodeIndex` is a binary CSR matrix of paragraphs × nodes written as `.npz`, plus a JSON sidecar with
the node list (`node_id`, `type`, `form`), the unit ids in pool order, the normalization version, the
extraction digest and a digest over both files. It is regenerable from the extraction and stays
git-ignored, like the concept matrices.

**The extraction itself is the non-reproducible record**, and it is versioned as
`data/extraction/extraction-<key>.jsonl.gz` when it compresses to 15 MB or less; if larger, the gap
is declared in the results and the digest alone is versioned. The pilot set, the hop run, the traces
and the gate decision are small and always versioned.

### D8 - The protocol moves into `src`, and the diagnostic still reproduces

`evaluation/second_hop.py` takes the diagnostic's pieces as functions: the dense order and read
top-10, `p1`, ranking with read paragraphs excluded, and the four non-concept hops plus the pooled
concept hop. `scripts/second_hop_diagnostic.py` becomes a caller, and a data-dependent test asserts
that it still reproduces the committed `second_hop-dev.json` exactly.

**The old hops keep their tie-breaking to reproduce the diagnostic; the new arms break ties by unit
id.** Pool rows are ordered by the question whose context introduced them, so a tie broken by row
position favours paragraphs from `p1`'s own source question, which is a leak towards the gold. With
binary incidence and one weight per node, ties are common in the new arms, so this is not a detail.
Unit ids are content hashes and carry no position.

### D9 - The node hop

For an arm with node set `A` (entities, concepts, or both), incidence `X_A` and rarity weights
`w = log(1 + N / (1 + df))` over the whole pool — the Phase 3 formula, `rarity_weights`, applied to
node document frequency — a candidate `v` scores `sum over n in A shared by p1 and v of w_n`. Read
paragraphs are excluded, `p1` among them; candidates with a positive score are ranked by score
descending, then unit id; the rest are unranked. For EC, the node set is the union of both
namespaces with each node's own weight. Nothing is fitted.

### D10 - The pilot set and the navigation run

`PilotSet` implements the spec's contract. It is built from the pool, the cached corpus embeddings
and the cached dev question embeddings, sorted by question id, refused if any question is not dev,
and loaded only if its digest and pool hash verify.

`cer navigate` loads the pilot, the node index and the pooled-embedding space, runs every hop for
every pilot question at depth 100, and writes the `HopRun`: per question and hop, the score at 10 and
100 and the positive-candidate count; per hop, rates per question and per paragraph; new relevant
retrievals (a missing paragraph in an arm's top-10 that is in neither dense's top-110 nor
BM25-on-question's top-100); concentration; the subgroup; and the provenance of HU-5. The
`NavigationTrace` is written in the same run and bound to the `HopRun` digest. The report reads the
traces of the **first five pilot questions by id** in which an arm found a missing paragraph, per
arm, plus every case where EC found a paragraph E did not.

### D11 - The gate

For each test, per-question hit@10 scores of the two hops are compared question by question: wins,
losses, ties. The p-value is `scipy.stats.binomtest(wins, wins + losses, 0.5,
alternative="greater")`; with no discordant question it is 1.0. A test passes at `p < 0.05`. The
outcome function takes the results of "EC beats BM25", "EC beats E", "E beats BM25" and "C beats BM25"
and returns GO, NAMES ONLY or STOP exactly as the spec's table does, with any ambiguous STOP recorded
in `anomalies`. `scipy` is already a dependency.

### D12 - Id-bearing artifacts and the secrets gate

Unit ids and question ids are hexadecimal hashes, and detect-secrets flags every one as a
high-entropy string: the pilot set alone would add well over a thousand baseline entries, the traces
more. Auditing thousands of machine-written ids one by one would make the baseline unreadable, which
defeats its purpose.

The Phase 5 id-bearing artifacts under `data/pilot/` and `data/navigation/` are therefore excluded by
path, through the `--exclude-files` filter recorded in `.secrets.baseline` and honoured by the CI
hook. The exclusion is narrow (those two directories, `.json` only), justified in
`docs/security/README.md`, and checked locally with `detect-secrets-hook` before the commit that
introduces it. The extraction archive is binary and is checked the same way.

### D13 - What the contamination audit asserts

Test questions are refused by `check_dev_only` at the pilot builder and at the navigation run. The
extraction request builder accepts a unit and nothing else, and a test scans the extraction cache
for every question string of both splits. The pilot's `p1` and read top-10 are asserted identical
when the gold annotations are shuffled. The extraction covers every unit of the pool, asserted before
`cer nodes` builds the index.

### D14 - Order of commits, and the two moments a person decides

The pilot set is committed (step 4) before any extraction exists, so it cannot be shaped by one.
The prompt is committed (step 12) before the full run, and the author confirms the spend. After
that, steps 13-16 run without a decision in them: the gate is a function, and its outcome decides
what the master plan says.
