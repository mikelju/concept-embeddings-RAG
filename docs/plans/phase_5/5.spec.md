# Spec Phase 5: Text-derived concepts — navigation pilot

> Functional specification — WHAT to build and WHY.
> The HOW is defined in the phase plan (`5.0_text_derived_concepts.md`).
> Acceptance criteria are checked with `/7-verificar` when the phase ends.

---

## Problem and objective

**Problem.** The first research line tested concepts induced from pooled paragraph embeddings and
closed negative ([`4.1_research_line_closure.md`](../phase_4/4.1_research_line_closure.md)). Its
verdict is scoped: it never tested the representation the proposal describes, in which a
paragraph's concepts are **read from its text**. The exploratory second-hop diagnostic measured on
the same dev questions shows where that representation would have to prove itself: when dense has
read its top-10 and missed a gold paragraph, a hop through pooled-embedding concepts from the best
paragraph finds it at 0.076 hit@10 (K = 512), below simply reading further down the dense list
(0.297) and far below BM25 on the question (0.449).

**Objective.** Answer one question with a gate declared before any number exists: **when dense has
missed a paragraph a bridge question needs, does a hop over entities and concepts extracted from the
text find it better than BM25 on the question — and do the concepts add anything the entities do
not?** The answer is GO (open Phase 6), NAMES ONLY (the concept hypothesis stops, with a positive
finding about entities recorded) or STOP (the line closes).

### What stays fixed

Everything except the representation the hop walks over: the corpus, the pool of 19,366 paragraphs,
the indexing unit, the embedding model, the dense and BM25 retrievers, the dev/test split and the
seed. The second-hop protocol is the one `scripts/second_hop_diagnostic.py` already defines, so its
rows are directly comparable.

### Decisions settled in the specification conversation

| Decision | Choice | Why |
|---|---|---|
| What is extracted | **The whole corpus**, 19,366 paragraphs | A hop needs the nodes of its candidates too. Extracting only read and gold paragraphs would make the gold nearly the only candidate with nodes; extracting a baseline-built candidate pool would cap the hop at what BM25 and dense already found. At an estimated ~13 USD the full corpus removes both problems |
| Which questions | **All 152 eligible dev questions**, no sampling | The population is the rule itself: every dev question with a gold paragraph outside dense's top-10. It is the diagnostic's population, so its figures compare directly, and it doubles the resolution of a 50-question sample at no extra cost |
| Where the hop starts | **`p1`, dense's first paragraph** | Never the gold paragraph dense did find: choosing the origin by the answer would contaminate the hop |
| Extractor | **Claude Sonnet 5**, offline, structured output | The task is structured extraction, not open reasoning. Vocabulary consistency is handled by the pipeline — a fixed schema and deterministic normalization and deduplication — not by paying for a larger model, which would not remove synonymy either |
| Statistical unit | **The question** | Six questions miss two paragraphs; counting paragraphs would weight them twice |
| Primary comparator | **BM25 on the question**, frozen now | The strongest second hop of the prior diagnostic at hit@10. Choosing "the best of four" after measuring would select the rival by the result |

## User stories

### HU-1: The pilot population is frozen by rule before anything is measured

**As** the researcher,
**I want** the pilot's questions to be defined by a written rule and frozen in an artifact before any
text-derived hop runs,
**so that** no question can be added, dropped or re-weighted after the results are known.

**Acceptance criteria:**
- [ ] The rule is exactly: every **dev** question for which at least one gold paragraph is outside
      dense's top-10 on the question. No sampling, no manual inclusion or exclusion
- [ ] The artifact lists the question ids, each question's missing gold paragraphs, `p1`, the read
      top-10, the rule text, the pool hash and a digest; loading it verifies the digest
- [ ] Rebuilding it from the frozen pool and cached embeddings yields the identical artifact
- [ ] It holds 152 questions and 158 missing paragraphs, or the discrepancy with the diagnostic is
      explained before the phase continues
- [ ] It is written, and committed, before the first extraction result is read by any hop

### HU-2: The corpus is described by entities and concepts read offline from its text

**As** the researcher,
**I want** every paragraph of the corpus to be read once, offline, by an LLM that returns its
entities and its concepts in a fixed structure,
**so that** the representation under test is the one the proposal describes, built without ever
seeing a question.

**Acceptance criteria:**
- [ ] The extractor receives only a paragraph's indexable text — title and paragraph, what both
      retrievers index — and nothing about any question, answer, gold annotation or split
- [ ] The output is constrained to a declared schema with two lists: **entities** (named, specific
      things: people, organizations, places, works, events) and **concepts** (general topics or
      notions, not proper names). No other node type
- [ ] Every response is validated against the schema and bounded in length; a response that fails
      is recorded as a failure for that paragraph, never silently repaired or dropped
- [ ] Every paragraph's response is cached on disk, keyed by model, prompt digest and paragraph id;
      re-running reads the cache and pays nothing twice
- [ ] The prompt is frozen before the full run. It may be checked for schema compliance on a small
      sample of paragraphs chosen by a written rule, never by looking at any hop result
- [ ] The run prints a cost estimate first and refuses to start above a declared ceiling of
      **25 USD**; the actual cost, calls, cached calls and failures are recorded in the artifact
- [ ] Extraction failures above **1%** of the corpus are a finding reported before any hop is
      measured, not a detail

### HU-3: Nodes are normalized deterministically, and fragmentation is measured rather than judged

**As** the researcher,
**I want** raw extracted strings turned into nodes by a declared, deterministic normalization and
deduplication,
**so that** the concept arm is not lost to surface variation, and the variation that remains is a
number rather than an impression.

**Acceptance criteria:**
- [ ] Normalization is a pure function of the string: the same input always yields the same node,
      on any machine, with no model and no embedding involved
- [ ] Entities and concepts are separate namespaces: the same string as an entity and as a concept
      is two nodes
- [ ] A paragraph's node set has no duplicates after normalization
- [ ] The node index — paragraphs × nodes, with each node's type — is written with its digest, the
      normalization version and the extraction it was built from, and verified on load
- [ ] Reported per type, not assessed by eye: number of distinct nodes, share of nodes appearing in a
      single paragraph, paragraphs per node (mean, median, maximum), nodes per paragraph, and
      paragraphs with no node of that type
- [ ] Synonymy that normalization cannot resolve (`sitcom` / `situation comedy`) is declared as a
      limitation that works **against** the concept arm

### HU-4: Three arms separate navigating by names from navigating by concepts

**As** the researcher,
**I want** the same hop run over entities only, concepts only, and both,
**so that** a gain can be attributed to concepts rather than to proper names — which BM25 on a
paragraph's text already follows.

**Acceptance criteria:**
- [ ] Three arms: **entity-only (E)**, **concept-only (C)** and **entity + concept (EC)**
- [ ] All three score a candidate identically, with no fitted parameter: the sum, over the nodes the
      candidate shares with `p1`, of each node's rarity weight computed over the corpus — the scoring
      form of the diagnostic's concept hop, over binary node incidence
- [ ] Only candidates with a positive score are ranked; ties break by paragraph id; paragraphs in
      the read top-10 are excluded, exactly as in the diagnostic
- [ ] Nothing about the arms — weights, normalization, node types — is changed after any hop result
      has been seen

### HU-5: Measured against the same second hops, on the same questions

**As** the researcher,
**I want** the three arms and every earlier second hop measured in one run over the frozen pilot,
**so that** every comparison is on identical questions and identical missing paragraphs.

**Acceptance criteria:**
- [ ] The run measures E, C and EC beside: continue the dense list, **BM25 on the question (the
      primary comparator)**, dense neighbours of `p1`, BM25 with `p1`'s text, and the pooled-embedding
      concept hop at K = 512 (the selected space) as a reference
- [ ] For each hop and each question: hit@10 and hit@100, where a question's score at depth *k* is
      the share of its missing paragraphs found in the hop's top *k*
- [ ] Rates are reported per question (the statistical unit) and per paragraph (for continuity with
      the diagnostic); the four non-concept hops reproduce the diagnostic's paragraph-level figures
      exactly, or the difference is explained
- [ ] **New relevant retrievals** are counted per arm: missing paragraphs an arm places in its top-10
      that are neither in dense's top-110 (read + continued) nor in the top-100 of BM25 on the question
- [ ] Candidate concentration is reported per arm: how many paragraphs receive a positive score from
      `p1`, as a share of the pool
- [ ] The subgroup of questions with exactly one gold paragraph in the read top-10 is reported
      separately and decides nothing
- [ ] Every result records the pilot digest, node-index digest, extraction model and prompt digest,
      pool hash, embedding model and revision, and code version

### HU-6: Every positive retrieval says which node led to it

**As** the researcher,
**I want** each missing paragraph an arm finds to carry the nodes that brought it,
**so that** a success can be read as a path — `p1` → node → paragraph — and told apart from a
lucky coincidence.

**Acceptance criteria:**
- [ ] For every (question, arm, missing paragraph) found within top-100, the trace records the rank,
      the score, and every node shared with `p1` with its type, normalized form and contribution,
      heaviest first
- [ ] The contributions in a trace sum to the recorded score
- [ ] The traces are an artifact bound to the digests of the run that produced them, and verified
      on load
- [ ] The report reads a declared number of traces per arm, chosen by rule (the first by question
      id), including failures of the kind "EC found it, E did not" when they exist

### HU-7: The gate is declared here and applied as written

**As** the researcher,
**I want** the GO / NAMES ONLY / STOP decision computed mechanically from the three tests below,
**so that** no reading of the numbers after the fact can move it.

**The gate.** Metric: **hit@10 per question** over the 152 pilot questions. Each comparison is a
paired sign test over the questions where the two hops' scores differ (questions with equal scores
are ties and are dropped), one-sided, significance **p < 0.05**. "X beats Y" means X scores higher
on significantly more questions than Y does.

| Outcome | Condition |
|---|---|
| **GO** | EC beats BM25-on-question **and** EC beats E |
| **NAMES ONLY** | E beats BM25-on-question **and not** GO |
| **STOP** | Every other pattern: neither EC nor E beats BM25-on-question, **or** an ambiguous pattern the two rows above do not name |

**NAMES ONLY needs positive evidence that entities alone navigate.** An outcome is never labelled
"names" unless E has itself beaten the comparator. The case this excludes is the ambiguous one: EC
beats BM25-on-question, but neither beats E nor lets E beat the comparator on its own. That result
shows neither that concepts add something nor that names suffice, so it resolves to STOP and is
reported as an anomaly.

**Acceptance criteria:**
- [ ] The three tests are computed by code from the per-question scores, and the outcome is written
      to an artifact with each test's wins, losses, ties and p-value
- [ ] NAMES ONLY is never assigned unless the test "E beats BM25-on-question" passed
- [ ] Any pattern that reaches STOP without "neither EC nor E beats the comparator" — EC beating the
      comparator without beating E while E does not beat it, or concept-only beating the comparator
      while neither EC nor E does — is recorded in `anomalies` with the tests that produced it
- [ ] No other comparison enters the decision. "C beats BM25-on-question" is computed and reported,
      because the anomaly above needs it, and never changes the outcome
- [ ] hit@100, new relevant retrievals, concentration, fragmentation and the subgroup are reported
      beside the decision and never change it
- [ ] The gate is not re-run with a different metric, test, threshold, comparator or pilot set

### HU-8: No contamination, audited rather than assumed

**As** the researcher,
**I want** the absence of test-split contamination and of gold leakage checked by tests,
**so that** the pilot's numbers are admissible as evidence.

**Acceptance criteria:**
- [ ] No code of this phase reads a test-split question; a test question passed to the pilot builder
      or the hop evaluation is refused
- [ ] Neither the extraction prompt nor its cache contains any question text, answer or gold
      annotation, and a test asserts it on the cache
- [ ] Which paragraphs are extracted does not depend on the gold: the extraction covers the whole
      pool
- [ ] The hop origin `p1` and the read top-10 are computed without the gold
- [ ] The report declares what was already known before this phase: the dev population and the
      baseline second-hop figures, from the Phase 4 diagnostic. The text-derived arms had never been
      measured

### HU-9: The result and the decision are recorded, whichever way it goes

**As** the researcher,
**I want** a results document and a master plan that reflect the gate's outcome,
**so that** the project's state says what the pilot found, not what was hoped.

**Acceptance criteria:**
- [ ] `docs/plans/phase_5/5.results.md` reports every figure from an artifact, with the command that
      regenerates it, and states the gate outcome with its three tests
- [ ] **GO**: the master plan opens Phase 6 with what this pilot hands it. **NAMES ONLY** or
      **STOP**: the master plan records the stop and its scope, and does not open Phase 6
- [ ] The founding decisions table changes only on GO, and only for what the pilot verified

## Data contracts

### `PilotSet` (JSON, one per phase, versioned)

| Field | Type | Constraints |
|---|---|---|
| `rule` | str | The HU-1 rule, verbatim |
| `split` | str | Always `dev` |
| `read_depth` | int | 10 |
| `questions` | list | One entry per question, sorted by id |
| `questions[].qid` | str | A dev question id |
| `questions[].p1` | str | Unit id of dense's first paragraph |
| `questions[].read` | list[str] | Dense's top-10, in rank order |
| `questions[].missing` | list[str] | Gold unit ids outside `read`; never empty |
| `unit_set_hash`, `model`, `revision` | str | The pool and embeddings it was computed over |
| `digest` | str | sha256 over the rest of the payload |

**Invariants:** every `missing` id is a gold unit of its question and absent from `read`; `p1 ==
read[0]`; no test question appears.

### `ExtractionRecord` (cached per paragraph; aggregated into one artifact)

| Field | Type | Constraints |
|---|---|---|
| `unit_id` | str | A pool unit id |
| `model` | str | The extraction model id |
| `prompt_digest` | str | Digest of the frozen prompt template |
| `status` | str | `ok` or `failed` |
| `entities` | list[str] | Raw strings as returned; bounded count and length |
| `concepts` | list[str] | Raw strings as returned; bounded count and length |
| `failure` | str \| null | Reason, when `status == failed` |

**Invariants:** no field holds question, answer or gold text; the aggregate records the total cost,
calls, cached calls and failures.

### `NodeIndex` (verified on load)

| Field | Type | Constraints |
|---|---|---|
| `normalization_version` | str | Changes whenever normalization changes |
| `extraction_digest` | str | The extraction it was built from |
| `nodes` | list | `{node_id, type, form}`; `type` in `entity`, `concept` |
| `incidence` | sparse, paragraphs × nodes | Binary |
| `unit_ids` | list[str] | Row order; equals the pool's |
| `digest` | str | Over the arrays and the metadata |

### `HopRun` (JSON, one per run)

Per hop and per question: `hit@10`, `hit@100`, positive-candidate count; the aggregates of HU-5;
the configuration of HU-5; a digest.

### `NavigationTrace` (JSON, one per run)

Per found (question, arm, missing paragraph): `rank`, `score`, and `nodes: [{type, form, weight,
contribution}]`, bound to the `HopRun` digest.

### `GateDecision` (JSON, one per phase)

`outcome` in `GO`, `NAMES_ONLY`, `STOP`; for each of the three tests: `wins`, `losses`, `ties`,
`p_value`; the `HopRun` digest; `anomalies: list[str]`.

## Restrictions

- **Offline extraction only.** The LLM builds the node index before any hop runs and is never called
  during retrieval or evaluation.
- **Dev only.** The pilot never reads the test split, and no test-split figure is produced in this
  phase.
- **No fitted parameters.** Scoring, weights and normalization are declared, not tuned; nothing is
  chosen by looking at a hop result.
- **Non-reproducible extraction, reproducible pipeline.** Current models reject `temperature`, so an
  identical prompt can return different nodes on another day. The cached extraction is the record,
  exactly as with concept labels; everything downstream of it is deterministic and regenerable.
- **The key is a secret.** `ANTHROPIC_API_KEY` is read from `.env` at runtime and never printed,
  logged, cached or written into an artifact.
- **External input.** The model's output is untrusted: schema-validated, length-bounded, never
  evaluated. Together with the new artifact deserialization, this makes `/8-auditar` mandatory for
  this phase.
- **Windows on ARM.** No new dependency without asking first; normalization is expected to need
  none. The `labeling` dependency group already provides the SDK.
- **ASCII only** in `print()`, logging and Python string literals; extracted node forms are data and
  may hold any Unicode.
- **Cost ceiling** of 25 USD for the extraction, enforced before the run starts.

---

## Anti-goals (what this phase does NOT do)

- NO PageRank, personalized propagation, diffusion or multi-round expansion: one hop from `p1`.
- NO agents and NO LLM inside the retrieval loop.
- NO concept embeddings, embedding-based merging, synonym tables or a curated ontology.
- NO relation or attribute nodes (`born in`, `played for`): entities and concepts only.
- NO evaluation at a context budget and NO Full Support: this measures one navigation step. A
  system-level comparison at equal budget is Phase 6's, if the gate opens it.
- NO test split, and NO second benchmark.
- NO tuning of the prompt, the normalization or the scoring after any hop result is seen, and NO
  re-running the gate with a different metric, threshold, comparator or question set.
- NO change to the founding decisions table unless the outcome is GO.
