# Phase 4: Query-aware iterative expansion (System C)

> Functional spec: `docs/plans/phase_4/4.spec.md`
> This plan implements the requirements defined in that spec.

## Objective

Stop following the question and start navigating the corpus. Phase 3 scored the concept space once,
fused it with dense, and the fitted weight came back at `w = 1.0`: System B *is* dense at every budget
on both splits, and it recovers **0** of the 72 dev questions that defeat both baselines. This phase
builds **System C** - expansion by diffusion over `X`, with partial restart on the question at every
round - measures it in the unchanged harness at equal token budget, and finds out whether the second
paragraph can be reached through concepts at all.

Two arms, not one: **dense-seeded** (System C proper) and **conceptual-seeded** (the isolating
variant), built from the same diffusion code with the same parameters, so that a gain can be told
apart from "the dense retriever already brought almost everything". The configuration is fitted on dev
under a declared cap of 40 evaluations, frozen in a versioned artifact, and test is read once.

**The bar is the dense+BM25 control at 0.8643 Full Support on test @2,048**, not dense at 0.8250: a
cheap lexical hybrid already achieves that on this corpus without any of this machinery. System C
beating dense and not the control is a result, and is reported as exactly that.

The deliverable is `docs/plans/phase_4/4.results.md` plus the frozen `ExpansionSelection` artifact and
the per-query traces. **A negative verdict closes this phase as well as a positive one.** What would
not close it is a win nobody can attribute - which is why the two seed arms exist, why the restart
parity of HU-2 is a test rather than a claim, and why the rivals' numbers are read from the Phase 3
result files instead of being recomputed here.

**HU-1 - The corpus is navigated by diffusion over `X`, not by a second ranking**
- [ ] Propagation is computed as **sparse matrix-vector products** against `X` and `X`ᵀ. The
      unit x unit matrix (19,366²) is **never materialized**, at any iteration, in any intermediate
- [ ] The operator is written down in this plan (D2, D3) and recorded in every result config: which
      matrix, which view, which normalization, applied in which order
- [ ] **Operator normalization is measured, not assumed**: it is one of the two free parameters, and
      its three arms are a measured cell of the grid rather than a belief held in a comment
- [ ] The ranking is deterministic including ties, broken by unit id exactly as every other retriever
      in this project does. The same question and the same artifacts produce the same list every run
- [ ] A test asserts one diffusion step against a reference computation on a small hand-built matrix,
      so the implementation is checked against arithmetic rather than only against itself
- [ ] The retriever reads no concept label, no gold annotation and no split. The guard tests that
      keep `retrieval/` free of the labels artifact keep passing unchanged

**HU-2 - The restart makes the expansion query-aware, and that is checkable**
- [ ] The restart is applied at **every** iteration, not only at the first, and its fraction is a

- [ ] **At `restart = 1.0` the system reproduces its seed system's ranking exactly**, to floating

- [ ] At `restart = 0.0` the walk is measured once on dev at the chosen normalization, both arms, and

- [ ] The question's signal that is restarted onto is the same one the seed used (D1), and a result

- [ ] The stop is **per-query**, on new mass falling below a declared threshold (D6), with a hard

## Technical notes and decisions

Decisions **D1-D13 are declared here before any number is measured**, which is what HU-1, HU-4 and
HU-6 require of the operator, the stopping rule and the grid. Anything the measurement forces to
change is recorded as a deviation (`4.Y_name.md`), never edited into this list afterwards.

### D1 - The mass vector, and what "the question's signal" is

The walk carries a **non-negative mass vector over the 19,366 units**, and the restart target is the
**seed's own score vector**: the seed is asked for its hits once per question, the scores are clipped
at zero and L1-normalized, and that vector is `s_0`.

This is what HU-2's last criterion asks for - the signal restarted onto is the signal the seed used -
and it is what makes the parity property of HU-2 exact: L1 normalization is a positive scalar, so
`s_0` ranks the units exactly as the seed did, and at `restart = 1.0` the walk never leaves it.

The rejected alternative was restarting on the query's concept vector pushed into unit space
(`X (w ⊙ c_q)`). It would have made the **dense** arm restart onto a conceptual signal its seed never
used, which is a second system rather than a restart, and it would have broken the one property that
makes every later difference attributable to expansion.

A dense cosine can in principle be negative. Clipping at zero is therefore declared rather than
assumed, and the **number of clipped seed hits is counted and recorded per run**: on the top-100 of
this corpus it is expected to be zero, and a non-zero count is a finding to be written down, not a
silent repair.

### D2 - The operator: two sparse products, damped on the concept side

One round is

```
c = Xᵀ s            units  -> concepts
u = X (w ⊙ c)       concepts -> units
```

with `w` the **inherited `idf` rarity weight of Phase 3** (`w_j = log(1 + N / (1 + df_j))`), applied
to the concept vector in the middle of the round trip. That is exactly where Phase 3 applies it - to a
concept vector, leaving `X` and the atoms byte-identical on disk and in memory - and it is what stops
the corpus's most common concepts from ferrying mass across the whole pool at every hop.

`X (w ⊙ (Xᵀ s))` is associativity used in the only order that is affordable: the unit x unit matrix
`X W Xᵀ` has 375 million entries and **is never formed**. Both products are `scipy.sparse` matvecs
against the inherited `raw` view, which at K = 512 holds roughly 250,000 non-zeros.

For the **conceptual-seeded** arm the damping therefore appears twice, in two different places: once
inside the seed (Phase 3's damped query vector) and once per round trip (here). They are different
objects, both inherit the same declared weight, and neither is refitted.

### D3 - Three normalization arms, and the mass is renormalized after every propagation

`normalization` is the second free parameter. Degrees are read once from the inherited matrix:
`d_u` = row sums, `d_c` = column sums.

| Arm | Operator | What it does |
|---|---|---|
| `none` | `X`, `Xᵀ` as they are | Mass concentrates on the best-connected units. The null hypothesis of HU-1: maybe on this space it does not matter |
| `symmetric` | `D_u^{-1/2} X D_c^{-1/2}` | The standard bipartite diffusion scaling: demotes high-degree units and high-degree concepts by the geometric mean of their degrees |
| `stochastic` | `D_c^{-1}` on the way back, `D_u^{-1}` on the way out | The bipartite random walk: from a unit, pick a concept with probability proportional to its weight; from a concept, pick a unit the same way. Mass-preserving by construction |

After each propagation the result is **L1-normalized before it is mixed with the restart**, so that
`restart` is a genuine fraction of unit mass and the stop threshold of D6 means the same thing in all
three arms. Under `stochastic` that renormalization is a no-op up to float error, which is asserted as
a test rather than assumed.

Zero degrees are a division this code must not perform. Phase 2 measured **zero orphan units and zero
dead atoms at every K**, so a zero row or a zero column is an assertion that should hold, not a case
to be papered over: the degree floor raises rather than substituting a one.

### D4 - The candidate set and the ranking

The final ranking is by `(-mass, unit_id)` over the candidate set

```
{units with strictly positive final mass}  ∪  {the seed's hits}
```

Ties break by unit id, exactly as `dense.py` and `conceptual.py` do. The union with the seed's hits is
what keeps the parity property exact rather than "exact up to a tie": a seed hit whose clipped score
is zero must not be displaced from the list by whichever zero-mass unit of the pool happens to sort
first alphabetically.

### D5 - `seed_top_k = top_k = 100`, declared and fixed

The seed is asked for exactly the depth the harness reads. It is not a third free parameter, and it is
not swept. Asking the seed for more would change what the seed contributes and would make "`restart =
1.0` reproduces the seed" a property that holds at one depth and not at another. The whole point of
diffusion is to reach units the seed never returned, which it does from 100 of them.

### D6 - The stopping rule, declared and not fitted

Stop when the mass stops moving:

```
delta_t = || s_{t+1} - s_t ||_1      both vectors L1-normalized
```

- `STOP_THRESHOLD = 1e-3` - a thousandth of the total mass moved in a round.
- `MAX_ITERATIONS = 5` - HotpotQA is a two-hop benchmark and one round trip is one hop, so five is
  more than twice what the corpus's structure needs. A run where most questions reach it is a finding
  about the threshold, reported as one (HU-4).

`stop_reason` is `converged` when `delta_t` is zero to float tolerance, `threshold` when it is below
the threshold but not zero, and `cap` otherwise. Both constants live in `config.py` and neither is
fitted: HU-4 forbids a third degree of freedom, and needing one would be a deviation.

### D7 - Two free parameters, twelve cells, two arms, and a counted budget

| Parameter | Grid | Points |
|---|---|---:|
| `restart` | 0.2, 0.4, 0.6, 0.8 | 4 |
| `normalization` | `none`, `symmetric`, `stochastic` | 3 |

12 cells, measured on both seed arms: **24 dev evaluations**. The declared cap for the whole phase is
**40**, and one evaluation is one pass of one retriever over the 600 dev questions, whether by
`evaluate_retriever` or by `per_question_success`. The budget:

| Spend | Evaluations |
|---|---:|
| The grid (12 cells x 2 arms) | 24 |
| `restart = 0.0` at the chosen normalization, both arms (HU-2) | 2 |
| The frozen configuration measured on dev by `evaluate` | 2 |
| Failure analysis on dev @2,048, both arms (HU-8) | 2 |
| **Total** | **30** |

Ten evaluations of slack, and the count is written into the artifact as `dev_evaluations_spent`.
`restart = 1.0` is **not** in the grid: it is the seed, and it is asserted by a test rather than paid
for with a dev evaluation.

### D8 - One decision, and the tie-break is cost

The ledger holds **one** decision: the cell (`restart` x `normalization`), chosen over 12
alternatives on **Full Support at 2,048 tokens on dev, on the dense-seeded arm**.

The choice is made on the dense arm and **applied unchanged to the conceptual arm**. Choosing
separately per arm would make the two differ in more than the seed, which is precisely what HU-3
forbids and what would make the isolating variant stop isolating anything. The conceptual arm's own
grid is measured and reported beside it; a disagreement between the two optima is a finding, not a
second choice.

Two ties, resolved in advance and in the conservative direction:

- **Margin below `resolvable_margin`** (the Phase 3 function, unchanged): the cell with **fewer mean
  iterations** wins. §73 is the reason - a gain paid for in compute is not free - and it hands a close
  call to a declared criterion instead of to a few thousandths on 600 questions.
- **Equal recall and equal iterations**: the **larger restart** wins. More restart is less expansion,
  so an undecided measurement cannot arrive as evidence for the system under test. This is Phase 3's
  rule (`tie toward the option that claims less`) in this phase's vocabulary.

### D9 - The two arms differ in the seed and in nothing else

`DiffusionRetriever` takes its seed as a constructor argument and reads nothing else about it. A test
builds both arms from the same parameters and asserts that every recorded field but `seed_arm` and the
seed object itself is equal, because giving one arm a different operator is the single easiest way to
manufacture this phase's headline.

### D10 - The trace: produced as it runs, scoring nothing, sampled by a rule fixed now

Tracing is off by default and enabling it changes no score - asserted by running the same question
both ways and comparing the ranking. The trace is built **inside the loop**, because a trace
reconstructed from the final ranking can disagree with the run it claims to explain.

**The sample rule, declared before the run**: the 72 dev questions that defeat both baselines, plus
the symmetric difference between System C and dense on dev @2,048 (every question one answers and the
other does not). The *rule* is fixed here; which qids it selects is known only after the run, which is
the point.

One artifact per (seed arm, config digest), written atomically with a digest, holding **concept ids
and never labels**. Labels are joined in only when the trace is read for the report, from the Phase 2
artifact, by the reporting code - never by anything under `retrieval/`.

### D11 - The freeze, and why `evaluate` grows a system selector

The Phase 4 selection is written once and never overwritten, exactly as Phase 3's is, and
`check_freeze_precedes` is applied to every expansion result against the Phase 4 artifact.

`cer evaluate` currently measures all five Phase 3 systems on every split it is given. Running it
again for Phase 4 would produce a **second test-split result for each of them**, and Phase 3's D10
declares a `-2` suffix on a Phase 3 test result to be a deviation document waiting to be written. So
`evaluate` gains a `--systems` selector, and the Phase 4 test read names the two expansion systems
only. HU-7 asks for the rivals' numbers to be read from the Phase 3 files rather than recomputed, and
this is the mechanism that makes that the only possibility rather than a good intention.

The Phase 3 freeze requirement is unchanged: test is not read without it. The expansion systems
additionally require the Phase 4 freeze, and refuse to be built without it.

### D12 - The per-run counters live on the retriever, and the CLI merges them into the result

`evaluate_retriever` receives its config **before** it runs, and the harness is not to be modified, so
a measurement of the run itself cannot arrive through that door. `DiffusionRetriever` therefore
accumulates `mean_iterations`, the iteration histogram, the sparse-product count and the clipped-seed
count as it goes; the CLI reads them after `evaluate_retriever` returns and writes the augmented
result with `dataclasses.replace(result, config={**result.config, ...})`.

This is why `mean_iterations` and `iterations_histogram` sit in `config` rather than in `cost`,
where they arguably belong: `cost` is written by the harness and the harness is frozen. The spec's
data contract puts them in `config` for the same reason.

Mutable per-run state on a retriever is a smell, so it is bounded: the counters are reset at the start
of every run, they are never read by the scoring path, and a test asserts both.

### D13 - `selection.py` gains public primitives, and the Phase 3 artifact must still verify

The Phase 4 artifact follows Phase 3's pattern rather than inventing a second one, so three primitives
stop being private: the payload serializer, the payload digest, and the freeze-ordering check
generalized over both report types. `Decision`, `resolvable_margin` and `load_selection` are imported
and used unchanged.

**No payload key, value or serialization order changes.** The risk this decision carries is that a
refactor silently invalidates the digest of the Phase 3 selection already frozen on disk, which would
make every Phase 3 number unverifiable. A test therefore loads `data/selection/selection.json` and
checks that it still verifies, and it fails loudly if the shape ever drifts.
