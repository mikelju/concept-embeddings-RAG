# Spec Phase 6: Dense + Entity Navigation — end-to-end comparison

> Functional specification — WHAT to build and WHY.
> The HOW belongs in the phase plan (`6.0_*.md`).
> Acceptance criteria are verified with `/7-verificar` when the phase ends.

---

## Problem and objective

**Problem.** Phase 5 established a positive second-hop signal for text-derived entities on a frozen
HotpotQA bridge diagnostic: the entity hop beat BM25-on-question at hit@10 on the pilot. That result is
useful evidence about the mechanism, but it is not an end-to-end retrieval result. In particular, at
hit@100 the entity hop was behind BM25 on `p1` text, and the Phase 5 gate did not test the complete
retrieval pipeline at a fixed context budget.

The project already has a stronger, measured hybrid: **dense + BM25**. Its historical test result is
**0.8643 Full Support at 2,048 tokens**. The research question is therefore no longer whether entity
navigation can beat an isolated second-hop comparator; it is whether entity navigation can replace the
BM25 component in the complete hybrid without giving up retrieval quality.

**Objective.** Compare two otherwise equivalent end-to-end systems under one frozen protocol:

```
A = Dense + BM25
B = Dense + Entity Hop
```

The phase must determine whether the entity signal can substitute for the lexical signal while keeping
the project's fixed-budget evaluation and contamination discipline. The phase is a measurement of a
replacement hypothesis, not an invitation to add more entity machinery.

**What this phase does not attempt.** It does not test concepts, entity canonicalization, relations or
attributes, multi-round expansion, or `Dense + BM25 + Entity`. It also does not reopen Phase 3's concept
space decisions or Phase 5's extraction result. Those are separate questions and stay outside this
specification.

---

## What is inherited and stays fixed

The following are inputs to the phase, not new choices:

| Item | Frozen value / rule |
|---|---|
| Corpus | Phase 1 frozen HotpotQA distractor pool, 19,366 paragraphs |
| Population | 600 dev / 1,400 test, from the frozen Phase 1 partition |
| Indexing unit | One complete benchmark paragraph; same `indexable_text` as dense and BM25 |
| Dense retriever | Phase 1 retriever and embedding cache, unchanged |
| BM25 retriever | Phase 1 retriever, unchanged |
| Context budgets | 512, 1,024, 2,048 and 4,096 tokens |
| Headline metric | Full Support; Gold Paragraph Recall and Context Precision remain required |
| Secondary retrieval metrics | Recall@2, Recall@5, Recall@10 |
| Tokenizer / filling rule | Phase 1 harness, unchanged |
| Random seed | Frozen project seed / manifest seed |
| Entity representation | Phase 5 raw text-derived **entity-only** node index; no canonicalization |
| Entity scoring | Phase 5 frozen one-hop score and deterministic ranking rule |
| Entity origin | Dense `p1`, the first dense paragraph for the question |
| Entity hop depth | The Phase 5 one-hop candidate set; no second entity hop |

The historical 0.8643 Full Support @2,048 result is a **reference bar** only. The Phase 6 comparison must
still evaluate both systems under the same explicitly frozen protocol rather than infer a conclusion from
the Phase 5 diagnostic or from unlike result files.

## User stories

### HU-1: The end-to-end population and protocol are frozen before measurement

**As** the researcher,
**I want** the evaluation population, budgets, metrics and inherited components fixed before the entity
system is measured,
**so that** the replacement claim cannot move after seeing the result.

**Acceptance criteria:**
- [ ] The phase records the exact pool hash, Phase 1 manifest identity, split sizes, tokenizer,
      budgets, primary metric, secondary metrics, seed and evaluation harness version.
- [ ] The evaluation population is the complete frozen Phase 1 population: 600 dev and 1,400 test;
      no question is sampled or manually excluded.
- [ ] No test question or test metric is read during implementation, debugging or selection.
- [ ] The Phase 6 run refuses to proceed if the pool, tokenizer or split does not match the inherited
      Phase 1 artifacts.
- [ ] The test configuration is frozen before the first test question is evaluated.

### HU-2: The Dense + BM25 control is frozen, not re-optimized for the comparison

**As** the researcher,
**I want** the existing dense + BM25 hybrid treated as a fixed control,
**so that** the experiment measures replacement of BM25 rather than a new optimization of the control.

**Acceptance criteria:**
- [ ] The control is built through the same fusion/evaluation mechanism used by the project for the
      existing dense + BM25 result.
- [ ] The Phase 3 control configuration and result provenance are read and verified, not retyped from
      memory or reconstructed from the final decimal.
- [ ] If the historical control artifacts exactly match the Phase 6 protocol, they are reused as the
      reference rather than recomputed unnecessarily.
- [ ] If a protocol mismatch requires a fresh control measurement, that measurement is completed and
      frozen on dev before test and is reported as a Phase 6 protocol reconciliation.
- [ ] The control receives no entity-specific adjustment, extra tuning or privileged candidate depth.

### HU-3: Entity navigation is the only new retrieval signal

**As** the researcher,
**I want** System B to replace BM25 with the Phase 5 raw entity hop and nothing else,
**so that** any difference is attributable to the entity-navigation mechanism.

**Acceptance criteria:**
- [ ] Entity retrieval uses the frozen Phase 5 extraction and node-index artifacts; no new LLM
      extraction is performed.
- [ ] Only **entity nodes** are used. Concepts are excluded completely from the retrieval path.
- [ ] The entity hop starts from dense `p1` and uses the Phase 5 frozen one-hop scoring semantics,
      normalization and tie-breaking.
- [ ] Entity canonicalization, clustering, alias resolution, relation nodes, attribute nodes and
      multi-round expansion are not introduced.
- [ ] No question text, answer, supporting fact or gold annotation enters entity extraction,
      normalization or candidate generation.
- [ ] The Phase 5 entity index is treated as immutable input; changing it is a separate research phase.

### HU-4: Dense + Entity uses the same hybrid machinery as the control

**As** the researcher,
**I want** Dense + Entity built through the same fusion and ranking machinery as Dense + BM25,
**so that** the comparison is about the component being substituted rather than about different
fusion implementations.

**Acceptance criteria:**
- [ ] Dense + Entity implements the same `Retriever` contract as the control components.
- [ ] The dense component is the unchanged Phase 1 retriever.
- [ ] The entity component is the frozen Phase 5 entity-hop retriever.
- [ ] The same score normalization and fusion scheme is used for Dense + BM25 and Dense + Entity.
- [ ] The same candidate-list depth and deterministic tie-breaking rules apply to both hybrids.
- [ ] No special weighting, post-filtering or candidate expansion is introduced only for the entity
      system.
- [ ] RRF remains the parameter-free reference where the existing Phase 3 machinery defines it; any
      weighted fusion is fitted by exactly the same procedure and grid for both hybrids.

### HU-5: Any dev selection is made by one declared procedure and frozen once

**As** the researcher,
**I want** all choices that can affect the comparison selected on dev only,
**so that** the test set remains a genuine held-out evaluation.

The phase does not reopen Phase 3's research questions. It may only fit whatever fusion choice is
strictly necessary to make the two hybrids comparable under the inherited protocol.

**Acceptance criteria:**
- [ ] The phase has no new representation hyperparameter to optimize: no entity threshold, no
      canonicalization threshold, no hop depth grid, no relation setting and no concept setting.
- [ ] If fusion weights must be fitted, both systems use the identical declared grid and selection
      objective on the 600-question dev split.
- [ ] The dev selection objective is **Full Support at 2,048 tokens**, matching the project's prior
      hybrid selection protocol.
- [ ] The complete dev table at all four budgets is retained, so a choice that looks good only at one
      budget cannot be hidden.
- [ ] Ties between candidate fusion choices are resolved by the same conservative rule already used by
      Phase 3; no result-derived preference for Entity is introduced.
- [ ] The selected configuration is written to a versioned freeze artifact before test is read.

### HU-6: The primary comparison is end-to-end and fixed-budget

**As** the researcher,
**I want** both systems evaluated through the unchanged Phase 1 harness,
**so that** a second-hop improvement that does not survive context filling is not mistaken for an
end-to-end improvement.

**Acceptance criteria:**
- [ ] Dense + BM25 and Dense + Entity are evaluated at exactly 512, 1,024, 2,048 and 4,096 tokens.
- [ ] Both systems use the identical context-filling rule: ranked units are added whole until the
      budget is reached; units that do not fit are skipped and the next ranked unit is considered.
- [ ] The headline metric is Full Support; Gold Paragraph Recall and Context Precision are reported
      alongside it.
- [ ] Recall@2, Recall@5 and Recall@10 are reported for continuity with earlier phases.
- [ ] Dense-only is reported as the common baseline, so any apparent loss or gain can be read against
      the original retriever as well as against the BM25 control.
- [ ] Results are reported separately for dev and test; no test value participates in selection.
- [ ] Cost is recorded per system: mean query latency and mean units included at the largest budget.

### HU-7: The replacement question is answered explicitly, with paired evidence

**As** the researcher,
**I want** the comparison to distinguish replacement, improvement and regression,
**so that** the phase does not turn an arbitrary decimal difference into a claim.

**Acceptance criteria:**
- [ ] The report states the Full Support result of Dense + BM25 and Dense + Entity side by side at
      every budget on dev and test.
- [ ] The report states the paired per-question differences on the headline test comparison at
      2,048 tokens: Entity-hybrid wins, BM25-hybrid wins and ties.
- [ ] The report includes the paired Gold Paragraph Recall difference at 2,048 and the complete
      per-budget metric table.
- [ ] Any claim that Entity can **replace** BM25 is based on the predeclared decision rule below,
      not on a favorable-looking single aggregate percentage.
- [ ] The report also shows failure analysis against dense-only: which questions are newly recovered,
      which dense-supported questions are lost, and whether the effect is concentrated in the Phase 5
      bridge population.

### HU-8: The mechanism remains auditable

**As** the researcher,
**I want** the end-to-end result to remain traceable to the entity hop that produced it,
**so that** an apparent gain can be inspected rather than treated as a black-box hybrid.

**Acceptance criteria:**
- [ ] For every test/dev question where the entity component changes the final candidate set relative
      to dense, the run can identify the originating dense `p1` and the entity-hop candidate provenance.
- [ ] The entity-hop contribution can be traced back to the shared normalized entity nodes used by the
      Phase 5 index.
- [ ] Trace production changes no ranking or metric value.
- [ ] Entity traces and end-to-end results are bound to the relevant Phase 5 artifact digests and the
      Phase 6 run/freeze digest.
- [ ] The report reads a declared sample of recovered, unchanged and lost questions, selected by rule
      before qualitative inspection.

### HU-9: Contamination, reproducibility and provenance are first-class requirements

**As** the researcher,
**I want** the result to be reconstructable from frozen artifacts without touching the test set during
selection,
**so that** the replacement claim is defensible.

**Acceptance criteria:**
- [ ] The Phase 6 code path has no access to gold labels during retrieval or entity scoring.
- [ ] The Phase 5 extraction and entity node index are loaded by verified digests; a mismatch aborts.
- [ ] The dev freeze artifact records every fitted choice and the artifact versions used to fit it.
- [ ] The test result records the frozen configuration digest, pool hash, Phase 1 baseline identity,
      Phase 5 entity-index identity and code version.
- [ ] A second run over unchanged inputs either reproduces the result or reports the source of any
      nondeterminism; no silent overwrite is allowed.
- [ ] The test split is read exactly once under the frozen configuration, unless a deviation document
      explicitly records why that rule had to be broken.

### HU-10: The phase ends with a declared decision about the research line

**As** the researcher,
**I want** the end-to-end evidence to determine what happens next,
**so that** canonicalization and additional combinations are consequences of evidence rather than
assumptions.

The phase uses the following decision rule, declared before measurement:

| Outcome | Condition |
|---|---|
| **ENTITY-REPLACEMENT SUPPORTED** | At 2,048 test tokens, Dense + Entity is not lower than Dense + BM25 on Full Support, and the paired test does not show a significant Entity deficit; the report must still state the absolute difference and its uncertainty/paired counts. |
| **ENTITY-PARTIAL / INVESTIGATE** | Dense + Entity shows a measurable positive end-to-end effect relative to dense-only, but fails the replacement condition above. This keeps the research line open only for a clearly identified follow-up question. |
| **STOP** | Dense + Entity shows no useful end-to-end signal over dense-only, or the evidence shows a material regression without a compensating finding that the spec can distinguish. |

**Acceptance criteria:**
- [ ] The decision is computed from the declared test comparison and is not rewritten after seeing the
      result.
- [ ] `ENTITY-REPLACEMENT SUPPORTED` is never inferred from the Phase 5 hit@10 pilot alone.
- [ ] `ENTITY-PARTIAL / INVESTIGATE` must name the specific remaining question it opens; it does not
      automatically open canonicalization, concepts or a three-way hybrid.
- [ ] The founding decisions table remains unchanged unless a later verified phase establishes a new
      project-level decision.

## Decision rules and statistical convention

The phase's headline quantity is **Full Support at 2,048 tokens**, because that is the project's
existing end-to-end selection budget and the budget of the historical control bar.

For the paired test comparison, the unit is the **question**. For each question, compare the binary
Full Support outcome of Dense + Entity with Dense + BM25 at 2,048 tokens. Ties are retained for the
reported counts but excluded from the sign-test denominator. The same paired exact binomial convention
used elsewhere in the project is used if a significance test is required: two-sided reporting for a
neutral comparison, or a one-sided test only when the direction and alpha are explicitly fixed in the
phase plan before the result is seen.

The replacement rule deliberately separates **non-inferiority in the primary metric** from superiority.
A system does not need to beat BM25 to replace it; it must avoid a statistically supported regression at
the declared budget. Absolute differences, paired counts, and uncertainty are always reported so that a
numerical near-tie is not presented as proof of equality.

The four budgets remain mandatory because a component can be harmless at 2,048 while changing retrieval
behavior at 512 or 4,096. No secondary budget can overturn the predeclared headline decision, but any
important reversal is reported as part of the mechanism.

## Constraints and anti-goals

- No LLM call is introduced into the retrieval loop.
- No new entity extraction is performed during the end-to-end comparison.
- No concepts enter the system under test.
- No canonicalization, clustering, alias resolution or entity filtering is introduced.
- No relation or attribute graph is introduced.
- No multi-round traversal is introduced.
- No `Dense + BM25 + Entity` combination is introduced.
- No benchmark or corpus change is introduced.
- The Phase 1 evaluation harness remains unchanged. If it must change, that is a deviation and the
  interface problem is itself part of the finding.

---

## Success criterion

The phase succeeds by producing a defensible end-to-end answer to the replacement question, not by
forcing a positive result. A successful outcome may be superiority, non-inferiority/replacement,
partial evidence that motivates one sharply defined follow-up, or a negative result that closes the
line. In every case the comparison must be reproducible, fixed-budget, held-out on test, and traceable
to the Phase 5 entity-hop mechanism.
