# Spec Phase 6: Dense + Entity Navigation — end-to-end comparison

> Functional specification — WHAT to build and WHY.
> The HOW belongs in the phase plan (`6.0_*.md`).
> Acceptance criteria are verified with `/7-verificar` when the phase ends.

---

## Problem and objective

**Problem.** Phase 5 found a positive second-hop signal for text-derived entities on a frozen
HotpotQA bridge diagnostic: the entity hop beat BM25-on-question at hit@10 on the 152-question dev
pilot (56 wins, 24 losses, 72 ties, p = 0.000226). That is evidence about the mechanism, not an
end-to-end retrieval result. At hit@100 the entity hop was behind BM25 on `p1`'s text (0.7434 against
0.7533), and the Phase 5 gate never tested a complete pipeline at a fixed context budget.

The project already has a stronger measured hybrid: **Dense + BM25**, fitted in Phase 3 and recorded
at **0.8643 Full Support at 2,048 tokens on test** (1,210 of 1,400), against dense's 0.8250
(1,155 of 1,400). That figure is a historical measurement under the Phase 3 protocol. It becomes this
phase's control figure only if Phase 6 reproduces it (HU-2); it is never compared with a new system
across a protocol difference.

**Objective.** Answer one question:

> **Can an entity-based second hop replace the BM25 component of the Dense + BM25 system without
> reducing retrieval quality?**

```
A = Dense + BM25        (hybrid-bm25)
B = Dense + Entity Hop  (hybrid-entity-hop)
```

"Replace without reducing quality" is tested as **non-inferiority** of B against A on a pre-declared
metric, margin and test (see "Decision rules and statistical convention"). A second, separate question
— whether B adds anything over dense alone — is tested beside it. The phase ends in exactly one of
three states: **ENTITY-REPLACEMENT-SUPPORTED**, **ENTITY-PARTIAL / INVESTIGATE** or **STOP**.

**Three things this spec keeps apart.**

1. **The frozen historical control** — the Phase 3 Dense + BM25 configuration and its recorded
   results. Inherited, verified by reproduction, never re-optimized (HU-2).
2. **The fusion procedure** — the Phase 3 code path that built and fitted that control: normalization,
   schemes, grid, dev objective, tie rules. Reused unchanged, and applied identically to both hybrids
   (HU-4, HU-5).
3. **The decisions Phase 6 takes to build Dense + Entity** — only B's fusion scheme and weight, taken by
   procedure (2) on dev, plus the infrastructure change needed to admit a second-stage component
   (see "The two systems, defined").

**What this phase does not attempt.** It does not test concepts, entity canonicalization or
resolution, relations or attributes, multi-round or multi-hop expansion, or `Dense + BM25 + Entity`.
It introduces no new representation, no new extractor, no new LLM extraction, and no change of
corpus or benchmark. It does not reopen Phase 3's representation or control decisions, nor Phase 5's
extraction or gate. Those are separate questions and stay outside this specification.

## The two systems, defined

### Dense-only (`dense`)

The Phase 1 retriever, unchanged. It is the common baseline, the reference of the secondary question,
and the "no second signal" reference from which the non-inferiority margin is derived.

### A — Dense + BM25 (`hybrid-bm25`)

The Phase 3 `FusedRetriever` over `[dense, bm25]`. Each component is asked for `top_k = 100`; the
fused list is the best 100 of the union of the two lists (at most 200 units). Its scheme and weight
are the frozen historical ones when the control is reused, and the ones the same procedure selects on
dev if it has to be re-measured (HU-2). Nothing else about it is chosen in this phase.

### B — Dense + Entity Hop (`hybrid-entity-hop`)

**The Entity Hop is a second-stage candidate generator conditioned on dense's output, not a
retriever.** It never reads the question. It reads what dense returned for the question, and it
proposes paragraphs linked to dense's first paragraph by shared entity names. For each question `q`:

1. **Dense stage.** `D(q)` is the dense component's top-100 list, ordered by descending score with ties
   by unit id — the very list that enters the fusion. One dense retrieval per question serves both the
   conditioning and the fusion.
2. **Read set and origin.** `read(q)` is the first 10 units of `D(q)`; `p1(q)` is its first unit.
3. **Entity stage.** `E(q)` is the Phase 5 entity hop, unchanged:
   - a candidate `v` scores the sum of the weights of the **entity** nodes it shares with `p1(q)`,
     over binary incidence;
   - every unit of `read(q)`, `p1(q)` included, is excluded;
   - only candidates with a score **> 0** are kept;
   - candidates are ranked by descending score, ties by unit id;
   - the list is truncated at a **maximum depth of 100**, the depth every fusion component is asked
     for and Phase 5's deepest measured depth.

   Let `P(q)` be the number of positive candidates before truncation. Then `|E(q)| = min(100, P(q))`.
   **Nothing is padded:** if 34 candidates score above zero, `E(q)` holds 34; if none does, it is empty.
4. **Fusion.** `[D(q), E(q)]` enter the same fusion as A, dense first. The universe the fusion sees is
   `D(q) ∪ E(q)`: at least 100 and at most 200 units, the same bounds as A's. `E(q)` never contains the
   10 read units, so it can overlap `D(q)` only at ranks 11-100; when it lies wholly outside `D(q)` the
   union reaches 200. The fused list is the best 100 of that universe.

**Consequences of the inherited fusion on `E(q)`, declared rather than repaired.** They follow from
Phase 3's rules applied to a list of this shape, and none is compensated:

- **Empty `E(q)`** — `p1` has no entity node (as for a `p1` among the 8 failed extractions), or shares
  none with any unread paragraph. Under `weighted` the entity component abstains; under `rrf` it
  contributes no term. Either way B's ranking for that question is exactly `D(q)`, for any
  `w_dense > 0` (at the grid endpoint `w_dense = 0.0` every unit scores 0.0 and the order is by unit id).
- **Flat `E(q)`** — a single candidate, or all candidates at the same score. Under `weighted` min-max
  has no range, so the entity component abstains: every unit receives 0.0 from it, and for any
  `w_dense > 0` B's ranking is `D(q)` except possibly at the tail, where units tied at 0.0 break by unit
  id. Under `rrf` the list still contributes by rank, its internal ties broken by unit id. RRF has no
  abstention.
- **Bottom tier at 0.0** — min-max maps the lowest score present in `E(q)` to 0.0, the same value an
  absent unit receives, so under `weighted` that tier gets no entity contribution. The rule is the one
  applied to BM25's and dense's lowest returned scores; entity scores are coarse sums of a few weights
  with many ties, so the tier can be large.
- **No reinforcement of the read set** — the ten read units never receive an entity contribution,
  whereas BM25 can score them. This is the Phase 5 exclusion, a property of the mechanism.
- **At `w_dense = 1.0`** the weighted fusion equals dense except possibly among units tied at 0.0 in the
  tail. The same holds for A.

These cases are ordinary, not hypothetical. Over the 152 Phase 5 pilot questions (`hop-run.json`,
entity arm), `P(q)` has a mean of 173.3, a median of 34.5 and a maximum of 1,798; 6 questions have no
candidate, 11 have exactly one, and 105 have fewer than 100. Those figures are quoted from a frozen dev
artifact and choose nothing.

**What "the same opportunity to contribute" means.** Both second signals:

1. are cut at the same maximum depth of 100 candidates;
2. enter the same fusion function with the same fixed order (dense first), the same per-query min-max
   normalization over each component's own returned list, the same absent floor of 0.0, the same
   abstention rule, the same RRF constant and the same tie-breaks by unit id;
3. have their scheme and weight fitted by the same function, over the same grid, on the same 600 dev
   questions, against the same objective, with the same tie rules;
4. are filled into the same budgets by the same rule and measured by the same harness and metrics;
5. derive from the same pool text and the same dense list for the question.

It does **not** mean equal list lengths, equal access to the read units, or equal treatment of the
question text. Those differences define the two mechanisms. Equality is set in the pipeline, not by
padding the entity list, re-admitting read units or giving either signal its own floor.

**The infrastructure change needed to admit a second-stage component.** `FusedRetriever` accepts only
second signals named in `SECOND_SIGNALS = ("conceptual", "bm25")` that are `Retriever`s answering
`retrieve(query, top_k)`. An entity component conditioned on `D(q)` cannot be plugged in as it is, so
generalizing the hybrid to accept one is a **necessary infrastructure change, not a new signal**. The
implementation belongs to the plan. These invariants do not:

1. **A is unchanged, bit for bit.** `hybrid-bm25` returns identical rankings to the Phase 3
   `FusedRetriever` for every question, scheme and grid weight. HU-2's exact reproduction of every
   recorded figure is the end-to-end evidence; a direct ranking-level equality check is the plan's to
   write.
2. **The fusion primitives are unchanged:** normalization, floor, abstention, RRF, tie-breaks, the
   dense-first order, and the name rule `hybrid-` + the second component's name.
3. **The entity semantics are unchanged.** The component's output equals
   `node_hop(types=("entity",), p1, read, depth=100)`, as the continuity check of HU-3 shows.
4. **The entity component is conditioned on `D(q)` itself**, never on a second, differently ordered
   dense list.
5. **The harness sees the unchanged `Retriever` contract.** It cannot tell A from B.
6. **One fitting function serves both hybrids**, as Phase 3's D9 requires.
7. **No gold, answer, supporting fact or split label** is read anywhere on the retrieval path.

## User stories

### HU-1: The end-to-end population and protocol are frozen before measurement

**As** the researcher,
**I want** the evaluation population, budgets, metrics, inherited components and decision parameters
fixed before the entity system is measured,
**so that** the replacement claim cannot move after seeing the result.

**Acceptance criteria:**
- [ ] The phase records the pool hash, the Phase 1 manifest identity, the split sizes, the embedding
      model and revision, the tokenizer, the budgets, `top_k`, the metrics, the seed and the code
      version.
- [ ] The evaluation population is the complete frozen Phase 1 population, 600 dev and 1,400 test. No
      question is sampled or excluded — including questions whose `p1` has no entity node or whose
      entity list is empty, as Phase 5 kept its failed `p1`.
- [ ] No test question or test metric is read during implementation, debugging, fitting or freezing.
- [ ] The run refuses to proceed if the pool, split, tokenizer, embedding revision, node index,
      extraction, Phase 5 reference artifacts or `selection.json` do not verify.
- [ ] The decision parameters of the statistical convention (metric, budget, split, δ with its
      derivation, α, methods, state procedure) are copied from this spec into the freeze, and the
      freeze refuses a value that differs from the spec.
- [ ] The test configuration is frozen before the first test question is evaluated.
- [ ] On test the systems are evaluated in a fixed order: dense and A first, then the test reproduction
      check of HU-2 (in `reused` mode), then B. No B test figure exists before that point.

### HU-2: The Dense + BM25 control is inherited, verified by reproduction, and never re-optimized

**As** the researcher,
**I want** the Phase 3 Dense + BM25 hybrid treated as a frozen control whose reuse is earned by exact
reproduction,
**so that** the experiment measures the replacement of BM25 rather than a new optimization of the
control, and a historical figure is never compared across a protocol difference.

**What is inherited.** The historical control is the configuration Phase 3 froze: components
`[dense, bm25]`, scheme `weighted`, `w_dense = 0.5`, `w_bm25 = 0.5`, per-query min-max, absent floor
0.0, `top_k = 100`. It was selected by **gold paragraph recall at 2,048 tokens on the 600 dev
questions** (weighted curve 0.8592 … 0.9308 at `w = 0.5` … 0.9017, RRF 0.9208), **not** by Full
Support. Phase 6 does not re-optimize it, re-fit it by another objective, or give it another grid.

**What "reuse" means.** Result files store aggregates only, with no per-question outcomes and no
digest, while the statistical convention needs paired per-question outcomes. Reuse therefore means:

1. the frozen configuration is the control, taken as it is;
2. the historical figures are an **exact reproduction target**. Phase 6 re-executes the Phase 3 fitting
   function for `[dense, bm25]` on the 600 dev questions and must obtain `selection.json`'s control
   curve at all 11 grid points and its `rrf_score`, value for value — and so the same selection. It
   must also obtain the historical dev and test aggregates of `dense` and `hybrid-bm25` at every
   budget and every metric;
3. the paired data of the decision come from the Phase 6 run, whose aggregates are those historical
   figures once reproduced.

**Re-executing the procedure to verify reproduction is not re-optimization.** Its only admissible
output is the recorded one. If it could select anything else, the control would not be the recorded
one, and that is the incompatible branch below, not a choice.

**Acceptance criteria:**
- [ ] `selection.json` is loaded digest-verified; the historical result files are loaded and their
      configuration checked (`unit_set_hash`, `tokenizer`, `seed`, `top_k`, `model`, `revision`, and
      for `hybrid-bm25` also `fusion_scheme` and `fusion_weights`). Every value is read, not retyped
      from memory or reconstructed from a decimal.
- [ ] **Dev reproduction.** The re-executed fit gives the control's curve and `rrf_score` equal to
      `selection.json`, and therefore weighted with `w_dense = 0.5`. The Phase 6 dev aggregates of
      `dense` and `hybrid-bm25` equal their historical dev files exactly, at all four budgets, for gold
      recall, Full Support, precision, recall@{2, 5, 10} and mean units included. Latency is not
      deterministic and is excluded.
- [ ] **Test reproduction** (`reused` mode). Before B is evaluated on test, the Phase 6 test aggregates of
      `dense` and `hybrid-bm25` equal their historical test files exactly, by the same list of figures.
      In `re-measured` mode the historical test files are compared descriptively, since the
      incompatibility was already recorded before test, and differences are reported without stopping
      the run.
- [ ] **Compatible** — every check passes: the control mode is `reused`. The historical configuration is
      the Phase 6 control, and the historical aggregates are confirmed as this phase's own.
- [ ] **Incompatible at dev** — any dev check fails: the mode is `re-measured`. A deviation document
      (`6.Y_name.md`) records the mismatch before anything further is measured. The control's scheme
      and weight are then taken from the identical procedure (HU-5) run under the Phase 6 protocol,
      **solely to reconcile the protocol**, and frozen with B's before test. The historical 0.8643 and
      `w = 0.5` are reported as history only and are never compared with B.
- [ ] **Incompatible at test** — a test check fails in `reused` mode: the run stops before any B test
      figure exists and
      a deviation document identifies the cause. The mode becomes `re-measured`. If the cause
      invalidates the dev fit, the control is re-fitted on dev and a new freeze is written before test
      is read again; otherwise the frozen fit stands. Either way `dense` and A are re-read on test under
      the valid freeze, A's figures are taken from the Phase 6 measurement and never from the historical
      file, and B is then evaluated once.
- [ ] The control receives no entity-specific adjustment, no extra tuning and no privileged candidate
      depth, in either mode.
- [ ] The mode (`reused` or `re-measured`) and every dev reproduction check, with its outcome, are
      recorded in the freeze. The test checks are recorded in the decision artifact.
- [ ] The non-inferiority margin δ does not depend on the mode: it is fixed by the statistical
      convention from the historical record.

### HU-3: The Entity Hop is the Phase 5 mechanism, used as a second-stage generator

**As** the researcher,
**I want** System B to replace BM25 with the Phase 5 raw entity hop, conditioned on dense's output and

**so that** any difference is attributable to that mechanism and not to a new variant of it.

### HU-5: Dev selection uses one procedure and one objective, frozen once

**As** the researcher,
**I want** every choice that can affect the comparison made on dev, by the procedure that produced the
control,
**so that** test remains a genuine held-out evaluation and the two hybrids differ only in their second
signal.

**The policy.** Phase 6 inherits Phase 3's fusion procedure without reopening Phase 3's representation
decisions. Both hybrids use exactly the same normalization, grid, dev selection objective, weight
tie-break and weighted-versus-RRF rule. If the historical control cannot be reproduced under that
protocol, it is re-measured by the same procedure, solely to reconcile the protocol, before test
(HU-2). This rules out the one asymmetry that would void the comparison: a BM25 weight inherited from
one objective beside an entity weight optimized by another metric or procedure.

**Selection objective and decision metric are different roles, with one value each.**

- **Dev selection objective: gold paragraph recall at 2,048 tokens**, for both hybrids. It is the
  objective that produced `w_dense = 0.5`. Selecting B on anything else would make "same procedure"
  false, and re-selecting both on Full Support would re-optimize the control.
- **Test decision metric: Full Support at 2,048 tokens** (statistical convention). It is the metric the
  control was judged on in Phases 3 and 4, and the one this project treats as deciding for a multi-hop
  question. Phase 4's selection on Full Support chose an expansion cell, not a fusion weight, and is
  not a hybrid selection protocol.
- **Gold recall does not handicap the entity mechanism.** Every question has exactly two gold
  paragraphs, so a question's gold recall is 0, 0.5 or 1, and Full Support is gold recall = 1. The
  entity hop's own gain — turning a half-supported question into a fully supported one by finding a
  missing paragraph linked to `p1` — raises gold recall by exactly as much as any other gold paragraph
  does, and never goes unrewarded. The two metrics differ in two places only: gold recall counts
  0 ↔ 0.5 transitions, which Full Support ignores, and it weighs a 0 → 1 transition twice as much as
  a 0.5 → 1 transition, which Full Support weighs equally. Both differences apply to both hybrids by
  the same rule. They are inherited, symmetric, and made visible by the per-point dev metrics below.

**Acceptance criteria:**
- [ ] The phase has no representation hyperparameter to optimize: no entity threshold, no
      canonicalization threshold, no hop-depth or read-depth grid, no relation setting and no concept
      setting.
- [ ] B's scheme and weight are fitted by the **same fitting function** as the control, over
      `FUSION_WEIGHT_GRID` (0.0 to 1.0 in steps of 0.1, `w` on dense), with RRF measured on the same
      questions, against gold recall at 2,048 on the 600 dev questions.
- [ ] Ties between weights go to the larger dense weight; `weighted` is chosen only if its best score
      **strictly** exceeds RRF's, otherwise `rrf`. These are the Phase 3 rules, applied to both hybrids.
- [ ] No other figure — Full Support, recall@k, another budget, a test value — selects anything.
- [ ] If B's fit selects `w_dense = 1.0`, or RRF, the phase proceeds to test unchanged. The selection is
      reported as the finding it is; there is no early stop and no re-fit.
- [ ] For both hybrids, the dev metrics at all four budgets are retained for every grid point and for
      RRF, so a reader can see what Full Support would have favoured. Descriptive only.
- [ ] The dev table at all four budgets is reported for dense, A and B's selected configuration.
- [ ] The dev decisions are counted by Phase 3's rule: for B, the scheme, plus the weight when
      `weighted` wins (2, or 1 if RRF wins); for the control, none in `reused` mode and the same count
      in `re-measured` mode.
- [ ] The selected configurations, the decision parameters and the qualitative sampling rule of HU-8
      are written to a versioned freeze artifact before test is read.

### HU-6: The comparison is end-to-end, at fixed budgets, with per-question outcomes

**As** the researcher,
**I want** all three systems measured by the Phase 1 harness's unchanged measurement semantics, with
each question's outcome recorded,
**so that** a second-hop improvement that does not survive context filling is not mistaken for an
end-to-end improvement, and so that the paired tests have the data they need.

**The harness's measurement stays unchanged. Its record is extended.** The retrieval call, `top_k`, the
filling rule, the metric definitions and their aggregation stay as they are. What the harness lacks is
a record of per-question outcomes, which the paired statistics require. Adding that record is the one
declared extension, admissible only because it changes nothing the harness already produces.

**Acceptance criteria:**
- [ ] `dense`, `hybrid-bm25` and `hybrid-entity-hop` are evaluated at exactly 512, 1,024, 2,048 and
      4,096 tokens, with `top_k = 100` and the same tokenizer, on dev and on test.
- [ ] All three use the identical filling rule: ranked units are added whole while they fit; a unit
      that does not fit is skipped and the next ranked unit is considered.
- [ ] Gold recall, Full Support and context precision are reported at every budget, and recall@2, @5
      and @10 for continuity with earlier phases.
- [ ] **Per-question outcomes are recorded** for every system, split and budget: gold recall, Full
      Support, precision, units included; and recall@{2, 5, 10}.
- [ ] Aggregates recomputed from the per-question records **equal the harness's own aggregates
      exactly**. A mismatch invalidates the run.
- [ ] The extension does not alter the harness's aggregates. HU-2's reproduction of the historical
      files, run with the extension active, demonstrates it. Any other change to the harness is a
      deviation.
- [ ] Dense-only is reported as the common baseline beside both hybrids.

## Decision rules and statistical convention

Everything in this section is fixed before any Phase 6 number exists, and copied into the freeze
before test is read.

### What is decided, and on what

| Element | Value |
|---|---|
| Decision metric | **Full Support** (both gold paragraphs inside the context) |
| Budget | **2,048 tokens** — the budget of the control's selection, the historical bar and every failure analysis of this project |
| Split | **test**, all 1,400 questions |
| Statistical unit | The **question** |
| Pairing | The same question across systems, all measured in the same Phase 6 run |
| Comparisons | B vs A (primary, non-inferiority); B vs dense (secondary); A vs dense (assay sensitivity) |
| α | **0.05, one-sided**, for every decision test |

### Primary question: can B replace A? (non-inferiority)

**Notation.** For test question `i`, `A_i` and `B_i` are 1 when the system fully supports it at 2,048
tokens. `b` counts questions with `B_i = 1, A_i = 0`; `c` counts `B_i = 0, A_i = 1`; `n = 1,400`. The
difference is `Δ = p_B − p_A`, observed as `Δ̂ = (b − c) / n`. **Ties — questions both systems support,
or neither does — stay in `n`.** The sign tests below drop ties from their denominator; this test does
not.

**Hypotheses.** `H0: Δ ≤ −δ` against `H1: Δ > −δ`. Non-inferiority means rejecting `H0`.

**The margin.** `δ = (1 − f) × M1`, where:

- `M1 = 55 / 1,400 = 0.039286` is the historical **test** effect of A over dense on Full Support at
  2,048: 1,210 − 1,155 questions, read from `run-hybrid-bm25-test-20260911T133204+0000.json` and
  `run-dense-test-20260911T133159+0000.json`;
- `f = 0.5` is the fraction of that effect B must be shown to preserve, so the tolerated loss is the
  remaining `1 − f`;
- so **`δ = 0.5 × 55 / 1,400 = 55 / 2,800 = 0.019643`**, 27.5 questions out of 1,400.

In words: **B replaces BM25 when it is shown to keep more than half of what BM25 added to dense.**

**δ is a predefined methodological decision, not a statistically inferred quantity.** No estimate,
test or interval produced it, and none can revise it: `M1` is a recorded historical difference taken
at face value, `f` is a declared value judgment, and δ follows from the two by arithmetic. It is fixed
here, before any Phase 6 measurement.

Why this margin:

- **Effect preservation.** What BM25 adds to dense is the only quantity this project has measured
  that says what the replacement must keep. Literal zero tolerance cannot be tested (it would be a
  superiority test), so the margin is set as a fraction of that effect — the standard framework for
  non-inferiority margins.
- **Why half.** `f = 0.5` is the most commonly used preserved fraction. A stricter `f = 0.75` would
  give `δ = 0.25 × M1 ≈ 0.98` points, below what the fixed population can resolve (see "Precision" below): under
  the same approximation, a B exactly as good as A would be declared non-inferior only about a third of
  the time at 10% discordant pairs. The question would be close to unanswerable by design. The choice
  of `f` is a value judgment; it is closed here and changeable only under "Freezing the decision
  parameters".
- **Why the test effect, not the dev effect.** The control's weight was fitted on dev, so its dev
  effect (31 / 600 = 0.0517) is optimistically biased, and it would give the more lenient
  `δ = 0.0258`. The test effect is the held-out estimate, and the stricter of the two.
- **Why this is not tuning on test.** δ is not a parameter of any system and selects nothing. It uses
  only the results of dense and of the frozen control, recorded on 2026-09-11 before this phase existed
  and already quoted in the master plan. It holds no Entity data. It is fixed here, before any Phase 6
  measurement. Because the population is the same fixed 1,400 questions and both systems are
  deterministic, the margin framework's constancy assumption holds by construction. In `reused` mode
  HU-2's test reproduction verifies it rather than assuming it. In `re-measured` mode it is an
  assumption, recorded as such in the deviation.
- **Declared gap: the uncertainty of M1.** The historical files store aggregates only, so the
  discordant counts of A against dense on test are unknown and no interval for M1 can be computed. The
  conservative "95–95" variant, which takes M1 at the lower limit of its interval, is therefore not
  applied: obtaining that interval before the freeze would mean reading test per question. δ uses the
  point estimate. After the run, the interval for A − dense computed from the Phase 6 outcomes is
  reported descriptively and cannot change δ or the state.
- δ is the same in `reused` and `re-measured` control modes.

**The test.** **Tango's score test** for the difference of paired proportions (Tango, 1998) at
`Δ0 = −δ`, one-sided at α = 0.05. Equivalently, the lower limit `L` of Tango's two-sided 90% score
interval for Δ, computed over all `n = 1,400` questions. **N passes if and only if `L > −δ`**, strictly.
Why this method: it is the standard matched-pairs interval for non-inferiority, it behaves better than
the Wald interval near the boundaries, it is deterministic (no resampling, no random number
generator), and it is defined for any counts, including zero discordant pairs. The implementation is
validated against a published worked example before any Phase 6 test figure exists.

**α = 0.05, one-sided.** Why:

- It is the project's only declared α (`GATE_ALPHA`), the level of the gate that opened this line.
  Changing α for the phase whose outcome it would decide invites the suspicion of tailoring.
- The regulatory convention of one-sided 0.025 exists so that a non-inferiority claim is no easier than
  a two-sided 0.05 superiority claim. This project's superiority claims are one-sided at 0.05, so the
  same parity principle gives 0.05 here. It is also the per-side level of the 90% interval standard in
  equivalence testing.
- The one-sided 97.5% bound is reported as a sensitivity reading. It decides nothing.

**Precision, stated before measuring.** A planning figure under the normal approximation, not a result:
the one-sided 95% bound lies about `1.645 × sqrt(d / n)` below `Δ̂`, where `d` is the share of discordant
pairs. That is about 1.0 points at `d = 5%`, 1.4 at 10% and 1.7 at 15%, against `δ ≈ 1.96` points. Even
if B were exactly as good as A, non-inferiority would fail about 25% of the time at `d = 10%` and 40% at
`d = 15%`. **An inconclusive replacement is therefore a plausible, predeclared outcome.** The population
is fixed: no question is added, and an inconclusive result is not re-tested.

### Secondary question: does B add anything over dense?

**S: B beats dense** on Full Support at 2,048 on test, by the project's paired exact sign test (exact
McNemar). Only questions where exactly one of the two systems succeeds count. **Ties are excluded from
this test's denominator.** Wins are B-only successes, losses are dense-only successes, and the p-value
is the one-sided exact binomial (p = 0.5, `alternative = "greater"`); no discordant question gives
p = 1. The direction, B > dense, is fixed now. **S passes if and only if p < 0.05.**

Positive evidence over dense means S passes and nothing weaker: not a positive difference, not a
favourable dev figure. The magnitude is reported beside it. The test is the Phase 5 gate's convention
(`gate.sign_test`).

### Assay sensitivity

**V: A beats dense**, by the same test. Non-inferiority to a control means something only if that
control, in the same measurement, does better than having no second signal at all. **V is a
precondition of ENTITY-REPLACEMENT-SUPPORTED and of route P2 of ENTITY-PARTIAL / INVESTIGATE**, the
two outcomes that rest on non-inferiority. When V fails, an N pass carries no evidence and grounds no
state.

In `reused` mode V cannot fail. With 1,210 and 1,155 reproduced, A-only successes exceed dense-only
successes by exactly 55, and dense-only successes are at most 190 (the questions A fails). So there are
at most 435 discordant questions, and the least favourable split, 245 wins in 435, still gives an exact
one-sided p of 0.0048. The rule is kept so the procedure stays complete in `re-measured` mode.

### Multiplicity

- **ENTITY-REPLACEMENT-SUPPORTED** asserts V, N and S together. Under the intersection-union principle
  (Berger, 1982), requiring every test to pass at α keeps the false-positive rate of the conjunction at
  or below α, so no adjustment applies.
- **ENTITY-PARTIAL / INVESTIGATE** is reached by one of two routes, mutually exclusive because S
  separates them. **Route P1** asserts S alone: one test at α. **Route P2** asserts V and N together,
  without S: by the same intersection-union principle, at or below α with no adjustment. Neither
  route asserts replacement.
- **STOP** asserts nothing positive.
- The descriptive tests and intervals below are not decisions. They are unadjusted and labelled as
  such.
- No test is repeated at another budget, metric or split to reach a state.

### The state procedure

Applied in order, once:

1. If **S, V and N all pass** → **ENTITY-REPLACEMENT-SUPPORTED**.
2. Otherwise, if **S passes** → **ENTITY-PARTIAL / INVESTIGATE, route P1**: a gain over dense is shown,
   replacement is not established.
3. Otherwise, if **V and N both pass** → **ENTITY-PARTIAL / INVESTIGATE, route P2**: B is non-inferior to
   a control shown to beat dense, but its own gain over dense is not shown.
4. Otherwise → **STOP**.

Every combination, so exclusivity and exhaustiveness can be checked row by row:

| S | V | N | State | Route | Recorded anomaly | Open question recorded |
|---|---|---|---|---|---|---|
| pass | pass | pass | ENTITY-REPLACEMENT-SUPPORTED | — | — | — |
| pass | pass | fail | ENTITY-PARTIAL / INVESTIGATE | P1 | — | *Does the raw entity hop keep more than half of BM25's contribution to the hybrid?* Not established: B adds to dense, but its deficit against A was not shown to be smaller than δ. |
| pass | fail | pass | ENTITY-PARTIAL / INVESTIGATE | P1 | control shows no effect over dense in this measurement; the non-inferiority pass is uninterpretable | *Can B replace A under this protocol?* Not judgeable: B adds to dense, but the control showed no effect over dense, so non-inferiority to it carries no evidence. |
| pass | fail | fail | ENTITY-PARTIAL / INVESTIGATE | P1 | control shows no effect over dense in this measurement | *Can B replace A under this protocol?* Not judgeable: B adds to dense, but the control showed no effect over dense, so non-inferiority to it carries no evidence. |
| fail | pass | pass | ENTITY-PARTIAL / INVESTIGATE | P2 | non-inferiority shown without evidence of a gain over dense | *Does B add anything over dense?* Not established: B lies within δ of a control shown to beat dense, but its own gain over dense was not shown. |
| fail | pass | fail | STOP | — | — | — |
| fail | fail | pass | STOP | — | control shows no effect over dense in this measurement; the non-inferiority pass is uninterpretable and grounds no state | — |
| fail | fail | fail | STOP | — | control shows no effect over dense in this measurement | — |

In `reused` mode V cannot fail (see "Assay sensitivity"), so only rows 1, 2, 5 and 6 can occur there.

**Why "N passes, S fails" is ENTITY-PARTIAL / INVESTIGATE when V passes.** B has then been shown to lie
within δ of a control that, in the same measurement, was shown to beat dense. That is evidence about
B's level, and STOP — whose record is that nothing shows B adds to dense or stands within δ of a
control shown to beat dense — would contradict it. It is not ENTITY-REPLACEMENT-SUPPORTED either: replacement also requires
B's own gain over dense, and S did not show it. So the row goes to route P2, with its anomaly and its
open question, and asserts neither replacement nor a gain over dense. **When V fails as well**, the N
pass is uninterpretable and grounds no state: with S failing too, nothing positive is shown, and the
state is STOP.

**The open question is fixed per row, now.** Every ENTITY-PARTIAL / INVESTIGATE row carries the question
written in the table, and the decision artifact records that text verbatim. It is never formulated,
chosen or reworded after the result is seen. The report may add observations, labelled as such, but
they are not the recorded question. Recording a question opens nothing.

### Mapping of foreseeable outcomes

`Δ̂` is the observed difference B − A; `L` is the Tango lower limit.

| Scenario | What it looks like | State |
|---|---|---|
| **(a)** Entity practically tied with BM25, but the test cannot affirm anything | `Δ̂ ≈ 0`, `L ≤ −δ` | **ENTITY-PARTIAL / INVESTIGATE (P1)** if S passes, recorded as "replacement inconclusive at the declared margin", never as "Entity is worse". **STOP** if S fails: N has failed, so route P2 cannot apply |
| **(b)** Entity worse than BM25 by a small amount | `−δ < Δ̂ < 0` | **ENTITY-REPLACEMENT-SUPPORTED** if S, V and N pass (`L > −δ`): the margin tolerates, by design, a deficit shown to be smaller than δ, and the absolute deficit is reported beside the state. **ENTITY-PARTIAL / INVESTIGATE (P1)** if S passes but `L ≤ −δ` or V fails. If S fails: **ENTITY-PARTIAL / INVESTIGATE (P2)** if `L > −δ` and V passes, otherwise **STOP** |
| **(c)** Entity clearly better than dense but worse than BM25 | S passes, `L ≤ −δ` | **ENTITY-PARTIAL / INVESTIGATE (P1)**. If the deficit is instead shown to be smaller than δ (`L > −δ`), the case is (b) |
| **(d)** Entity better than BM25, but not statistically conclusive | `Δ̂ > 0`, superiority not shown | **ENTITY-REPLACEMENT-SUPPORTED** if S, V and N pass (`L > −δ`); superiority is not claimed. **ENTITY-PARTIAL / INVESTIGATE (P1)** if S passes but `L ≤ −δ` (which only very high discordance allows) or V fails. If S fails: **ENTITY-PARTIAL / INVESTIGATE (P2)** if `L > −δ` and V passes, otherwise **STOP** |
| **(e)** Entity worse than BM25 and also worse than dense | `Δ̂ < 0`, B supports fewer questions than dense, S fails | **STOP**. In `reused` mode route P2 cannot occur here: B below dense means at most 1,154 supported questions against A's 1,210, so `Δ̂ ≤ −56 / 1,400 < −δ`, and since `L ≤ Δ̂`, N fails. In `re-measured` mode, if N and V were both to pass, the row (fail, pass, pass) applies: **ENTITY-PARTIAL / INVESTIGATE (P2)** with its anomaly |

### Superiority over BM25

Not this phase's question. It is reported descriptively: `Δ̂`, where the 90% interval sits relative to
zero, and the two-sided exact McNemar p-value of B against A. If the whole interval lies above zero, the
report says exactly that, as an observation. It adds no fourth state, changes no state and opens nothing.

### What each state records, and what it closes

- **ENTITY-REPLACEMENT-SUPPORTED** records that, on this benchmark and under this protocol, raw one-hop
  entity navigation from dense's `p1` was shown to keep more than half of BM25's contribution to the
  hybrid at Full Support @2,048, and to add to dense. It does not establish superiority over BM25,
  generalization beyond HotpotQA, or anything about canonicalization. It opens nothing by itself.
- **ENTITY-PARTIAL / INVESTIGATE** records its route — **P1**, B adds to dense (S) without replacement
  being established; or **P2**, B is non-inferior to a control shown to beat dense (V and N) without a
  gain over dense being shown — together with the tests that failed, the anomalies of its row, the open
  question written for its row (verbatim), the scenario that occurred and the diagnostics. Any other
  remark is a labelled observation. It opens nothing: no canonicalization, concepts or three-way hybrid
  without the author's decision and a new spec.
- **STOP** closes the line "the raw Phase 5 entity hop, fused with dense, as an end-to-end retrieval
  signal in this pipeline": there is no evidence it adds to dense at Full Support @2,048 on test, nor
  that it stands within δ of a control shown, in the same measurement, to beat dense. It
  gives Phases 7 and 8 no justification from this phase. It does not retract Phase 5's pilot finding,
  which was a shallow second-hop signal. Nor does it test other uses of entities — canonicalized,
  multi-hop, or in a three-way hybrid — which remain untested levers, listed and not scheduled. Any
  return to them is a new line, with its own spec, by the author's decision.

### Reported, deciding nothing

- The superiority reading above.
- The one-sided 97.5% Tango bound for B − A: sensitivity to the regulatory convention.
- The M1 interval: Tango's two-sided 90% interval for A − dense, from the Phase 6 outcomes.
- The two-sided exact McNemar p-value of B against dense, so that a significant loss in scenario (e) is
  visible.
- Every other budget, gold recall, context precision, recall@k, the dev figures, the bridge-like
  subgroup, the diagnostics and cost.

None of these can overturn or qualify the state.

## Constraints and anti-goals

- No LLM call is introduced into retrieval, and no API key is read by this phase.
- No new entity extraction, no new extractor, and no new representation.
- No concepts enter the system under test.
- No canonicalization, clustering, alias resolution, entity filtering, score threshold or
  entity-specific candidate expansion.
- No relation or attribute nodes.
- No multi-round or multi-hop traversal.
- No `Dense + BM25 + Entity` combination.
- No benchmark or corpus change, and no change of the embedding model or indexing unit.
- No re-optimization of the control: no re-fit by another objective, grid, budget or tie rule.
- No tuning against test. B is read on test once, under the frozen configuration.
- Phase 5 is not re-run or reopened. Its artifacts are immutable inputs, read to verify continuity.
- The harness's measurement semantics stay unchanged. Per-question outcome recording is the one
  declared extension, under HU-6's equality invariant; any other change is a deviation.
- The `FusedRetriever` generalization is the one infrastructure change on the retrieval side, under
  the seven invariants of "The two systems, defined"; A stays bit-identical.
- No new dependency is expected: the exact binomial test and the root finding Tango's interval needs
  are both available in the installed scientific stack. Any other need goes through ASK FIRST.
- New artifacts are JSON, written atomically, carry a digest and are verified on load; no `pickle`.
  Because the phase adds artifact deserialization, `/8-auditar` applies.
- ASCII only in `print()`, logging and Python strings.

## Success criterion

The phase succeeds when it produces a defensible answer to the replacement question: one of
**ENTITY-REPLACEMENT-SUPPORTED**, **ENTITY-PARTIAL / INVESTIGATE** or **STOP**, computed by the
declared procedure from per-question test outcomes. Each of the three is a successful outcome,
including a replacement that is inconclusive at the declared margin, recorded as exactly that.

In every case the comparison must be reproducible from frozen artifacts, fixed-budget, held-out on test,
built on a control that was either reproduced exactly or re-measured by the identical procedure, and
traceable to the Phase 5 entity-hop mechanism. The phase fails if the state cannot be regenerated by a
command, if test is read before the freeze, or if a historical figure is compared across a protocol
difference.
