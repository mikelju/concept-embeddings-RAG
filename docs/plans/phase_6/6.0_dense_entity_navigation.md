# Phase 6: Dense + Entity Navigation — end-to-end comparison

> Functional spec: [`6.spec.md`](6.spec.md) (methodology approved by the author, commit `89fea19`)
> This plan implements the requirements defined there. Twenty-four implementation steps, so the
> atomic breakdown lives in [`6.tasks.md`](6.tasks.md).

## Objective

Answer one question with a procedure written before any Phase 6 number exists: **can a second hop over
text-derived entity names, started from dense's first paragraph, replace the BM25 component of the
Dense + BM25 hybrid without losing Full Support at 2,048 tokens on test?**

```
A = Dense + BM25        (hybrid-bm25, the Phase 3 control)
B = Dense + Entity Hop  (hybrid-entity-hop)
```

The answer is one of **ENTITY-REPLACEMENT-SUPPORTED**, **ENTITY-PARTIAL / INVESTIGATE** or **STOP**,
computed by code from per-question test outcomes: Tango's score test for non-inferiority of B against
A at the margin δ = 55 / 2,800 (N), and two exact sign tests, B against dense (S) and A against dense
(V), all one-sided at α = 0.05.

What changes is one component and nothing else. The corpus, pool, splits, embeddings, dense and BM25
retrievers, budgets, tokenizer, filling rule, metrics, fusion primitives and fitting procedure are
inherited and verified on load; the entity representation is Phase 5's frozen node index, used
unchanged. The plan adds exactly two things the spec allows: a second-stage slot in `FusedRetriever`
and a per-question record in the harness.

**The deliverable is measured evidence**: a frozen dev configuration, the per-question outcomes of
three systems on both splits, the decision artifact, and `docs/plans/phase_6/6.results.md`. Each of
the three states is a successful outcome, an inconclusive replacement included.

## Success criteria

evidenced: **test** (a named test module, written in the task shown), **artifact** (a field checked on
the real artifact, by a data-dependent test or by `/7-verificar`), or **report** (`6.results.md`,
every figure read from an artifact).

## Technical notes and decisions

Every decision below is taken before a Phase 6 number is measured. Anything the measurement forces to
change is a deviation (`6.Y_name.md`), never an edit to this list. Decisions marked **[confirm]** are
choices the spec left to the plan that the author should see before implementation starts.

### D1 - Three stages, one artifact directory, nothing written under `data/results/` [confirm]

| Stage | Split | Does | Ends |
|---|---|---|---|
| `cer replace-check` | dev | verifies every input (D2, D3), the historical test files by identity only; runs continuity (a)-(d); re-executes the control fit; measures `dense` and A on dev with outcomes; writes `checks-dev.json` | non-zero exit on any mismatch, before any B figure |

| `cer replace-test` | test | the ordered protocol of D14, the first read of any test metric; decision; test diagnostics, traces, readout | decision written once |

Three stages because each ends where the spec demands a stop that may need a person: a dev mismatch
needs a deviation document before anything further is measured, the freeze must be committed before
test is read, and a test mismatch needs a deviation before B exists. Phase 5 split its pipeline the same
way (`pilot`, `extract`, `nodes`, `navigate`). The names say what the phase asks, replacement.

**Everything goes to `data/replacement/`, flat, and nothing to `data/results/`.** The spec leaves the
location to the plan under one invariant: no existing reader of `data/results/` may mistake a Phase 6
result for a Phase 3 one. There is such a reader: `comparison.load_rivals` takes the **newest**
`run-{system}-{split}-*.json` of each Phase 3 system in the directory it is pointed at, and
`test_the_reader_reproduces_the_published_phase_3_table` points it at `config.RESULTS_DIR`. A Phase 6
`run-hybrid-bm25-test-*.json` written there would silently become the Phase 3 control. A separate
directory closes that by construction; every Phase 6 result also carries `"phase": 6` in its config.

Layout: `checks-dev.json`, `freeze.json`, `run-{system}-{split}-{stamp}.json` (harness `RunResult`,
append-only), `outcomes-{system}-{split}.json`, `diagnostics-{split}.json`, `traces-{split}.json`,
`readout-{split}.json`, `test-reproduction.json`, `decision.json`.

### D4 - The second-stage slot in `fusion.py`

```python
SECOND_STAGES = ("entity-hop",)          # beside SECOND_SIGNALS, which is not touched

class SecondStage(Protocol):
    name: str
    def propose(self, first: Sequence[Hit], top_k: int) -> list[Hit]: ...
```

`_in_fixed_order` accepts a second component whose name is in `SECOND_SIGNALS` and that has `retrieve`,
or whose name is in `SECOND_STAGES` and that has `propose`; anything else is refused with the existing
"unknown second signal" message. `FusedRetriever.retrieve` becomes:

```python
first = dense.retrieve(query, top_k)
second = other.propose(first, top_k) if staged else other.retrieve(query, top_k)
return fuse([first, second], scheme=..., top_k=top_k, weights=...)
```

For A this is the same two calls, in the same order, on the same arguments, handed to the same `fuse`
as before. The name rule gives `hybrid-entity-hop`. The stage is asked for `top_k`, which the harness
sets to `EVALUATION_TOP_K = 100`: the stage's maximum depth is the depth every component is asked for,
and the freeze asserts `top_k == 100`.

**`SECOND_SIGNALS` is not extended.** `selection.py` unpacks it into exactly two names
(`SYSTEM_B_SIGNAL, CONTROL_SIGNAL = SECOND_SIGNALS`), and the Phase 3 `SelectionReport` files its two
fits by them. A third element would break that line; a separate tuple leaves Phase 3 untouched.

**`base.py` is not touched**: `test_the_measurer_and_the_interface_know_nothing_about_this_phase`
guards it, and the harness keeps seeing a `Retriever`.

### D6 - `EntityHopStage`, in `retrieval/`, calling Phase 5's hop unchanged

`EntityHopStage(index, weights)` with `name = "entity-hop"`. For a list `first = D(q)`:

1. **Refuses** a `first` not ordered by descending score then unit id, or holding a duplicate: the stage
   is conditioned on `D(q)` itself (invariant 4), so it checks it received that order rather than
   re-sorting silently.
2. `read = first[:PILOT_READ_DEPTH]`, `p1 = read[0]`, mapped to pool rows through `index.unit_ids`.
3. Calls **`second_hop.node_hop(index, weights, types=config.ENTITY_HOP_TYPES, p1=..., read=...,
   depth=top_k)`** and returns `[(candidate.unit_id, candidate.score), ...]`. Invariant 3 holds by
   construction; a test compares the stage with a direct call anyway.
4. An `expand(first, top_k)` method returns the full `EntityExpansion` (`p1`, `read`, the
   `RankedCandidate`s with their nodes, `P(q)`, the number of entity nodes of `p1`) for diagnostics and
   traces; `propose` is `expand` projected to hits.

- **Weights** are `second_hop.node_weights(index)`, computed once. It is the function Phase 5's hop run
  used, over the same index, so every entity weight is the one `hop-run.json` saw.
- **Types** come from `config.ENTITY_HOP_TYPES = ("entity",)`; the constructor takes no types, no
  depth, no threshold.
- **Memoized** by `(tuple(read), top_k)`. `E(q)` is a pure function of those, and a fit asks the same
  question 12 times with the same `D(q)`. Phase 3's `_MemoizingDictionary` is the precedent: an
  optimization the arithmetic cannot notice, returning copies.
- **Why in `retrieval/`**: the Phase 3 scoring-path guard globs `retrieval/*.py`, so HU-9's "no gold on
  the retrieval path" covers the stage automatically. `evaluation/second_hop.py` is outside that glob;
  T5 applies the same predicate to it explicitly. The import runs `retrieval -> evaluation.second_hop ->
  retrieval.conceptual`, which does not import `fusion`, so there is no cycle.

### D7 - Dense reads the question cache, and questions are measured in pool order

The historical files were produced with `CachedQueryBackend` (Phase 3 plan, D10, T18 note) and with
each split's questions in pool order (`[q for q in questions if q.split == split]`). Exact reproduction
of precision and recall means needs both: the precision mean is a floating-point sum of fractions and
depends on its order. Phase 6 measures every system the same way, and records the order used (D9).

### D8 - The harness extension: one optional sink

```python
def evaluate_retriever(..., split=None, outcomes: list[QuestionOutcome] | None = None) -> RunResult
```

When `outcomes` is given, the harness appends one `QuestionOutcome` per question, in its own loop
order: `qid`; per budget `gold_recall`, `full_support`, `precision` (the **same float objects** it
appends to its own lists) and `units_included` (`len(context)`); `recall_at_k` per `k`. With `outcomes`
absent nothing changes, and every existing harness test passes untouched. `RunResult` gains no field,
so result files keep their shape. The harness module must still not name `fusion`, `selection`,
`conceptual`, `dictionary_key` or `FusedRetriever` (existing guard). `units_included` has a harness
aggregate only at the largest budget (`cost.mean_units_included`); the other budgets are recorded and
not compared.

### D9 - `PerQuestionOutcomes`, and the order the aggregates are recomputed in

The spec's contract: `questions` sorted by qid, `aggregates`, `run_result`, `freeze_digest`, `digest`.
Aggregates must equal the harness's exactly, which requires averaging in the harness's order. That
order is not stored as a field: it is **the split's order in `pool.json`** (D7), and the loader takes
the pool's split order as an argument, reorders the records by it, recomputes every mean with the
harness's own `_mean` arithmetic, and refuses the artifact on any inequality with `aggregates` or with
the named run result's `metrics` and `cost.mean_units_included`. The qid set must equal the split's
population. Written once with a digest; a second file for the same system and split takes a `-2`
suffix and is only legitimate under a deviation (D14). This keeps the contract as the spec wrote it.

*Implementation note (T2, 2026-09-17):* on the pinned Python 3.12 the builtin `sum` over floats is
compensated (Neumaier), and `_mean` uses it. A search over 400,000 short lists and 3,000 long lists
(up to 1,400 terms) of fractions `k / n` found no list whose mean changed with the order of its terms,
so the toys of T2 and T3 cannot be "built so that sorted-qid order would give a different sum". The
order rule stays exactly as written (records in the harness's order, the loader reorders by the pool's
split order), because the contract asks for it and it costs nothing; T2 asserts exact equality on
fractional precisions, and T3 checks the reordering directly, by the order in which the loader hands
the values to the mean. The spec's rationale sentence is not edited here.

### D13 - The freeze [decided: the supersession field, OI-4]

### D15 - Tango's score test

**Source of the formula.** The expression below is transcribed from the R source of `scoreci.mp` in the
CRAN package `PropCIs` (read at rdrr.io/cran/PropCIs/src/R/scoreci.mp.R), whose documentation cites
Tango (1998). It is rewritten in this spec's notation (`b` = B-only successes, `c` = A-only, Δ̂ =
(b − c) / n); T10 checks it against the paper's own equation before code depends on it.

```
pb   = -(b + c) + (2n - b + c) * D0
pc   = -c * D0 * (1 - D0)
q    = (sqrt(pb^2 - 8n * pc) - pb) / (4n)
T(D0) = (b - c - n * D0) / sqrt(n * (2q + D0 * (1 - D0)))
```

At `D0 = 0`, `q = (b + c) / 2n` and `T = (b − c) / sqrt(b + c)`, McNemar's statistic, which is the
special case the paper's abstract announces (as summarised in the search result of its Wiley page).

- **The decision reads the statistic, not the root.** N passes iff `T(−δ) > z`, with `δ` the exact
  `Fraction(55, 2800)` and `z = norm.ppf(1 − α)`. The lower limit `L` of the two-sided 90% interval is
  also computed (bracketed root finding with `scipy.optimize.brentq`) and recorded, and the decision
  stage **refuses to write** if `(L > −δ) != (T(−δ) > z)`: a disagreement would mean the monotonicity the
  equivalence rests on failed numerically, which is a deviation, not a tie to break.
- Undefined arithmetic (a negative discriminant or denominator) raises; nothing is clipped.
- Descriptive readings use the same functions: the one-sided 97.5% bound (`z = norm.ppf(0.975)`), the
  90% interval of B − A with its position against zero, and the M1 interval for A − dense.
- **Validation** (T10, T11): the McNemar special case; `L ≤ Δ̂ ≤ U`; swapping `b` and `c` negates the
  interval; limits in `[−1, 1]`; defined at `b = c = 0`; agreement with an independent bisection over
  the same statistic on a grid of counts (written from the formula, not copied from `PropCIs`); and
  **the published worked example**, a declared gap (see "Declared gaps"). `replace-test` refuses while the fixture slot
  `PUBLISHED_EXAMPLE` in `tango.py` is empty, so the gap cannot be skipped by accident.
- *Implementation note (T10, 2026-09-17):* T10's first action, checking the formula against the paper's
  own equation and recording its number, could not be done: the paper was not available to the
  implementing session, and no equation number is written from memory. The docstring of `tango.py`
  declares the formula "not verified against the paper". What was checked instead, from first principles:
  `q` is the restricted maximum-likelihood estimate of `p_c` under `p_b - p_c = D0` (the likelihood's
  score equation reduces to `2n q^2 + pb q + pc = 0`, and a test checks `q` against a bounded numerical
  maximization of that likelihood), `n (2q + D0 (1 - D0))` is the variance of `b - c` under it, and an
  independent bisection over the likelihood reproduces the lower limit. The check against the paper's
  equation moves to T11, with the worked example. `PUBLISHED_EXAMPLE` is a read-only empty mapping, and
  `require_published_example()` is the refusal `replace-test` calls.

### D17 - Diagnostics and traces come from the lists the run itself produced

Recording wrappers — `RecordingRetriever` around `dense` and `bm25`, `RecordingStage` around the entity
stage, and a recorder around the hybrid — keep the component lists and the fused list per call, in call
order, which is the harness's question order. Each exposes the inner `name` and delegates unchanged.
They are used for the selected-configuration runs on dev and on test, never inside a fit. From the
recorded lists and `token_counts`:

- **Diagnostics** (per question, per split, aggregated): `p1`, entity nodes of `p1`, whether `p1` is one
  of the 8 failed extractions (from the verified extraction records), `P(q)`, `|E(q)|`, `|E(q)| == 100`,
  empty, single candidate, abstained under the selected scheme (`weighted` only; `null` under RRF),
  bottom-tier size, overlap of `E(q)` with ranks 11-100 of `D(q)`, units of B's context @2,048 outside
  `D(q)`, and the same for A's context.
- **Traces**: for every unit in B's context @2,048 not in dense's context @2,048 (dense's context is

  `RankedCandidate.nodes`, heaviest first.
- **No second retrieval on test.** Recomputing B's rankings to explain them would be a second read of
  test; the wrappers make it unnecessary. What producing them changes is tested on dev: the same run
  with and without wrappers gives identical outcomes.
- The context each diagnostic re-derives from the recorded fused list must equal the recorded outcome's
  context at 2,048, or the stage stops.
- **Run digest**: `RunResult` has no digest field. The run digest is `digest_of_payload(asdict(result))`

  the file. Diagnostics and traces carry it with the freeze digest, the node-index and extraction
  digests, and their own digest. Every trace node must resolve in the index with type `entity`, and
  its weights must sum to `score` within the tolerance of OI-2.
- *Implementation notes (T14, 2026-09-17):* `RecordingHybrid(dense, second, scheme, weights)` builds
  the unchanged `FusedRetriever` over `RecordingRetriever` and `RecordingStage` components; the stage
  wrapper records the `EntityExpansion` behind every list it proposes. Diagnostics and traces are built
  together from the recordings of B's and A's selected runs, which must have seen the same `D(q)`, and

  checked against the recorded outcome at 2,048 by its units included, gold recall, Full Support and
  precision, recomputed from the gold in `evaluation/`. The bottom tier is the number of candidates at
  the lowest score present (0 for an empty list), reported under either scheme; `abstained` is `null`
  under RRF. The loader also refuses a trace node whose form differs from the index's, and, when handed
  the weights, a node weight other than the index's.

### D20 - Deterministic ids and the secrets gate: a content filter, not a path exclusion

*Revised on 2026-09-17 on the author's instruction: no blanket exclusion of `data/replacement/*.json`.*

**What raises the false positives, measured.** The scanner, run with its default settings and no
exclusion over Phase 5's id artifacts (`pilot.json`, `hop-run.json`, `traces.json`,
`gate-decision.json`), reports 1,906 findings (1,385 in `pilot.json`, the figure the security README
already records). **Every one is `HexHighEntropyString`, and every one is a lowercase hex string of
exactly 16, 24, 40 or 64 characters, standing alone as a JSON value**:

| Length | What it is | Where it appears |
|---|---|---|
| 24 | HotpotQA question ids | `qid` |
| 16 | unit ids and short keys | `p1`, bare list elements, `unit_set_hash`, `prompt_digest`, `reference_dictionary_key` |
| 40 | the resolved embedding-model commit | `revision` |
| 64 | sha256 digests | `digest`, `hop_run_digest`, `pilot_digest`, `extraction_digest`, `node_index_digest` |

`unit_id` lines raise nothing: the scanner's own `is_likely_id_string` heuristic already skips them.
Phase 6's outcomes, diagnostics, traces, readouts, freeze and decision carry the same shapes over 600 dev
and 1,400 test questions, so they would raise thousands of findings.

**Why not a path exclusion.** Every Phase 6 file mixes those ids with content the scanner must keep
reading: entity forms that came out of an LLM extraction (traces), verbatim texts and file names
(freeze, decision), configuration (run results). A path exclusion would stop scanning all of it. Phase
5's exclusion stays exactly as it is: its two directories were judged pipeline-written ids, figures and
configuration, and it was audited as such. It is not extended, and no Phase 6 file is added to it.

**The filter.** `.github/detect_secrets_filters.py::is_deterministic_replacement_id(filename, line,
secret, plugin)`, standard library only, is registered in `.secrets.baseline` `filters_used` as
`file://.github/detect_secrets_filters.py::is_deterministic_replacement_id`. The CI hook configures its
filters from the baseline, so the gate applies it. The scanner calls it once per finding, and it skips
that finding **if and only if all four hold**:

1. **Path.** `filename`, with `\` normalized to `/`, fully matches `^data/replacement/[^/]+[.]json$`:
   directly inside the directory, `.json` only.
2. **Detector.** `plugin` is `HexHighEntropyString`. A finding of any other detector is never skipped:
   keywords, private keys, AWS, JWT, Base64 entropy, and the rest.
3. **Line shape.** The whole line, trailing whitespace stripped, is exactly one of:
   - `"<key>": "<hex>"` with an optional trailing comma, where `<key>` is on an explicit allowlist and
     `<hex>` has one of the lengths allowed for that key. No suffix or wildcard keys.
   - a bare list element `"<hex>"`, optional comma, of length **16 or 24 only**, the unit-id and qid
     lists.

   `<hex>` is `[0-9a-f]` only.
4. **Value.** `secret` equals that `<hex>`.

The allowlist lives in the module as a literal mapping from key to lengths. It takes the keys of the
table above that a Phase 6 artifact also carries, plus the key names of the spec's data contracts with
the same shapes: `qid` {24}; `p1` {16}; `unit_set_hash`,
`prompt_digest` {16}; `revision` {40}; `digest`, `freeze_digest`, `node_index_digest`,
`extraction_digest`, `pilot_digest`, `hop_run_digest`, `traces_digest`, `run_digest`, `sha256` {64}.
T20 depends only on T1, so it cannot see the writers. The list is reconciled with the real artifacts
instead:
- a data-dependent test, skipped while `data/replacement/` is empty, requires every allowlisted key to
  occur there, so after T21-T23 a key no writer emits fails and is removed;
- a key the hook flags when T21, T22 or T23 artifacts are staged is added only by a reviewed change to
  this module and its test, committed on its own before the artifacts, and never by regenerating the
  baseline.

**What stays scanned inside `data/replacement/`**:
- every finding of every other detector;
- hex values of any other length, or containing uppercase letters;
- a hex value under a key that is not on the list;
- any line holding more than that one key and value, so a string appended to the line, a text, an
  entity form or a file name is always read;
- bare 40- or 64-character hex elements;
- nested files and non-JSON files.

Outside `data/replacement/` nothing changes.

**How it fails.** The installed detect-secrets 1.5.0 loads a file filter when it scans. If the file or
the function is missing, it logs a warning and applies no filter (`settings.get_filters`). A broken
filter therefore brings the findings back and fails the gate; it cannot silence anything. The opposite
risk, the module edited to skip too much, is what the T20 test guards, and a change to this module is
reviewed the way a baseline change is. Regenerating the baseline must pass `--filter` again, exactly as
Phase 5's pattern must be passed again; the README records both.

**Test** (`tests/test_security_gate.py`, T20):
- **Function level, skipped:** each allowlisted key at each allowed length; bare 16 and 24; either path
  separator.
- **Function level, reported:**
  - the same lines under `data/replacement/nested/`, in a `.py` file, under `xdata/`, and in `src/`;
  - a key off the list, a wrong length, uppercase hex;
  - extra content on the line;
  - a bare 64-character element;
  - a finding of another detector on an allowed line;
  - a `secret` that differs from the line's value.
- **End to end:** skipped when the `security` group is not installed. The real scanner is configured
  from the real `.secrets.baseline` and run from the root of a temporary tree laid out like the
  repository, with each case planted in its own file. Exactly the expected findings come back.
- **Structural:**
  - `filters_used` holds this one custom filter, and Phase 5's `should_exclude_file` pattern unchanged;
  - `test_the_path_exclusion_covers_only_the_phase_5_id_artifacts` adds `data/replacement/x.json` to the
    paths its pattern must still scan;
  - the module imports only the standard library.

**Recorded** in `docs/security/README.md`, in a subsection beside Phase 5's: the measurement above, why
no path exclusion, the four conditions, the allowlist, what stays scanned, how it fails, and how to
regenerate. `.gitignore` versions `data/replacement/*.json`. The hook is run over the tracked tree
before committing T20, and again before committing the artifacts of T21, T22 and T23, which are the
first real files the filter meets.

### D21 - Verbatim texts and the ASCII rule [confirm]

Two open-question texts contain `δ`, and `CLAUDE.md` forbids non-ASCII in Python strings. The house

Deviation paths are resolved against the project root when relative.

## Risks

- **R1 — The control does not reproduce on dev.** A library change since 2026-09-11 (numpy, scipy,
  `bm25s`) or a cache change would move a float. The spec's `re-measured` branch handles it; the
  library versions in D22 are what a deviation would need to find the cause.
- **R2 — Continuity (a) fails on a float tie.** Phase 5 broke ties by pool row, Phase 6 by unit id; the
  spec expects no exact tie and makes the stop mandatory. Nothing is switched silently.
- **R3 — The tokenizer recount needs the pinned tokenizer offline.** If it is missing from the local
  cache, `TokenCounter` may try the network; the stage then stops and says so rather than skipping.
- **R4 — Cost of the entity stage.** `node_hop` builds the entity column set by iterating over 137,262
  nodes on each call; memoization bounds that to one call per distinct read list (600 on dev, 1,400 on
  test), but the per-call cost is unmeasured.
- **R5 — An inconclusive replacement is a plausible outcome**, as the spec's precision section states;
  it is a successful end of the phase, not a reason to re-test.
- **R6 — Artifact size.** Six outcome files and four per-question descriptive files are versioned; their
  size is measured when written, and anything unreasonable is raised before committing.
