# Phase 9 — RunPod operating recipe

> Operational runbook for the **measurement-host part of Phase 9** (plan steps S5 and S6).
> S1-S4 are committed and pushed and the S5/S6 code passed a local smoke build over 300 units.
> Renting starts only after the author approves the envelope (stop point 1). The single
> evaluation pass (`fullwiki-eval`) is a **second, separate authorization** (stop point 2):
> nothing before section 9 computes a metric over any Phase 9 cohort.
>
> Files move through the pod's **Jupyter** file browser (upload and download); every command
> below runs in the pod's terminal.

---

## 1. Envelope

| Item | Value |
|---|---|
| Host | 1x NVIDIA RTX 4090, Linux x86_64, Secure Cloud, PyTorch template |
| Listed allocation | 41 GB RAM, 6 vCPU per GPU (RunPod pricing page, 2026-09-23); **stop if the pod shows less than 40 GB** |
| Hourly rate | listed 0.74 USD/h (2026-09-23); the contracted rate is copied at rental |
| Disk | a **volume of 100 GB** mounted at `/workspace` (it survives a pod stop; container disk does not) |
| Hard ceiling | **25 USD** total session billing (spec D11) |
| Query ceiling | mean <= 1.0 s per question per system (probe, then pass) |

Guard: at 0.74 USD/h the ceiling is 33.8 h of pod time. If the session reaches 80 % of the ceiling
(20 USD), stop the pod and ask the author before starting another step.

Expected duration (**linear projections, not measurements**): GLiNER 5,233,329 units at Phase 7's
measured 162.18 units/s = 8.96 h; BGE at 8.1's measured 2,136 units/s = 0.68 h; setup, corpus
rebuild, tokens, BM25, index, probe and downloads about 2.5 h; build session about 12 h (9 USD).
Evaluation pass: 7,405 questions x 3 systems at ~0.72 s (8.1's 0.069 s at 500k, scaled by 10.5)
is about 4.5-5 h (3.5 USD). Total about 17 h, 12-13 USD.

The build steps run **one after another**, never two at once, so each step's wall time and
throughput - GLiNER's above all, which is compared against Phase 7's projection - is measured
on an otherwise idle pod.

## 3. Pod setup (terminal)

Everything `uv` needs lives on the volume - its binary, its cache, the Python 3.12 it installs
and the Hugging Face cache - because a stopped pod loses its container disk, and the pass in
section 9 may run after a restart.

```bash
cat > /workspace/env.sh <<'ENV'
export UV_INSTALL_DIR=/workspace/.uv/bin
export UV_CACHE_DIR=/workspace/.uv/cache
export UV_PYTHON_INSTALL_DIR=/workspace/.uv/python
export HF_HOME=/workspace/.hf
export PATH=/workspace/.uv/bin:$PATH
ENV
source /workspace/env.sh

cd /workspace
git clone https://github.com/mikelju/concept-embeddings-RAG.git
cd concept-embeddings-RAG
git checkout <CHECKPOINT_SHA>
git rev-parse HEAD && git status --short

curl -LsSf https://astral.sh/uv/install.sh | sh
uv sync --group phase7

uv run --group phase7 python -c "import torch; x = torch.ones(1024, 1024, device='cuda'); print(torch.__version__, torch.cuda.get_device_name(0), float((x @ x).sum()))"
free -g; nproc; df -h /workspace
mkdir -p data/phase9/logs data/phase8_1/source
```

`free -g` must show at least 40 GB total. Record vCPU and RAM: the manifests' `hardware` block
reports the host, not the allocation.

**Upload** the three files of section 2 through Jupyter into the paths shown.

## 6. Build (S5): one process per step, one step at a time

```bash
uv run --group phase7 cer fullwiki-build --stage embed --hourly-rate-usd <RATE> 2>&1 | tee data/phase9/logs/embed.log
uv run --group phase7 cer fullwiki-build --stage tokens 2>&1 | tee data/phase9/logs/tokens.log
uv run --group phase7 cer fullwiki-build --stage bm25 2>&1 | tee data/phase9/logs/bm25.log
nohup uv run --group phase7 cer fullwiki-build --stage extract --hourly-rate-usd <RATE> > data/phase9/logs/extract.log 2>&1 &
tail -n 2 data/phase9/logs/extract.log          # repeat until "[OK] build extract" (~9 h)
uv run --group phase7 cer fullwiki-build --stage index 2>&1 | tee data/phase9/logs/index.log
```

- `extract` runs under `nohup`, so closing the browser does not stop it. It is resumable: if it
  dies, rerun the same `nohup` line. Finished shards are never re-extracted; a restarted shard is
  counted in `extraction.json`.
- `embed` refuses to run twice. If it dies after writing the vector cache but before
  `embedding.json`: **STOP** and ask.

## 9. The single evaluation pass (only after the author's explicit authorization)

The build ran at checkpoint `9abdc26`. Three CLI defects found by code review afterwards
(outcome on a stop, the pass marker's timing, the probe's second load) are fixed at `b7a28f1`;
the pass runs at that commit. The fixes touch only `cli.py` stages downstream of the build, so
no build artifact changes. If the overnight probe did not finish (for example the old
column-wise path ran out of memory), it is rerun at `b7a28f1` first; if it finished, whether
its `probe.json` (recorded at `9abdc26`) stands is the author's decision.

```bash
source /workspace/env.sh
cd /workspace/concept-embeddings-RAG
git fetch origin && git checkout b7a28f10391ee35eed66655613b489b3bd92154e && git status --short
cat data/phase9/logs/overnight.status; ls data/phase9/probe.json
# only if probe.json is missing:
uv run --group phase7 cer fullwiki-probe 2>&1 | tee data/phase9/logs/probe-b7a28f1.log
nohup uv run --group phase7 cer fullwiki-eval --authorized-pass > data/phase9/logs/eval.log 2>&1 &
tail -n 2 data/phase9/logs/eval.log              # repeat until the third "run written"
cd data/phase9 && tar czf /workspace/phase9-pass.tgz pass.json run-*.json outcomes-*.jsonl.gz logs/eval.log && sha256sum /workspace/phase9-pass.tgz
```

It refuses without `--authorized-pass` and refuses a second start whatever the first showed
(`pass.json`). Download `/workspace/phase9-pass.tgz`, terminate the pod, and copy the RunPod
session total as invoiced. `fullwiki-outcome` and `9.results.md` run on the laptop.

Memory, for the 41 GB allocation. Measured on the laptop (Windows peak working set): the whole
corpus loaded as units, 3.7 GiB; BM25 over its first 500,000 units, +0.6 GiB in 23 s. Linear
projection (not a measurement): BM25 over 5.2M units ~6.5 GiB and ~4 min. The vectors are 7.5
GiB of float32; `embed` encodes in blocks into one preallocated array and the vector digest is
read in place. Each step records its own `VmHWM`, so the figure reported is measured.
