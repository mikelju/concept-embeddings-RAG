# Phase 9: HotpotQA FullWiki — implementation plan

> Functional spec: [`9.spec.md`](9.spec.md), **approved 2026-09-23 and frozen**. This plan decides
> HOW; it reopens nothing the spec settled. A change to any spec rule is a written deviation
> `9.Y_*.md`, never a judgement call at the keyboard.
>
> Simplification rule: one question, **seven steps**, no `9.tasks.md`, reuse before generalization.

## Objective

> Does the simple Dense + Entity Hop architecture remain useful when retrieval is performed over the
> standard multi-million-paragraph HotpotQA FullWiki search space?

Primary endpoint: Full Support @2,048 tokens, P9-C (Dense + Entity Hop, 0.7/0.3) against P9-A
(Dense), on the 5,405 `retrieval-unseen` questions, one two-sided exact McNemar test, α = 0.05.
Terminal states: `SCALE_SUPPORTED`, `SCALE_NOT_SUPPORTED`, `SCALE_REGRESSION`, `DATA_STOP`,
`OPERATIONAL_STOP`.

## Author stop points

The plan runs end to end **except** at these three points, where it stops and asks:

1. **Before renting the GPU** (end of S5): the envelope below, the exact hourly rate and the
   download checklist are presented for approval. No money is spent before it.
2. **Before the single evaluation pass** (S6): the pass computes metrics over the 7,405 questions,
   including the 1,400 historical test and the 5,405 new held-out questions. It is run once, after
   every index is frozen, only on explicit authorization.
3. Any spec stop (`DATA_STOP`, `OPERATIONAL_STOP`), a reproduction check that misses its recorded
   figure, or two attempts without progress.

## Frozen envelope (from spec D11)

| Item | Value |
|---|---|
| Host | one RunPod NVIDIA RTX 4090, Linux x86_64, >= 64 GB RAM, ~150 GB volume |
| Hourly rate | recorded at rental (8.1 paid 0.74 USD/h for this class) |
| Hard ceiling | **25 USD** total session billing |
| Query ceiling | mean <= 1.0 s per question per system |
| Expectation (unmeasured) | GLiNER ~8.6 h (Phase 7 projection), BGE ~0.7 h (from 8.1's 2,136 p/s), corpus+BM25+index+tokens ~1-2 h, probe+pass ~1 h: **~12-14 h, ~9-11 USD** |

Between the build (S5) and the authorized pass (S6) the pod is **stopped with its volume kept**,
not running, so the wait costs only volume storage.

## Implementation steps

- [x] **S1 — SEC-033 and frozen constants.** `probe_layout` enforces the canonical per-line ceiling
      before `json.loads`. Add the Phase 9 constants to `config.py`: cohort sizes, the 74-question
      ceiling, query ceiling, budgets and ks, top-100 depth, the envelope ceiling, `PHASE_9_DIR`,
      and the paths of the Phase 3 and Phase 7 fits the weights are read from.
      → `corpus/fullwiki.py`, `config.py` — test: `tests/corpus/test_fullwiki.py` (oversized probe
      line refused), `tests/test_config.py`.

- [x] **S2 — `cer fullwiki-corpus` (laptop).** Verify the archive against D1, stream every record
      through the existing `iter_records` → `unit_of`, write `data/phase9/corpus.jsonl.gz` in archive
      order and `corpus.json` (Phase9CorpusManifest). No selection, no prefix.
      → `corpus/fullwiki.py` (a `write_corpus` helper), `cli.py` — test: small synthetic archive →
      exact units, digests stable under re-run, refusal on identity mismatch.

- [x] **S3 — `cer fullwiki-questions` (laptop).** Build the three cohorts from `hotpot_raw.json` and
      the Phase 1 manifest by qid; resolve gold titles under D4 (exact, then unique
      `normalized_title`); unresolved titles become a sentinel gold id no corpus unit can carry, so
      the question stays in the denominator and can never reach Full Support; write
      `questions.json` (Phase9QuestionManifest + per-question gold) or `DATA_STOP`.
      → new `evaluation/fullwiki.py`, `cli.py` — test: `tests/evaluation/test_fullwiki.py`
      (cohort arithmetic, exact vs normalized vs ambiguous, sentinel never matches, ceiling 74 → stop).

- [x] **S4 — C19 wiring reproduction (laptop, no money).** The Phase 9 system builders (`P9-A`,
      `P9-B`, `P9-C`, weights read from the recorded fits and asserted equal to 0.5/0.5 and 0.7/0.3)
      are run over the historical 19,366 pool, the Phase 7 GLiNER index and the 600 historical dev
      questions, and must reproduce the recorded Phase 7 dev Full Support @2,048 counts exactly.
      Miss → stop and ask. This touches only questions already used for dev.
      → `evaluation/fullwiki.py`, `cli.py` (`cer fullwiki-repro`) — test: builder weights and
      provenance; the reproduction itself is the evidence.

- [ ] **S5 — `cer fullwiki-build` (rented GPU, after stop point 1).** On the host: download and
      verify the archive, rebuild the corpus and require the S2 digests; token counts in batches;
      BGE embeddings (own cache under `data/phase9/cache/`, never the historical one — the
      `question_cache_key` gotcha); BM25 over `indexable_text`; GLiNER extraction in resumable
      shards (a finished shard is never re-extracted, so each unit is attempted once) with the
      weight-file SHA-256; the node index and its DF/hub statistics. One manifest per artifact.
      Smoke-tested locally first on a few hundred units (GLiNER on CPU).
      → `nodes/local_extraction.py` (shards, weight digest), `evaluation/fullwiki.py`, `cli.py`,
      `docs/plans/phase_9/9.runpod_recipe.md` — test: shard resume attempts each unit once;
      weight digest recorded; manifests cover the same unit set.

- [ ] **S6 — `cer fullwiki-probe` then `cer fullwiki-eval` (host).** The probe times P9-A/B/C over
      a fixed seeded sample of 100 historical dev questions (rankings only) and records peak
      RAM/VRAM → `OPERATIONAL_STOP` or go. If P9-C's time is near the ceiling, an exact faster hop
      (column-wise accumulation over the shared nodes) may replace the full-matrix product only
      after a test proves identical candidates and scores on the C19 index. Then **stop point 2**.
      With authorization, `fullwiki-eval` runs the single pass and writes one `run-<system>.json`
      per system plus per-question outcomes; it refuses if a run already exists.
      → `evaluation/fullwiki.py`, `retrieval/entity_hop.py` or `evaluation/second_hop.py` only if
      needed, `cli.py` — test: refusal to rerun; cohort split of metrics; (if built) exact-hop
      equivalence.

- [ ] **S7 — `cer fullwiki-outcome` (laptop), results, audit, delivery.** Exact McNemar on the
      primary cohort, terminal label written by code; `9.results.md` with the economics table and
      the verified literature ledger; master plan and `CLAUDE.md` state updated; targeted
      `/8-auditar` (untrusted archive parsing, model downloads/weights loading); `deliver`.
      → `evaluation/fullwiki.py`, `cli.py`, docs — test: label rules on constructed counts.

## Technical notes

- **Artifacts** live in `data/phase9/`, git-ignored like `data/phase8_1/`; figures and digests are
  recorded in `9.results.md`.
- **Reuse:** `iter_records`/`unit_of`, `normalized_title`, `DenseRetriever`, `BM25Retriever`
  (`bm25s`, no new dependency), `build_node_index`, `node_weights`, `EntityHopStage`,
  `FusedRetriever`, `evaluate_retriever` with `outcomes=` for the paired test, `TokenCounter`
  (batched).
- **No new dependencies.**
- **Dense at 5.2M × 384 float32** is ~8 GB; exact brute-force search is kept (8.1 measured
  0.069 s/query at C500).
- The corpus is rebuilt on the host from the downloaded archive and must match the S2 digests,
  rather than uploading ~2 GB from the laptop.
