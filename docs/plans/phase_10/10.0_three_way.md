# Phase 10: Dense + BM25 + Entity Hop at FullWiki scale — implementation plan

> Functional spec: [`10.spec.md`](10.spec.md), **approved 2026-09-24 and frozen**. This plan decides
> HOW; a change to any spec rule is a written deviation `10.Y_*.md`.
>
> Simplification rule: one question, **seven steps**, no `10.tasks.md`, reuse before
> generalization. Everything runs on the laptop; no money is spent.

## Objective

> Does adding the frozen Phase 9 Entity Hop as a third fused component make Dense + BM25 retrieve
> the full multi-hop evidence more often at FullWiki scale?

Primary endpoint: Full Support @2,048 on `test-10` (5,000 HotpotQA train "hard" questions), P10-C
against frozen P10-B, one two-sided exact McNemar test, α = 0.05. Terminal states:
`THREE_WAY_SUPPORTED`, `THREE_WAY_NOT_SUPPORTED`, `THREE_WAY_REGRESSION`, `DATA_STOP`, `DEV_STOP`.

## Author stop points

1. **Before the held-out pass (S6).** It opens `test-10`. It runs once, after the fit is committed,
   and only on explicit authorization.
2. Any spec stop (`DATA_STOP`, `DEV_STOP`), a D4 reproduction miss, or two attempts without
   progress.

## Implementation steps

- [x] **S1 — `cer p10-questions` (laptop).**
  - Add the Phase 10 constants to `config.py`: train URL, seed 10, set sizes, the 1 % ceiling,
    the 5.0-point probe margin, the grid step, the dev reference counts and `PHASE_10_DIR`.
  - Download the HotpotQA train release once, stream-verified and pinned in the manifest.
  - Verify that every validation question is level `hard`.
  - Draw the three sets in one `random.Random(10).sample` over the sorted hard qids, sliced in the
    order probe, test-10, test-11.
  - Map gold with the Phase 9 D4 function against the Phase 9 corpus, and write
    `data/phase10/questions.json`, or `DATA_STOP`.
  - → `evaluation/phase10.py` (new), `config.py`, `cli.py`.
  - Test: `tests/evaluation/test_phase10.py`: the draw is deterministic and disjoint, validation
    overlap is refused, the ceiling triggers the stop, and a short release triggers the stop.

- [x] **S2 — `cer p10-embed` (laptop CPU).**
  - Encode the three sets with the pinned BGE backend into `data/phase10/cache/questions/`, under
    a key that includes the set name. The question texts are not a secret, but they are only ever
    loaded by the step that is allowed to use them.
  - → `evaluation/phase10.py`, `cli.py`.
  - Test: the key differs per set and from Phase 9's; the revision is recorded.

- [x] **S3 — Three-component fusion.**
  - A `TripleFusedRetriever`, with dense first, BM25 second and the Entity Hop stage third in
    fixed order. It asks Dense once, BM25 the query, and the stage Dense's list, each at
    `top_k = 100`. It fuses with the existing `fuse(..., scheme="weighted")`, which already takes N
    min-max normalized components, and records `describe()` like `FusedRetriever`.
  - `FusedRetriever` is not modified.
  - A `fuse_lists` helper applies the same call to precomputed component lists, so the dev grid
    can reuse one retrieval per question.
  - → `retrieval/fusion.py`.
  - Test: `tests/retrieval/test_triple_fusion.py`: the retriever equals `fuse` over the three
    lists; weights are convex and named; the order is fixed; with `w_entity = 0` the entity list
    still enters the union exactly as `fuse` defines it; and `fuse_lists` equals `retrieve` on
    fixtures.

- [x] **S4 — `cer p10-repro` and `cer p10-probe` (laptop).**
  - Load and verify every Phase 9 artifact through the existing `_phase_9_inputs`: corpus, BM25
    rebuilt to its digest, vectors, entity index and token counts.
  - For each of the 7,405 dev questions, keep the three component lists (Dense, BM25, Entity Hop
    over Dense's list), each at depth 100, in `data/phase10/dev-lists.jsonl.gz` with a digest.
  - Rebuild the P9-A, P9-B and P9-C rankings: Dense directly, and the two hybrids through the
    same `fuse` call `FusedRetriever` makes. Score them with the Phase 9 harness and check the
    three counts exactly. Write `reproduction.json`; a miss stops the phase.
  - `p10-probe` then runs Dense alone on `probe` and writes `probe.json` with the D3 verdict.
  - → `evaluation/phase10.py`, `cli.py`.
  - Test: `FusedRetriever.retrieve` equals `fuse` over the component lists, for P9-B and P9-C on
    fixtures; the probe verdict at the margin, just above and just below it.

- [x] **S5 — `cer p10-fit` (laptop, dev only).**
  - The 66 convex weight triples, step 0.1. Each is scored on the cached dev lists: Full Support
    @2,048, then gold recall @2,048, then the tie rule.
  - Apply the dev gate: `w_entity = 0`, or no gain of at least one question over 4,536 →
    `DEV_STOP`.
  - Write `fit.json` and **commit it** before S6.
  - → `evaluation/phase10.py`, `cli.py`.
  - Test: the grid has 66 points; the tie rule; both gate branches; a refit refuses to overwrite.

- [ ] **S6 — `cer p10-eval --authorized-pass` (laptop, after stop point 1).**
  - Refuse without the flag, without `fit.json`, on a gate stop, or when `pass.json` exists.
  - Mark `pass.json` after the inputs load, then measure P10-A, P10-B (`FusedRetriever`, 0.5 / 0.5)
    and P10-C (`TripleFusedRetriever`, fitted weights) on `test-10`, one system after another, with
    the Phase 9 `measure_system`.
  - Write `run-<system>.json` and outcomes with latency and host.
  - → `evaluation/phase10.py`, `cli.py`.
  - Test: `tests/test_cli_phase10.py`: the refusals; the pass marker's timing; `test-11` is never
    loaded.

- [ ] **S7 — `cer p10-outcome`, results, delivery.**
  - Compute the exact McNemar of P10-C against P10-B with the Phase 9 function, write the label and
    the latency ratio, and write `outcome.json`.
  - Write `10.results.md`, update the master plan and `CLAUDE.md`, then run the checks and
    `deliver`.
  - → `evaluation/phase10.py`, `cli.py`, docs.
  - Test: the label rules on constructed counts.

## Technical notes

- **Reuse.**
  - `_phase_9_inputs` for loading and verifying every artifact, including SEC-034.
  - `phase9` D4 gold mapping, `measure_system`, the run contract, `primary_outcome` (exact
    McNemar) and `ColumnwiseEntityHopStage`.
  - The existing `fuse`.
- **Memory.** Phase 9's pass peaked at 19.9 GB on Linux; the laptop has 31.6 GB. The dev
  diagnostic (exploratory, running now) and the Phase 10 stages never run at the same time.
- **Time (projection, not measurement).**
  - Dense measured 0.031 s per query over 1M vectors, so about 0.16 s at 5.2M.
  - S4 is one retrieval per component per dev question, about 1-2 h.
  - S5 re-fuses cached lists, minutes.
  - S6 is 3 systems × 5,000 questions, about 1-2 h.
- **Cross-machine risk for D4.** Dense scores are float32 dot products, and the laptop's ARM BLAS
  may sum in another order than the pod's x86 one. A near-tie at a rank boundary could flip and
  change a count by a question. The gate is exact by the spec: a miss stops and is reported with
  the differing questions. It is not tolerated or explained away.
- **No new dependencies.** The train release is fetched with the standard library, like the
  Phase 1 `fetch`.

## Corrections

Implementation corrections found while executing; none changes a spec rule.

1. **Train source (S1).** The authors' CMU host no longer answers, as deviation 1.1 found for
   Phase 1. The train release is assembled from the canonical HuggingFace dataset
   (`hotpotqa/hotpot_qa`, config `distractor`, split `train`) through the Phase 1 rows path. The
   split is now a parameter, and validation stays the default. The pin records the endpoint, the
   row count, the fields kept, the bytes and the SHA-256 of the frozen file. Only the fields
   the draw and the gold mapping read are kept: the distractor contexts are not used by any step.
2. **Question vectors (S2).** Only `probe` and `test-10` are encoded. `test-11` is left for the
   next phase to encode when it is allowed to use it, so that Phase 10 never touches it beyond
   the draw and the gold mapping.
