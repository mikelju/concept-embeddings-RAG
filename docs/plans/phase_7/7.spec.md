# Spec Phase 7: Cheap Entity Extraction

> Functional specification — WHAT is measured and HOW it is decided, not how it is implemented.
> This phase is the first to run under the **simplification rule** (`CLAUDE.md`, master plan §46):
> one question, roughly 5–8 implementation steps, no `7.tasks.md`, no Phase 6 protocol machinery.
> **Approved.** Every decision this document once left open is settled below and listed in
> §"Decisions settled before implementation". Nothing here is a proposal any more.

---

## Problem and objective

**Problem.** Phase 6 established `ENTITY_REPLACEMENT_SUPPORTED`: a one-hop, query-blind Entity Hop
replaces the BM25 component of the dense hybrid and improves on Dense alone (test Full Support @2,048:
Dense `0.8250`, Dense + BM25 `0.8643`, Dense + Entity Hop `0.8900`). That result rests on an entity
representation read out of every paragraph by `claude-sonnet-5`, at a measured cost of
**25.9848 USD for 19,366 paragraphs**. HotpotQA FullWiki is on the order of five million paragraphs;
the same extraction, projected linearly at the measured per-paragraph rate, is approximately
**6,700 USD** — a projection, not a measurement. Online traversal is not the bottleneck
(10.447 ms/query, measured); **offline extraction is**.

**Objective.** Answer one question:

> **Can the expensive Claude-based entity extraction be replaced by a cheap or local extractor
> without materially losing the Entity Hop retrieval gain?**

Success is a written answer to three things: how much of the gain each candidate extractor keeps on
dev, what each candidate costs in time/money/hardware projected to ~5M paragraphs, and which
extractor Phases 8 and 9 inherit — plus one held-out test figure for the selected extractor. A
negative answer ("none of the cheap candidates keeps enough") is an acceptable and publishable
outcome of this phase.

## Candidate extractor families

Deliberately few. This is not an NER benchmark; adding a fourth model family is scope creep.

### A. Claude extraction — the reference

`claude-sonnet-5`, the frozen Phase 5 prompt (`prompt_digest 0107de3ae9b4e4a3`), used **as an existing
artifact**. Not re-run. Not re-priced. It defines what "keeping the gain" means.

### B. Local zero-shot / open NER — GLiNER or equivalent

Runs locally, no generative decoding, configurable entity classes. The primary cheap candidate.

### C. Conventional local NER — spaCy or equivalent lightweight pipeline

Mature, fast, potentially CPU-only, narrower ontology. The conservative cheap candidate.

### D. Wikipedia-native links / anchors — **DISCARDED, with evidence**

The roadmap admits this family "only if the dataset actually exposes enough information". It does not.
Checked directly against the frozen data rather than assumed:

- `data/hotpot_raw.json` (7,405 records) has exactly these top-level keys: `_id`, `answer`, `context`,
  `level`, `question`, `supporting_facts`, `type`. There is no link, anchor or entity layer.
- A context entry is `[title, [sentence, …]]` — plain text only.
- Scanning all **306,487** raw sentences: `0` occurrences of `wikipedia.org/wiki`, 19 sentences
  containing `href=`, 28 containing `[[`.
- In the 19,366-paragraph pool, **4 paragraphs** contain any `<a …>` fragment at all: 13 `href`
  anchors, 9 distinct targets (`Greek%20alphabet`, `sun%20god`, …). These are scraping artefacts
  inside the sentence text, not a link annotation.
- `data/pool.json` units carry only `unit_id`, `title`, `sentences`.

**Conclusion:** a Wikipedia hyperlink/anchor entity source is **not evaluable on the current corpus**.
It becomes available only with the FullWiki `with-links` distribution, which belongs to Phase 9. It is
therefore removed from Phase 7 and recorded as a Phase 9 opportunity.

**Settled: no title-mention arm.** The pool *does* expose one Wikipedia-native signal — the 19,366
article **titles** — and a deterministic "title mention" extractor (match other corpus titles inside a
paragraph's text) would be a zero-cost, zero-model candidate. It is **not** part of Phase 7: it is a
new mechanism rather than a cheap replacement for an existing one, and it cannot exist at FullWiki
scale in the same form, so measuring it here would answer a different question. Phase 7 has exactly
three arms: the Claude reference, B and C.

## What is measured

For every candidate that runs, both halves are recorded. No figure may be estimated and reported as
measured; a figure that does not exist is declared as a gap.

**Retrieval (dev for every candidate; test only for the selected one):**

- Full Support at all four budgets, headline at 2,048;
- Gold Recall at all four budgets;
- Recall@2 / @5 / @10;
- the fitted fusion scheme and weight, and the dev curve over the grid;
- mean query latency.

**Entity Hop behaviour:**

- positive candidates per question `P(q)`: mean, median, share of questions with zero;
- paragraphs with no entity node, and `p1`s with no entity node;
- number of units the hop introduces into the fused context that Dense did not supply
  (the Phase 6 recording wrappers already produce this; reuse them if it costs one call, otherwise
  declare it out of scope for a candidate that is not selected).

**Extraction cost and scale:**

- distinct entity nodes and entity incidences;
- extraction failures, by kind, and the failure rate;
- paragraphs per second (measured, not derived from a sample);
- total wall-clock extraction time;
- hardware actually used (CPU model / GPU model / RAM / OS / arch);
- model identity and revision, library versions;
- node index size on disk (bytes);
- monetary cost actually incurred (0.00 USD for a local run on owned hardware; the real invoice if a
  rented GPU is used);
- **projection to ~5,000,000 paragraphs**: wall-clock time and monetary cost, each labelled as a
  linear projection from the measured throughput, with its arithmetic shown.

## How dev selects the extractor, and what test reports

### The rule

1. Every candidate is measured **on dev only**: build its node index, fit the fusion scheme and weight
   with the inherited procedure and objective (gold recall @2,048, `FUSION_WEIGHT_GRID`, RRF measured
   on the same questions, Phase 3 tie-breaks), read dev Full Support @2,048.
2. Candidates are ranked by the selection rule below.
3. The winner is measured **once on test**, and that single run is the phase's held-out figure.
4. No candidate's test figure is ever read while candidates are being compared. No threshold, label
   set, fusion weight or extractor parameter may be changed after a test figure is seen.

### What "held out" means here, precisely

The 1,400 test questions are held out **with respect to the Phase 7 extractor selection**, and that is
the whole of the claim. They are **not** globally unseen by this project:

- Phase 6 already measured Dense, Dense + BM25 and Dense + Claude Entity Hop on exactly these 1,400
  questions, and those three figures are inherited and quoted, not re-measured;
- so the test split carries prior history, and a Phase 7 test number is not a first contact with it.

This changes nothing about the protocol. What it forbids remains exactly what it forbade: every
Phase 7 choice — which extractor, which label set, which fusion weight — is made on dev, and **only
the extractor selected on dev is ever run on test, once**. No Phase 7 candidate other than the winner
produces a test figure at all.

### Model identity is fixed before the first dev measurement

Each candidate's **exact model, exact revision/version and exact label set** are written into the
implementation plan and into `config.py` **before any dev figure exists**. Once a variant has been
measured on dev it is not swapped for another variant of the same family — a different GLiNER
checkpoint, a different spaCy pipeline, a different threshold — unless that variant is declared and
reported as a **separate candidate**, chosen on dev like any other. There is no silent upgrade.

### The selection rule

Deliberately transparent rather than statistical, as the simplification rule requires.

**Retention bar (primary).** A candidate is *materially equivalent* if it keeps at least **75%** of the
Claude Entity Hop's dev gain over Dense:

```text
claude dev gain  = 0.8783 - 0.8117 = 0.0666  (Full Support @2,048, dev)
bar              = 0.8117 + 0.75 * 0.0666 = 0.8617
```

A candidate passes when its Dense + Entity Hop dev Full Support @2,048 is **>= 0.8617**. In whole
questions that is **517 of 600**.

**Reference line (reported, not disqualifying).** Dense + BM25 scores `0.8633` on dev — **518 of 600**.
It is a qualification, not a floor: a candidate that passes the bar but lands below that line is
recorded with the note that a free lexical complement did at least as well on dev. That is a finding
about the extractor, never an automatic rejection.

> Noted as a fact and nothing more: the bar (517 questions) and the Dense + BM25 line (518 questions)
> are **one dev question apart**. The author is aware of the proximity and approves the pair as
> written — 75% is the operating bar, the BM25 line is a reported qualification. The closeness is not
> a third criterion and is not a reason to reopen either number.

**Economic bar (primary).** A candidate is *viable for FullWiki* when:

```text
no per-paragraph third-party API call
software / API extraction cost         = 0.00 USD      (local, open-weight, free to run)
projected FullWiki wall clock          <= 48 hours     on one machine the project can realistically obtain
Phase 7 experimental infrastructure    <= 30 USD       if rented compute is needed at all
```

The **projected FullWiki infrastructure cost** — GPU-hours or machine-hours at a real rate, for ~5M
paragraphs — is measured, shown with its arithmetic and reported for every candidate, but it is **not
yet a hard rejection threshold**. Phase 7 decides which extractor Phase 8 inherits; what a FullWiki
build is worth paying for is Phase 9's decision, taken with Phase 9's numbers.

**Choice.** Among candidates passing both bars, select the one with the lowest projected FullWiki
cost-and-time; ties break by higher dev Full Support @2,048; still-tied, by the smaller dependency and
operational footprint.

**If none passes.** The phase closes with a negative result: no cheap extractor tested preserves enough
of the gain, FullWiki is not scaled, and the next move is the roadmap's own branch (investigate
Wikipedia-native signals at FullWiki, or one further extraction approach). One paragraph in the
results document, no new decision machinery.

### Label sets

GLiNER needs an explicit label list and spaCy has a fixed ontology; that list is a real parameter.
Rule: each candidate declares its label set **once, before measuring**, derived from the categories the
frozen Phase 5 prompt already names (people, organizations, places, works, events). A second label set
is allowed only as a separately declared candidate, chosen on dev like any other, never as a retune
after seeing a result.

**Minimally new — the whole surface this phase should add:**

1. A **local extraction producer**: for each candidate, run it over the 19,366 paragraphs and emit

   instance because extraction may happen on another machine.

Nothing else. No new retriever, no new metric, no new fusion scheme, no freeze/guard/decision-table
machinery.

## Contracts

Kept to the two things a later reader must be able to answer: *which extractor produced this index*,
and *which configuration produced this number*.

> **`Phase7Extraction`, `Phase7Selection` and `Phase7Test` describe the minimum logical shapes that
> must end up persisted — nothing else.** They are not an instruction to create new dataclasses, new
> loaders, a registry, a base class or any other abstraction layer. If plain JSON files plus the
> structures the project already has (`ExtractionRecord`, `NodeIndex`, `FusionFit`, `RunResult`) carry
> these fields, that **is** the contract, fully satisfied. Build the smallest thing that writes the
> fields below and reads them back verified.

### `Phase7Extraction` (one directory per candidate)

| Field | Type | Notes |
|---|---|---|
| `extractor_id` | str | Short stable id, e.g. `gliner`, `spacy`; the directory name |
| `model` | str | Model identity as loaded |
| `revision` | str \| null | Pinned revision/commit/version; `null` only if the source exposes none, and then declared |
| `labels` | list[str] | The declared label set |
| `library_versions` | dict | The libraries that produced the records |
| `hardware` | dict | CPU / GPU / RAM / OS / arch, as measured |
| `n_units`, `failures`, `failure_rate` | int / dict / float | Same semantics as Phase 5 |
| `seconds`, `paragraphs_per_second` | float | Measured wall clock for the extraction pass |
| `usd` | float | Actually incurred; `0.0` for a local run on owned hardware |
| `projection_5m` | dict | `{paragraphs, hours, usd, method: "linear from measured throughput"}` |
| `records` | JSONL(.gz) | One line per paragraph, `unit_id` sorted, `ExtractionRecord` fields |
| `digest` | str | sha256 over the records text |

**Invariants:** every pool unit has a record, `ok` or `failed`; no record carries question, answer,
gold or split information; `concepts` is always empty in Phase 7; `entities` obey the existing bounds
(`MAX_NODES_PER_TYPE`, `MAX_NODE_CHARS`) and an answer outside them is a failure, never a repair.

### `NodeIndex` — unchanged

Built by `build_node_index(records, unit_ids, extraction_digest=<Phase7Extraction.digest>)`, written by
`save_node_index`. **Each candidate writes to its own directory**, because `load_node_index` requires
exactly one index per directory unless the digest is passed explicitly. `data/nodes/` and
`data/extraction/` are Phase 5/6 artifacts and are never written to by this phase.

### `Phase7Selection` (one per phase)

Per candidate: extractor identity, node/incidence counts, fitted scheme and weight, dev metrics at all
four budgets, hop behaviour figures, cost block and projection; then the rule as applied, the selected
`extractor_id`, and the reason. Written before the test run.

### `Phase7Test` (one per phase)

The single held-out run of the selected extractor: `RunResult` from the unchanged harness, plus the
inherited Dense / Dense + BM25 / Dense + Entity Hop (Claude) test figures quoted beside it with their
source files named.

## Restrictions

- **Dependencies: approved.** GLiNER and spaCy, with their models, are **approved** as Phase 7
  dependencies and candidates; the `CLAUDE.md` "ask first" rule is satisfied by this spec. Their
  availability on **Windows ARM64** remains a real operational risk. **Running the extraction pass on
  an x86 and/or GPU machine is also approved**: the pass is offline and its only output is an
  artifact, so it may be produced elsewhere and carried back into the repository. The experiment is
  not distorted to fit the laptop, and the hardware actually used is recorded with the figures.
- **Model downloads are external input.** Record model identity and revision. Prefer non-executing
  weight formats where a choice exists; spaCy pipelines and some model archives deserialize executable
  content, which is a reason to install them from their official distribution channel and pin them.
- **No Anthropic key is needed.** Local extractors must not require `ANTHROPIC_API_KEY`. Secrets stay
  in `.env`, are never printed, never cached, never committed.
- **Do not invalidate Phase 5/6 artifacts.** `data/extraction/`, `data/nodes/`, `data/replacement/`,
  `config.PINNED_*`, `EXPECTED_*` and the `extract` / `nodes` / `navigate` / `replace-*` stages stay
  exactly as they are, and the existing suite must still pass unchanged. The Phase 6 pins verify the
  Claude extraction by digest: any change there breaks a published result.
- **Determinism.** Extraction must be run with a fixed seed where the model exposes one, and any
  non-determinism (batching, GPU kernels) is declared. As in Phase 5, the written extraction artifact
  is the record; everything downstream of it is deterministic.
- **ASCII only** in `print()`, logging and Python string literals. Entity forms are corpus data and may
  hold any Unicode; they are never printed to a log.
- **Dev/test separation is operational, not aspirational.** The runner refuses test questions in any
  fitting or selection path, exactly as the existing selection code does.
- **English** everywhere in code, artifacts and documents produced by this phase.

## Anti-goals (what this phase does NOT do)

- NO general NER benchmark, NO NER F1, NO precision/recall against an entity gold standard.
- NO fourth, fifth or sixth extractor family added mid-phase.
- NO canonicalization, alias resolution, relations, triples, attributes or PageRank.
- NO query-aware Entity Hop, NO multiple seeds, NO second hop, NO change to read depth.
- NO change of Dense model (that is Phase 8) and NO FullWiki corpus (that is Phase 9).
- NO change to the corpus, the indexing unit, the splits, normalization v1 or the node index shape.
- NO LLM inside the retrieval loop.
- NO re-running the Phase 5 Claude extraction, and NO re-measuring the Phase 6 runs.
- NO Phase 6-style apparatus: no freeze/supersede protocol, no deviation branches, no decision table,
  no non-inferiority margin, no preregistered state machine, no `7.tasks.md`.
- NO tuning of anything against a test figure, ever.

Result-changing code only, per the simplification rule. Four areas, not a suite:

## Security

The phase adds new dependencies, model downloads and (possibly) model deserialization, which are the
`/8-auditar` triggers. **Settled:** a short, **targeted review of exactly those three surfaces** —
new dependencies, model download and identity, deserialization / model loading — carried out when the
extractors are added. Not a full Phase 6-scale audit, and nothing beyond those three surfaces unless a
concrete new surface actually appears.

## Success criterion

The phase is finished when the following exist and are written down:

- [ ] dev Full Support @2,048, with the fitted scheme and weight, for every candidate that ran;
- [ ] the measured cost block and the 5M projection for every candidate that ran;
- [ ] the selection rule applied as written, with the selected extractor named — or a written negative
      result if none passes;
- [ ] one held-out test run for the selected extractor, reported beside the inherited Dense,
      Dense + BM25 and Dense + Entity Hop (Claude) test figures — and no test run at all if no
      candidate passes, because a negative phase has nothing to read test for;
- [ ] every declared gap named (starting with the missing Phase 5 extraction wall-clock time);
- [ ] `7.results.md`, and a one-line update to the master plan's phase table.

Answered, the phase hands Phase 8 one thing: which extractor to build the entity index with.
