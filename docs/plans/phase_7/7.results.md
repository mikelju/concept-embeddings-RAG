> Can the expensive Claude-based entity extraction be replaced by a cheap or local extractor without
> materially losing the Entity Hop retrieval gain?

**Not yet answered.** Not because a candidate failed, and not because the measurement was attempted
and came out negative: the corpus-scale extraction pass has not been run. The apparatus that would
answer it exists and is exercised end to end by tests; what it is missing is one decision about
where to spend the wall-clock time, and that decision is the author's. §"What the author decides
next" states it in one paragraph.

This is **not** the spec's negative result. A negative result would be a written `selection.json`
with `selected: null` after every candidate had been measured on dev. That artifact does not exist,
and `data/phase7/` holds only the downloaded GLiNER checkpoint.

## What was actually measured

Two things, and only two. Both are operational facts about this machine, not retrieval results.

### 1. GLiNER throughput, measured on a 120-paragraph probe

Run on 2026-09-18 with the pinned configuration exactly as `config.py` declares it —
`urchade/gliner_medium-v2.1` at revision `40ec4193…`, five labels, threshold `0.5`,
`flat_ner=True`, batch size 8, loaded from `model.safetensors`:

| Figure | Value |
|---|---:|
| Sample | 120 paragraphs, drawn from the 19,366-unit pool with `random.Random(DEFAULT_SEED)` |
| Extraction wall clock | 215.0 s |
| **Throughput** | **0.558 paragraphs/s** |
| Model download + load | 28.1 s total, of which 19.0 s is model load |
| Records `ok` | 120 / 120, 2 with no entity |
| Entity mentions kept | 822 |
| Hardware | Windows 11 ARM64, Qualcomm ARMv8 12 cores, 31.6 GiB RAM, `torch 2.13.0+cpu`, 12 threads, device `cpu` |
| Configuration digest | `390d0d8ae603fd1d` |

**This is a pre-flight probe, not the phase's throughput measurement.** Plan decision D8 requires
throughput to be timed over one full pass of all 19,366 units, with no sampling; the manifest field
`paragraphs_per_second` will be that number, and it does not exist yet. The probe was run for one
purpose: to find out how long the full pass would take before starting it.

Projected linearly from the probe, and labelled as such:

```text
full pass over 19,366 paragraphs = 19366 / 0.558 / 3600 = 9.6 hours
5,000,000 paragraphs             = 5e6   / 0.558 / 3600 = 2,488 hours (103.7 days)
```

Both figures are **projections from a 120-paragraph sample on this laptop**. Neither is a measured
result, and the 5M figure in particular says nothing yet about the economic bar: the spec's ceiling
of 48 hours is "on one machine the project can realistically obtain", and this ARM64 laptop on CPU
is the slowest hardware the phase could possibly use. A GPU pass moves this number by orders of
magnitude, and D14 already approves running extraction elsewhere.

### 2. spaCy cannot be installed on this machine

The risk D14 anticipated has materialized, and the evidence is concrete rather than inferred. A
clean install of `spacy==3.8.16` into an isolated Python 3.12 ARM64 environment fails at its
transitive dependency `blis`:

```text
x Failed to build `blis==1.3.3`
|-> The build backend returned an error
`-> Call to `setuptools.build_meta.build_wheel` failed (exit code: 1)
    error: Unable to find a compatible Visual Studio installation.
help: `blis` (v1.3.3) was included because `spacy` (v3.8.16) depends on
      `thinc` (v8.3.13) which depends on `blis`
```

No `win_arm64` wheel exists for `blis` in any 1.x release, and its sdist needs an MSVC toolchain
this machine does not have. Per the plan's time-box, the attempt stopped there. The spaCy arm is
**ready to run and blocked only on hardware**: `cer cheap-extract --extractor spacy` on any x86_64
machine produces `data/phase7/spacy/{records.jsonl.gz, extraction.json}`, and those two files are
all that has to be carried back — evaluation always runs here, from the artifacts.

The project environment and `uv.lock` were not modified by this check; the probe environment was a
throwaway.

## What the author decides next

Two decisions, neither of which an agent may take on its own, because each spends either many hours
of the author's machine or money.

1. **The GLiNER pass.** 9.6 projected hours on this laptop. Either start it here and let it run, or

Once either extraction exists, everything downstream is one command and costs nothing but minutes.

**Money spent by this phase so far: 0.00 USD.** No API call per paragraph, no rented compute, no
subscription. The GLiNER checkpoint is Apache-2.0 and was downloaded once.

## Commands

```bash
# 1. Extraction. One per candidate, on whatever machine suits it.
#    GLiNER runs on this laptop (~9.6 h projected); spaCy needs x86_64.
uv sync --group phase7
uv run cer cheap-extract --extractor gliner
uv run cer cheap-extract --extractor spacy

#    On rented compute, the actual charge is recorded rather than projected:
uv run cer cheap-extract --extractor gliner --hourly-rate-usd 0.80 --actual-cost-usd 7.60

# 2. Dev measurement of every extracted candidate, then the selection rule.
#    Writes data/phase7/<id>/dev.json for each, then data/phase7/selection.json.
uv run cer cheap-eval

# 3. The held-out run of the selected extractor. Once, and only if one was selected.
uv run cer cheap-eval --test
```

`cheap-eval` refuses to measure a further candidate once `selection.json` exists, so both
extractions should be present before step 2 if both arms are wanted. `cheap-eval --test` refuses
without a selection, on a null selection, and on a second run.
