# Phase 7: Cheap Entity Extraction

> Functional spec: [`7.spec.md`](7.spec.md)
> This plan implements it. **Seven steps, no `7.tasks.md`.** Phase 7 is the first phase under the
> simplification rule (`CLAUDE.md`, master plan §46), so this document is deliberately an order of
> magnitude smaller than [`6.0_dense_entity_navigation.md`](../phase_6/6.0_dense_entity_navigation.md):
> two extractor adapters, one runner, two CLI stages, five test areas, one targeted security review.

## Objective

Answer one question: **can the expensive Claude entity extraction be replaced by a cheap local
extractor without materially losing the Entity Hop retrieval gain?**

Everything except the extractor is frozen — the 19,366-paragraph pool, the indexing unit, the
splits, `BAAI/bge-small-en-v1.5`, `normalization-v1`, the `NodeIndex` shape, `EntityHopStage` with
P1 only and one hop, the fusion machinery, Full Support @2,048 as the headline. Two local
candidates are extracted, measured on dev against the inherited Claude reference, and the dev winner
is measured once on test.

A negative answer is a valid outcome and closes the phase without a test run.

## Decisions fixed before any measurement

Every value below is chosen now, in this document and in `config.py`, so that no parameter can be
selected after a number has been seen. Per spec §"Model identity is fixed before the first dev
measurement", a different checkpoint, pipeline or threshold is a **separate declared candidate**,
never a retune.

### D1–D3 — candidate B: GLiNER

| Item | Value |
|---|---|
| Library | `gliner==0.2.29` (released 2026-09-08; pure-Python `py3-none-any` wheel) |
| Model | **`urchade/gliner_medium-v2.1`** |
| Revision | **`40ec419335d09393f298636f471328b722c6da9e`** (pinned commit, never `main`) |
| Backbone | `microsoft/deberta-v3-base`, tokenizer fetched from revision **`8ccc9b6f36199bec6961081d44eb72fb3f7353f3`** |
| Weights file | **`model.safetensors`** (780,735,696 B). The repo also ships `pytorch_model.bin`; it is never downloaded (see D14) |
| Labels | `["person", "organization", "location", "work of art", "event"]` |
| Threshold | `0.5` (library default) |
| Decoding | `flat_ner=True`, `multi_label=False`, batch size 8 |
| Window | `max_len = 384` sub-word tokens, `max_width = 12` (the checkpoint's own config) |

**Why this checkpoint.** It is the most-used English single-task GLiNER, Apache-2.0, and the only one
of the family that ships a plain fp32 `model.safetensors` — which lets the whole phase avoid pickle
deserialization rather than merely mitigate it. Medium (DeBERTa-v3-base) balances CPU throughput
against quality; small and large are not Phase 7 arms.

**Why these five labels.** One-to-one with the categories the frozen Phase 5 prompt already names:
*people, organizations, places, works such as books/films/songs/albums/TV series, events*. The
comparison is between extractors, so the ontology must be the same question asked of a different
reader.

### D4–D5 — candidate C: spaCy

| Item | Value |
|---|---|
| Library | `spacy==3.8.16` |
| Pipeline | **`en_core_web_sm`, version `3.8.0`** (the only model version compatible with spaCy 3.8, per the official compatibility index) |
| Source | the official release wheel `en_core_web_sm-3.8.0-py3-none-any.whl` (12,806,118 B), installed by URL; its sha256 is computed locally at install time and recorded |
| Components | `exclude=["tagger", "parser", "attribute_ruler", "lemmatizer", "senter"]`; only `tok2vec` + `ner` run |
| Batching | `nlp.pipe(..., batch_size=64, n_process=1)` |
| Labels kept | `EVENT, FAC, GPE, LANGUAGE, LAW, LOC, NORP, ORG, PERSON, PRODUCT, WORK_OF_ART` |
| Labels dropped | the seven numeric/temporal OntoNotes labels: `CARDINAL, DATE, MONEY, ORDINAL, PERCENT, QUANTITY, TIME` |

**Why `sm` and not `trf`.** This is the spec's *conservative, CPU-friendly* arm; its point is to show
what a mature, nearly free tagger buys. A transformer pipeline would be a different candidate with a
different cost profile, and adding it is scope creep the spec forbids.

**Why that label rule.** One line, declared in advance: keep every OntoNotes label that names a
*thing*, drop the seven that name a *quantity or a time*. Dates and cardinals are not named things
in the Phase 5 sense and would manufacture hub nodes across unrelated paragraphs.

### D6 — how an extractor's output becomes an `ExtractionRecord`

One declared conversion, identical for both candidates, applied before any measurement:

1. The extractor sees **only** `unit.indexable_text` — title and paragraph, what both retrievers
   index. Nothing else is in scope by construction, exactly as Phase 5 (`build_request`).
2. Every returned span's **surface text** is taken verbatim, stripped of surrounding whitespace.
   No lemmatization, no casing change, no canonicalization: `normalization-v1` is the only
   normalizer in this project and it runs later, in `build_node_index`.
3. **Deduplicate by exact surface form**, preserving first-occurrence order. A tagger emits one span
   per *mention*; Claude was asked for one item per *distinct name*, so the de-duplication is what
   makes the two comparable.
4. **Bounds, then failure, never repair** (spec invariant): after de-duplication, more than
   `config.MAX_NODES_PER_TYPE` (50) entities, or any form longer than `config.MAX_NODE_CHARS`
   (120 characters), makes the record `status="failed"`, `failure="bounds"` — the same reason code
   the eight Phase 5 failures carry. Nothing is truncated to fit.
5. **Long paragraphs (GLiNER only).** 131 of 19,366 units (0.68%) exceed 384 project tokens
   (median 112, p95 247, p99 355, max 1,850). A unit that does not fit the model window is split at
   its own sentence boundaries — the pool already stores `sentences` — into the fewest consecutive
   windows that each fit; each window is extracted and the entity forms are unioned. Every other unit
   is a single pass. spaCy has no window limit and never splits.
6. The record is the existing `ExtractionRecord` dataclass, unchanged: `entities` as above,
   `concepts=()` always (Phase 5 returned `NAMES_ONLY`), `input_tokens=output_tokens=0` (no billing),
   `model` = the extractor's model id, and `prompt_digest` = the candidate's **configuration digest**
   — sha256[:16] over the canonical JSON of `{extractor_id, model, revision, labels, threshold,
   window rule, library versions}`. That field already means "which configuration produced this
   record"; a local extractor has no prompt, and this is its analogue. It is named as such in the
   manifest.

### D7 — where each candidate's artifacts live

```text
data/phase7/
├── gliner/
│   ├── records.jsonl.gz        one line per unit, unit_id sorted, the Phase 5 line shape
│   ├── extraction.json         the manifest: identity, hardware, timing, throughput,
│   │                           failures, cost, projection, digest
│   ├── nodes-<digest16>.json   the NodeIndex sidecar, written by save_node_index
│   ├── nodes-<digest16>.npz
│   ├── dev.json                the dev reading: fit curve, chosen scheme/weight, metrics, hop figures
│   └── run-*.json              the harness RunResult files of this candidate
├── spacy/  (same shape)
├── selection.json              the rule as applied, and the selected extractor
└── test.json                   the single held-out run, written only if a candidate was selected
```

One directory per candidate is not decoration: `load_node_index` requires **exactly one** index per
directory unless the digest is passed explicitly, and `FusedRetriever.name` is `hybrid-entity-hop`
for every candidate, so two candidates in one directory would collide on both. `data/extraction/`,
`data/nodes/`, `data/replacement/` and `data/results/` are Phase 5/6 artifacts and are never written
to by this phase.

### D8 — how throughput is measured

`time.perf_counter()` around the extraction loop only — model load, download and process start are
outside it and reported separately. One pass over all 19,366 units in `unit_id` order, no sampling,
no re-timing of a subset. The manifest records `seconds`, `paragraphs_per_second = 19366 / seconds`,
and the hardware actually used: CPU model, `os.cpu_count()`, `torch.get_num_threads()`, RAM, OS,
arch, device (`cpu` / `cuda:N`) and GPU name when a GPU is used.

Determinism is declared, not assumed: both models are deterministic at inference and the seed is set
anyway, but float non-associativity across batch sizes and devices can move a span that sits on the
threshold. As in Phase 5, **the written artifact is the record**; everything downstream of it is
deterministic.

### D9 — how the 5M projection is computed

Linear from the measured throughput, with the arithmetic in the artifact and the label attached:

```text
hours = 5_000_000 / paragraphs_per_second / 3600
usd   = hours * hourly_rate          (0.00 on owned hardware; the real rate if compute is rented)
method = "linear from measured throughput over 19,366 paragraphs"
```

No efficiency factor, no assumed speed-up, no invented hardware. The Claude reference's own
projection (~6,700 USD at the measured per-paragraph rate) is quoted the same way and is likewise a
projection, not a measurement.

The run's actual infrastructure charge is recorded separately with
`cheap-extract --actual-cost-usd <charge>`. A nonzero `--hourly-rate-usd` requires this
explicit amount: the 5M projection is never substituted for an invoice, and rented
compute is never silently recorded as free. Both amounts must be finite and non-negative.
Owned hardware defaults to an actual charge of zero.

### D10 — how dev is run, per candidate

```text
records → build_node_index(..., extraction_digest=<manifest digest>) → save_node_index
        → EntityHopStage(index, second_hop.node_weights(index))
        → fit_fusion_weight([dense, stage], questions=dev600, base_config=...)
              inherited defaults: metric gold_recall, budget 2048, FUSION_WEIGHT_GRID + RRF
        → FusedRetriever([dense, stage], scheme=<fitted>, weights=<fitted>)
        → evaluate_retriever(..., split="dev")  → dev.json
```

`dense` is built exactly as Phase 6 builds it: `DenseRetriever` over the cached corpus embeddings
plus `build_query_backend(dev_questions, backend, question_cache)`. Nothing is re-embedded.
`fit_fusion_weight` already calls `_check_questions`, which refuses any question whose split is not
`dev`, so the dev/test guard is the project's single existing refusal rather than a second copy of it.

### D11 — how the selection rule is applied

Computed in code from `dev.json` of every candidate that ran, written to `selection.json` **before**
any test run, in the spec's order:

1. retention bar: `dev Full Support @2048 >= 0.8617` (517 of 600);
2. economic bar: no per-paragraph third-party API call, software/API cost `0.00 USD`, projected
   FullWiki wall clock `<= 48 h`, Phase 7 infrastructure spend `<= 30 USD`;
3. among those passing both, the lowest projected FullWiki cost-and-time; ties by higher dev Full
   Support @2,048; still tied, by the smaller dependency and operational footprint;
4. the Dense + BM25 dev line (0.8633, 518/600) recorded as a **qualification** beside any candidate
   that lands below it, never as a rejection;
5. if none passes, `selected: null` plus the written negative result, and the phase stops there.

### D12 — how test is run, once

`cheap-eval --test` refuses to start unless `selection.json` exists with a non-null `selected`, and
refuses if `data/phase7/test.json` already exists. It then measures **only** the selected candidate's
hybrid, at the scheme and weight its dev fit chose, over the 1,400 test questions, once, and writes
`test.json` with that `RunResult` beside the three inherited test figures and the files they come
from (`data/replacement/run-dense-test-*.json`, `run-hybrid-bm25-test-*.json`,
`run-hybrid-entity-hop-test-*.json`). Nothing is refitted, and no other candidate is measured on test.

### D13 — CLI surface: two stages, and why not one

```text
cer cheap-extract --extractor {gliner,spacy}     the extraction pass, writes data/phase7/<id>/
cer cheap-eval [--test]                          dev + selection; with --test, the single held-out run
```

Two, not one, because the two passes must be runnable **on different machines** (D14): extraction
needs only `data/pool.json` and the extractor; evaluation needs the cached embeddings, the splits and
the harness. Splitting them is what makes an x86/GPU extraction pass possible without moving the rest
of the project. `cheap-eval` covers dev, selection and test in one stage, by flag, rather than three.

### D14 — where each pass runs, and what is downloaded

Checked against PyPI and the Hugging Face API rather than assumed (all figures below are read, not
guessed):

| Package | cp312 `win_arm64` wheel | Consequence |
|---|---|---|
| `gliner` 0.2.29 | pure Python (`py3-none-any`) | installs anywhere |
| its deps: `torch` ≥2.0, `transformers` ≥4.51.3 <5.17.0, `huggingface_hub`, `safetensors`, `sentencepiece` | already installed (`torch 2.13.0+cpu`, `transformers 5.16.1`); `sentencepiece` 0.2.2 ships cp312-win_arm64 | **GLiNER is expected to install on the ARM64 laptop** |
| `spacy` 3.8.16 | yes | — |
| `thinc` 8.3.13 | yes | — |
| **`blis`** (required `>=1.3.0,<1.4.0` by thinc) | **no win_arm64 wheel exists, in any 1.x release** | **spaCy cannot be installed from wheels on this laptop** |

So the plan is explicit rather than hopeful: **GLiNER extraction runs locally on the ARM64 machine.**
For **spaCy**, one short time-boxed attempt to build `blis` from its sdist is allowed; if it does not
build cleanly, the spaCy extraction pass runs on an **x86_64 machine** and only
`data/phase7/spacy/{records.jsonl.gz, extraction.json}` is carried back into the repository. The
evaluation always runs on the project machine, from the artifacts. The hardware actually used is
recorded per candidate, and a candidate extracted on different hardware from another is compared on
retention first and on its own measured throughput second — which is exactly what the manifest
records.

**Downloads, and what is deliberately not downloaded.** Model files are fetched with
`huggingface_hub.snapshot_download(repo_id, revision=<pinned sha>, allow_patterns=[...])`, and the
allow-list **excludes `pytorch_model.bin`, `tf_model.h5` and `rust_model.ot`**: GLiNER loads
`model.safetensors`, and the DeBERTa tokenizer needs only `spm.model`, `tokenizer_config.json` and
`config.json`. No pickle archive is downloaded, so none can be deserialized. If a loader nonetheless
demands a `.bin`, that is a finding to report, not a reason to fetch one.

## Tests

Result-changing code only, per the simplification rule. Five areas, not a suite:

1. **Conversion to `ExtractionRecord`** — de-duplication preserves first-occurrence order; >50
   entities or a >120-character form yields `status="failed"`, `failure="bounds"` and empty
   `entities`; `concepts` is always empty; a unit with no span is `ok` with no entity; the sentence
   windowing of a long paragraph unions its windows and leaves short paragraphs on a single pass.
2. **Artifact round-trip** — records survive write/read byte-identically, the digest is stable across
   two writes of the same records, and a modified archive raises rather than loading.
3. **`NodeIndex` from Phase 7 records** — on a small fixture corpus, the index's entity columns and
   rarity weights drive `EntityHopStage` to the expected ranking, and the index refuses a build that
   does not cover every unit.
4. **Dev-only selection** — a test question handed to the fit or the selection path is refused; a
   node index built over another pool is refused; `cheap-eval --test` refuses without a selection and
   refuses a second run.
5. **`EntityHopStage` compatibility** — a stage built on a Phase 7 index fuses through
   `FusedRetriever` and is measured by `evaluate_retriever` with no change to either.

Plus: the existing suite, `ruff check .` and `mypy src` must still pass unchanged. No model is
downloaded and no extractor library is imported inside a test; both adapters are exercised through a
fake that returns fixed spans.

## Notes and technical decisions

- **Reuse first, and it is nearly total.** The only genuinely new code is the span→record conversion
  and the runner's wiring. `build_node_index`, `save_node_index`, `load_node_index`,
  `second_hop.node_weights`, `node_hop`, `EntityHopStage`, `FusedRetriever`, `fit_fusion_weight`,
  `evaluate_retriever`, `digest_of` and the atomic writers are all used exactly as they are. No
  extractor registry, no base class, no abstraction for a hypothetical third extractor: if Phase 8
  or 9 needs one, it will be added then, against a real requirement.
- **No Phase 6 machinery.** No freeze artifact, no supersede protocol, no deviation branch, no
  decision table, no non-inferiority margin, no state machine, no recording hybrid unless the
  introduced-units figure turns out to cost one call. The spec's contracts are field lists, not
  classes to build (spec §Contracts).
- **The Phase 6 pins are load-bearing and untouched.** `PINNED_EXTRACTION_DIGEST`,
  `PINNED_NODE_INDEX_DIGEST`, `EXPECTED_ENTITY_NODES` and friends verify the Claude extraction by
  digest; any change there breaks a published result. Phase 7 adds constants beside them and edits
  none.
- **The reference arm is quoted, never re-run.** Claude extraction: 25.9848 USD, 96,416 entity nodes,
  155,109 entity incidences, 8 `bounds` failures (0.0413%), 163 paragraphs with no entity node. Its
  wall-clock extraction time was never recorded and stays a **declared gap**, so "paragraphs per
  second" exists for the local candidates and not for the reference.
- **Corpus length facts, measured from `data/token_counts.json`**: mean 124.4 project tokens, median
  112, p95 247, p99 355, max 1,850; 131 units (0.68%) above 384. The GLiNER window rule therefore
  touches well under 1% of the pool, which is why it is a declared edge rule rather than a chunking
  strategy — and the project's "complete-meaning indexing unit" rule is untouched: the *indexing*
  unit is still the whole paragraph; only the extractor's reading window is split.
- **ASCII in logs.** Entity forms are corpus data and may hold any Unicode; they are never printed,
  exactly as `cer nodes` already avoids printing them.
- **What this plan does not do**: no canonicalization, no relations or triples, no PageRank, no
  query-aware hop, no second seed, no second hop, no change to read depth, no change to the Dense
  model (Phase 8) and no FullWiki corpus (Phase 9), no NER F1 against an entity gold standard, no
  fourth extractor family, and no tuning of anything against a test figure.
