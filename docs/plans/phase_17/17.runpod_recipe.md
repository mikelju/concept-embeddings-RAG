# Phase 17 — RunPod operating recipe

> Operational runbook for **plan step S4**: scoring the three pools (HotpotQA dev, MuSiQue
> validation, MultiHop-RAG answerable) with the three declared judges, J-light, J-strong and
> J-decision (deviation [17.1](17.1_clm8b_third_judge.md)), on one rented GPU. Everything else
> (`p17-outcome`, the paper) runs on the laptop afterwards.
>
> Written out in full, not by reference, following the shape of
> [`16.runpod_recipe.md`](../phase_16/16.runpod_recipe.md); the differences from it are the plan's
> ("The pod recipe: differences from `16.runpod_recipe.md`"). The pod is created, driven over SSH
> and terminated by the agent through the RunPod GraphQL API, as in Phase 16.
>
> **Stop point 1.** Nothing here starts before the author says go on this recipe, the rate, the
> frozen commit and the projected cost. On the pod, **if the session reaches 10 USD, or a
> projection exceeds it, stop the pod and ask the author before anything else.**
>
> The pod scores pairs; it computes no retrieval metric. Labels: **measured** (read off an
> artifact or a command today), **derived** (arithmetic on measured values), **projection** (not
> a measurement).

### Why the disks (derived)

Qwen3-8B is 16.4 GB of weights (`pool.json`), bge-reranker-v2-m3 2.27 GB, MiniLM 0.09 GB, the
heads 76 MB. The environment is large: torch 2.13.0+cu126 with its CUDA libraries, then vLLM
0.30.0 and its dependencies on top (several GB; not measured). `env.sh` puts uv's cache and
Python, the Hugging Face cache and the virtual environment (inside the repository) on the
volume, so the volume holds about 16.4 + 2.4 + (venv 10-15 + uv cache 8-12, projection) + 0.3
GB of uploads + scores, which is too tight for 40 GB. **Volume 80 GB** gives room; the container
disk goes to **40 GB** for vLLM's compile and kernel caches, `/tmp` and the system (redirected
to the volume in `env.sh` as far as the environment variables allow). Extra cost: a few cents
per hour at most (projection; RunPod prices disk by GB-month). `df -h` is read after setup and
after each model download; under 5 GB free: STOP.

## 6. The cross-encoders: six processes, one at a time

Order: J-light on MultiHop-RAG, MuSiQue, HotpotQA, then J-strong on the same three. Each is one
process, started only after the previous printed `[OK]`:

```bash
cd /workspace/concept-embeddings-RAG && source /workspace/env.sh
nohup uv run cer p17-score --judge light --set multihop-rag --hourly-rate-usd <RATE> > data/phase17/logs/light-multihop-rag.log 2>&1 &
tail -n 3 data/phase17/logs/light-multihop-rag.log      # repeat until "[OK] ..."
```

then `--set musique` (log `light-musique.log`), `--set hotpotqa` (`light-hotpotqa.log`), then
the same three with `--judge strong` (`strong-<set>.log`). Wait with a loop such as
`until grep -qE "^\[OK\]|Traceback|Error" <log>; do sleep 20; done`.

What each process does: it refuses unless `integrity.json` and `pool.json` are committed
unmodified and passing and the pairs file's SHA-256 is `pool.json`'s; it loads the pinned judge
and refuses a served revision or weights SHA-256 other than the pin; it scores shards of 250
questions (one `predict` call each, written atomically under `data/phase17/shards/<judge>-<set>/`,
resumable: if a process dies, rerun the **same line once**; a second failure: **STOP**); it writes
`scores-<judge>-<set>.jsonl.gz` once (an existing file refuses), re-scores the first 20 questions
at batch size 1 for determinism, and adds the set's block to `scoring-<judge>.json`.

Batches: J-light 256 pairs, J-strong 32 pairs (maximum lengths 512 and 8,192, float32,
matmul precision `highest`). **Out of memory** shows within seconds (batches start with the
longest pairs): halve the batch once, recorded here and in the commit; a second out-of-memory:
**STOP**.

### The checks after each process (quick looks; no metric is involved)

```bash
# per (judge, set), substituting both names:
python3 -c "

print('pairs', b['pairs'], 'pool.json', p['pairs'], b['pairs'] == p['pairs'])
print('truncations', b['truncations'])
print('determinism', b['determinism'])
print('seconds', b['wall_seconds'], 'pairs/s', b['pairs_per_second'], 'usd', b['usd'], 'vram_mb', b['peak_vram_mb'], 'rss_mb', b['peak_rss_mb'])
"
python3 -c "
import gzip, json, math
n = bad = 0
for line in gzip.open('data/phase17/scores-<JUDGE>-<SET>.jsonl.gz', 'rt'):
    r = json.loads(line); n += 1
    assert len(r['unit_ids']) == len(r['scores'])
    bad += sum(not math.isfinite(x) for x in r['scores'])
print('rows', n, 'non-finite', bad)

```

Expected: revision and weights prefix equal the pin (`233902d2…`/`821d1aa6` for J-light,
`953dc6f6…`/`d9e3e081` for J-strong); `pairs` equal `pool.json`'s (317,776 / 400,745 /
1,295,224) and `True`; rows 2,255 / 2,417 / 7,405; **0 non-finite**; truncations and determinism
recorded (they decide nothing). Anything else: **STOP**.

### The projection after J-strong's first shard (before it continues)

When `strong-multihop-rag.log` shows its first shard (`[INFO] shard 1/...`), compute from the
log and the manifest-in-progress (`data/phase17/shards/strong-multihop-rag/shard-0000.json` holds

```
strong_pairs_per_s   = shard-0000 pairs / shard-0000 seconds          (measured)
```


Then `musique`, then `hotpotqa`, each after the previous printed `[OK]`. Per set the stage
embeds every distinct unit of the pool once (the offline pass: 23,116 / 76,148 / 841,339 units,
measured on the laptop), then the questions shard by shard, then the determinism re-score (the
first 20 questions' states and all their units, one text per request). A restart embeds only
the units of the shards still missing.

**The projection after J-decision's first shard on MultiHop-RAG, before HotpotQA starts.**
Read the offline pass and the first shard from
`data/phase17/shards/decision-multihop-rag/offline.json` (`passes[0].seconds`, `units`,
`tokens_reported`) and `shard-0000.json` (`seconds`, questions):

```
tokens_per_s     = passes[0].tokens_reported / passes[0].seconds                  (measured)
units_per_s_mhr  = passes[0].units / passes[0].seconds                            (measured)
offline_s(set)   = distinct_units(set) * mean_tokens_per_unit(set) / tokens_per_s (derived;
                   mean tokens 68.7 / 101.8 / 66.7 budget tokens for MultiHop-RAG / MuSiQue /
                   HotpotQA, from the corpus manifests, an approximation of Qwen3's count)
query_s(set)     = questions(set) * (shard-0000.seconds / its questions)          (derived)
decision_s       = sum over MuSiQue and HotpotQA of (offline_s + query_s)
                   + what MultiHop-RAG still needs                                (derived)
session_total    = (elapsed_h_so_far + decision_s / 3600 + 0.5 h download and termination)
                   * <RATE>                                                       (derived)
```

If `session_total` exceeds **10 USD**: stop vLLM and the pod and ask the author; do not start
HotpotQA. Otherwise record the figure and go on. HotpotQA's offline pass is by far the longest
(841,339 units): its progress lines (`[INFO] offline: n/N units (x units/s)`) are watched; if
the rate falls below what the projection assumed such that the total would pass the guard, stop
and ask.

The checks after each process are those of section 6, with `scoring-decision.json`, plus:
`score` is `logit`, the `scale` (100.0 expected, derived from the stored `logit_scale`), the
`serving` block holds the verbatim command and pooler, `offline.distinct_units` equals the
laptop's, `tokens_reported` against `tokens_expected` match, **0 truncations**, `peak_vram_mb`
(the process's own; vLLM's is in `nvidia-smi`).
