# Phase 3: Hybrid conceptual retrieval (System B)

> Functional spec: `docs/plans/phase_3/3.spec.md`
> This plan implements the requirements defined in that spec.

## Objective

Retrieve through the concept space for the first time, and produce a number that can be believed.
Phase 2 shipped four spaces and chose none of them; this phase chooses one against dev recall, builds
the conceptual retriever that scores over `X` alone, fuses it with the Phase 1 dense retriever into
**System B**, and measures a **dense+BM25 control** under the identical fusion and the identical
fitting procedure so that "the hybrid beats dense" cannot be reported as evidence for a concept space
when it is a generic property of fusing two signals.

The deliverable is `docs/plans/phase_3/3.results.md` plus a versioned selection artifact, and the
three decisions Phase 4 inherits from it: **which K, which view of `X`, and whether anything is
damped**. A well-argued negative result closes this phase as well as a positive one — the outcome
that would be a genuine failure here is not "System B loses", it is a win nobody can attribute.

## Success criteria

<!-- Mapped 1:1 from the spec's acceptance criteria -->

**HU-1 - The question enters the concept space with no textual intermediary**
- [ ] The query reaches the concept space through the embedding backend and the dictionary atoms
      only: no label, no generated text, no keyword extraction, no LLM call — and a test asserts the
      retrieval path neither imports nor reads the labels artifact
- [ ] Both operators are implemented and measured on the **dev split only**, and the chosen one is
      recorded with the artifact together with the number that chose it
- [ ] Any truncation of the query's concept vector is an explicit, recorded parameter, never a
      constant buried in the code
- [ ] The mapping is deterministic: same question + same dictionary → same concept vector, and the
      seed of anything stochastic travels in the config
- [ ] The mapping reads no gold annotation and no split label. It sees a question string and nothing
      else

**HU-2 - Chunk scoring over the active dimensions of X**
- [ ] Implements the existing `Retriever` protocol unchanged. **The harness is not modified to
      accommodate it**; if it has to be, that is a finding recorded as a deviation
- [ ] A unit's score comes from the query's concept vector and the unit's row of `X`, over the
      concepts active in both. No dense similarity and no lexical signal enters this retriever
- [ ] **Both views of `X` are measured** — `raw` and `row_normalized` — and the chosen one is
      declared with its reason
- [ ] Ranking deterministic including ties, broken by unit id exactly as the dense retriever does
- [ ] Returns hits at the same `top_k = 100` the baselines use, so budget filling sees the same depth
      of candidate list for every system
- [ ] A unit with an all-zero row of `X` can never be retrieved, and that is asserted rather than
      discovered — Phase 2 measured zero orphan units at every K

**HU-3 - The choice of K, made on dev and reported beside what recall cannot see**
- [ ] All four spaces measured on the **dev split**, selection made on **conceptual-only gold
      recall**, never on the fused system
- [ ] Primary figure is dev gold recall at the **2,048-token budget**, with the full four-budget
      table reported alongside so a ranking that holds at one budget only is visible as such
- [ ] For each K, in the same table as recall: **hub share** (units activated by the largest concept,
      and its share of row-normalized mass) and **thin-concept count** (< 30 supporting units), both
      read from the Phase 2 diagnostics artifacts, not recomputed
- [ ] **The selection is written into a versioned artifact**, naming the winning K, its dictionary
      key, the metric and budget that chose it, and the runner-up with its margin
- [ ] If the margin is smaller than the dev split can resolve, that is stated and the tie is broken
      by a **declared, structural** criterion — the smaller hub — not by the larger decimal
- [ ] The test split is not read at any point of the selection

**HU-4 - Fusion with weights that were fitted, not eyeballed**
- [ ] The fusion is invariant to the arbitrary scale of each signal by an explicitly declared
      mechanism (see decision D6)
- [ ] **A parameter-free fusion is measured as a reference** — RRF — and the weighted fusion is
      reported against it; a weighted scheme that does not beat it on dev has bought a degree of
      freedom it did not need, and that is reported as the finding it is
- [ ] Weights searched on the **dev split only**, over a declared grid, with the grid, the selected
      value and the dev curve around it all recorded
- [ ] The fused retriever also implements the unchanged `Retriever` protocol
- [ ] The dense component is the **Phase 1 dense retriever unmodified**, reading the same embedding
      cache. Nothing here re-embeds or re-ranks the corpus

**HU-5 - The control that makes the claim falsifiable**
- [ ] A dense+BM25 hybrid measured under the **same fusion mechanism and the same dev-fitted
      procedure** as System B
- [ ] The results table reports side by side: BM25, dense, dense+BM25 (control), conceptual-only, and
      System B
- [ ] The report states plainly where System B lands **relative to the control**, and treats
      "System B beats dense but not dense+BM25" as the negative result it is
- [ ] The control is a measurement, not a system to be optimized: not tuned beyond the identical
      procedure, and not carried forward into Phase 4

**HU-6 - The hub, declared before it is measured**
- [ ] A **declared variant** weights each concept by its rarity across the pool (an IDF-shaped
      function of its support), measured with and against on the dev split
- [ ] The damping is a **retrieval parameter and leaves the dictionary untouched**: no atom removed,
      merged or rewritten; the Phase 2 artifacts stay read-only inputs
- [ ] The damping function and its parameters are declared in this plan **before** the variant runs
      (decision D7) and are recorded in the result config
- [ ] Reported whether it helps or not, including at the K where no hub exists (512, 1,024) — and if
      it helps *there* too, that is a finding about rarity weighting in general, not about the hub
- [ ] **No concept is pruned in this phase.** Pruning by coherence stays a Phase 5 ablation; selecting
      concepts by their LLM-given names is excluded permanently

**HU-7 - The dev split spent accountably, the test split read once**
- [ ] The selection artifact lists **every decision made against dev**, with its alternatives and the
      margin that decided it, and reports the count itself
- [ ] The full configuration is **frozen** before test is read, and the freeze is observable in the
      artifact — a recorded configuration with a timestamp, not an intention
- [ ] Test evaluated **once**, on the frozen configuration. A forced re-run is recorded as a deviation
      (`3.Y_name.md`) with what changed and why
- [ ] The report states System B's dev-to-test gap beside the same gap for the Phase 1 baselines,
      which were fitted on nothing
- [ ] No hyperparameter, threshold, weight or K is ever chosen, adjusted or confirmed by a number
      computed on test

**HU-8 - Measured in the unchanged harness, and the winning space made readable**
- [ ] Every system measured at the same four budgets, on the same splits, with the same tokenizer and
      the same `top_k`, through `evaluate_retriever` unmodified
- [ ] The same four metrics reported: gold recall, Full Support, context precision, recall@{2,5,10}.
      Full Support remains the headline
- [ ] **Cost recorded per system**: mean query latency and mean units included at the largest budget,
      as Phase 1 did
- [ ] Every result carries the config keys the harness already requires **plus** `dictionary_key`,
      `k`, `view`, `query_operator`, `fusion_scheme` and `damping`
- [ ] The **Phase 1 failure analysis is repeated for System B** on dev @2,048: how many of the 72
      questions that defeated both baselines it recovers, and how many it loses that dense had
- [ ] If the selected K is not 2,048, its concepts are labelled for the report only, under the Phase 2
      rules, and the spend is confirmed before the run; if it is 2,048, the existing labels artifact is
      reused and nothing is spent
- [ ] `docs/plans/phase_3/3.results.md` records every figure with the artifact it was read from.
      Nothing is recomputed for the report

## Technical notes and decisions

Decisions **D1-D8 are declared here before any number is measured**, which is what HU-4 and HU-6
require of the fusion grid and the damping function. Anything the measurement forces to change is
recorded as a deviation (`3.Y_name.md`), never edited into this list afterwards.

### D1 - The query enters as a cached embedding, never a fresh encode

`DenseRetriever.retrieve` calls `backend.encode([query])` on every call: 30.7 ms per question on this
CPU, ~18 s per pass over the 600 dev questions. The sweep of this phase makes dozens of passes, and
re-embedding the same 600 strings each time would cost hours for nothing.

`embed_questions` computes dev and test question embeddings once, caches them keyed by
(model, revision, question-set hash, split), and `CachedQueryBackend` implements the existing
`EmbeddingBackend` protocol by lookup. **It raises on a miss** rather than falling back to the model,
because a silent fallback is exactly the bug that would make the sweep slow without making it wrong,
and therefore invisible. `DenseRetriever` is not modified: it receives a different backend.

### D2 - The conceptual score is a dot product over `X`, not a cosine

`scores = X @ c`, with `X` in CSR and `c` the query's concept vector. Sparsity does the work HU-2
asks for: only concepts active in both contribute, by construction. A cosine is deliberately *not*
used, because dividing by the row norm silently applies the `row_normalized` view and would collapse
the very comparison HU-2 requires between the two views.

### D3 - Both views are loaded from disk, never derived on the fly for the sweep

`row_normalized` is a pure function of `raw` (Phase 2, decision D7) and both artifacts exist on disk.
The sweep loads the artifact for the view it is measuring, so what is measured is what a later phase
would load.

### D4 - The query operator has three arms, and truncation is part of the operator

Truncating the query's concept vector is not a separate knob to be swept independently; it is what
distinguishes one projection operator from another. The declared arm set:

| Arm | Operator | Truncation |
|---|---|---|
| `projection_top16` | `atoms @ q`, clipped at zero | top 16 concepts |
| `projection_full` | `atoms @ q`, clipped at zero | none |
| `sparse_coding` | `dictionary.encode(q)` at the corpus coding alpha | none (sparse by construction) |

16 matches the corpus side: Phase 2 calibrated `X` to 8-16 active concepts per unit
(`SPARSITY_TARGET_BAND`), so a top-16 query vector describes the question at the same resolution the
units are described at. Both the truncated and untruncated projections are measured because the
principled choice and the unconstrained one disagree often enough that assuming either would be a
guess. Counted in the ledger as **one** decision with three alternatives.

### D5 - The sweep is 24 conceptual-only dev evaluations, and its cost is bounded before it runs

4 K x 3 operator arms x 2 views. Query concept vectors are computed once per (K, arm) and reused
across views and budgets; the four budgets come out of a single ranking pass, as the harness already
does. The one arm with a real cost is `sparse_coding`, which runs a lasso per question per K; if
600 x 4 codings exceed a few minutes, the codes are cached to disk under the same artifact rules and
that is recorded — not silently skipped.

### D6 - Fusion: declared normalization, declared grid, RRF as the reference

- **Normalization**: per-query min-max over the union of the components' `top_k` lists. Each component
  is asked for `top_k = 100`; the union is at most 200 units; the fused retriever returns the best
  `top_k` of that union. **A unit absent from a component's list receives that component's normalized
  floor (0.0)** — declared rather than left to an implementation detail, since it is the difference
  between "this component ranked it last" and "this component never saw it".
- **Weighted scheme**: `s = w * dense_norm + (1 - w) * other_norm`, with the grid
  `w ∈ {0.0, 0.1, ..., 1.0}` (11 points). The endpoints are in the grid on purpose: if the optimum
  lands on `w = 1.0`, the fusion is telling us the second signal contributes nothing, and that is a
  result worth being able to read directly off the curve.
- **RRF**: `s = Σ 1 / (60 + rank_i)`, the standard constant, no weight to fit. Measured for both
  hybrids and reported beside the weighted scheme.

### D7 - The damping function, declared before it is measured

`w_j = log(1 + N / (1 + df_j))`, where `df_j` is the number of units with a non-zero weight on concept
`j` and `N = 19,366` is the pool size. Applied multiplicatively to the **query's** concept vector,
which is algebraically the same as scaling the columns of `X` but leaves both the matrix and the
dictionary untouched on disk and in memory, as HU-6 requires. `df_j` is read from the Phase 2
diagnostics (`units_per_concept`), not recomputed.

At K = 4,096 the hub has `df ≈ 19,250`, giving it a weight near `log(2) = 0.69`, while a concept
supported by 30 units gets `log(1 + 625) ≈ 6.4`: roughly a 9x demotion of the corpus's house style
relative to a specific concept. `damping ∈ {none, idf}` is a two-arm decision measured on the
selected space, and also reported at K = 512 and 1,024 where no hub exists.

### D8 - The order of the decisions is fixed in advance, and so is the ledger

The order cannot be reshuffled after the fact to flatter a result:

1. **Space configuration** (K x operator x view, 24 alternatives) on conceptual-only dev gold recall
   @2,048. Fusion is not involved: a strong dense signal masks the differences between spaces, and
   what is being chosen here is a space.
2. **Damping** (2 alternatives) on the selected space, conceptual-only.
3. **Fusion scheme** (RRF vs weighted, 2 alternatives) on dev System B.
4. **Fusion weight** (11 alternatives) if and only if the weighted scheme won step 3.

Four ledger entries, each carrying its alternatives and its margin, so `n_dev_decisions = 4` with the
arm counts visible inside. The control is fitted by steps 3 and 4 through the same code, but its
choices are not System B's decisions and are recorded separately.

### D9 - The control is built by the same function or the comparison is void

`build_fusion(...)` and `fit_fusion_weight(...)` are called with `[dense, conceptual]` and with
`[dense, bm25]`. Step 18 asserts parity as a test rather than as an intention, because giving the
control a worse fusion is the single easiest way to manufacture this phase's headline.

### D10 - The freeze is enforced by the code, and a second test read is visible

`cmd_evaluate` refuses to evaluate a Phase 3 system on test unless a frozen `SelectionReport` exists,
and stamps its `frozen_at` into the result config. The harness already writes append-only (`-2`, `-3`
suffixes, never an overwrite), so a second test run cannot hide: **a `-2` suffix on a Phase 3 test
result is, by this plan, a deviation document waiting to be written.**

### D11 - Labelling is conditional, report-only, and confirmed before it spends

If the selected K is 2,048, the Phase 2 labels artifact is reused and nothing is spent. If it is not,
the selected space is labelled under the Phase 2 rules — cached, non-reproducible by design, never
read by retrieval — at roughly 7 USD, and **the spend is confirmed with the author before the run**.
Nothing in the metrics path depends on it either way.
