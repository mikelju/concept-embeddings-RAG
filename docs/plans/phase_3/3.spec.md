# Spec Phase 3: Hybrid conceptual retrieval (System B)

> Functional specification - WHAT to build and WHY.
> The HOW belongs in the phase plan (`3.0_phase_name.md`).
> Acceptance criteria are verified with `/7-verificar` at the end of the phase.

---

## Problem and objective

**Problem**: Phase 2 built a second coordinate system for the same 19,366 paragraphs and proved only
that it is well-formed. Four spaces exist, none is chosen, and not one number in that phase is
evidence: a concept space is not a retriever. Meanwhile the thing the project has to beat is
measured and hard - dense retrieval reaches 0.825 Full Support at 2,048 tokens on test, and BM25 is
close enough behind that "we improved on dense" is not by itself an interesting sentence.

**Objective**: retrieve with the concept space and find out what it is worth. Map the question into
the space with no textual intermediary, score units over the active dimensions of `X`, fuse that
signal with the dense one, and measure the result in the unchanged Phase 1 harness against both
baselines. The phase ends with a number for System B and with the three decisions Phase 4 inherits
and cannot make for itself: **which K**, **which view of `X`**, and **whether anything is damped**.

**What this phase cannot prove.** It cannot test the hypothesis. Phase 1 isolated the failure mode
this project exists for - 12% of dev questions defeat both baselines, always because the retriever
finds the entity the question names and never reaches the bridge entity it does not name - and a
one-hop retriever has no mechanism for that second hop, whatever space it scores in. System B can
land below dense and §69 remain entirely open. What Phase 3 settles is narrower and still
necessary: whether the representation Phase 4 will diffuse over can retrieve at all, and on which
of the four spaces.

**What closes this phase.** A reproducible number for System B against dense and BM25, at all four
budgets, on both splits - positive or negative. The outcome that would be a genuine failure of this
phase is not "System B loses"; it is **a win nobody can attribute**, which is why HU-5 exists.

## User stories

### HU-1: The question enters the concept space with no textual intermediary

**As** the researcher,
**I want** the query mapped to concepts by geometry alone, with the two candidate operators measured
against each other,
**so that** nothing an LLM or a keyword extractor decides can enter the retrieval path, and so that
the operator is chosen by a measurement rather than by the first thing that came to mind.

§6 and §50 of the hypothesis describe extracting concepts from the question as text and embedding
them. The founding decision replaced that with a dot product, because a concept's embedding *is* its
atom and the query embedding already lives in that space. Two operators satisfy that constraint and
they are not the same:

- **Projection**: `c = atoms @ q`, optionally clipped at zero and truncated to the strongest
  concepts. Dense in K; every concept receives a score.
- **Sparse coding**: the query embedding coded against the dictionary with the same non-negative
  operator the corpus was coded with, at a declared `alpha`. Sparse, and symmetric with `X` by
  construction: query and unit are described in the same way.

**Acceptance criteria:**
- [ ] The query reaches the concept space through the embedding backend and the dictionary atoms
      only. **No label, no generated text, no keyword extraction and no LLM call** takes part, and a
      test asserts that the retrieval path does not import or read the labels artifact
- [ ] Both operators are implemented and measured on the **dev split only**, and the chosen one is
      recorded with the artifact together with the number that chose it
- [ ] Any truncation of the query's concept vector (top-m concepts, or a weight floor) is an
      explicit, recorded parameter, not a constant buried in the code
- [ ] The mapping is deterministic: the same question and the same dictionary produce the same
      concept vector on every run, and the seed of anything stochastic travels in the config
- [ ] The mapping reads no gold annotation and no split label. It sees a question string and nothing
      else

### HU-2: Chunk scoring over the active dimensions of X

**As** the researcher,
**I want** a conceptual retriever that scores units over `X` and nothing else,
**so that** there exists one system whose ranking is produced purely by the concept space, and so
that the contribution of that space can be read on its own before any fusion hides it.

**Acceptance criteria:**
- [ ] The conceptual retriever implements the existing `Retriever` protocol unchanged, so the
      harness cannot tell it apart from dense or BM25. **The harness is not modified to accommodate
      it**; if it has to be, that is a finding about the interface and is recorded as a deviation
- [ ] A unit's score is computed from the query's concept vector and the unit's row of `X`, over the
      concepts active in both. No dense similarity and no lexical signal enters this retriever
- [ ] **Both views of `X` are measured** - `raw` and `row_normalized` - and the chosen one is
      declared with the reason. They are not interchangeable: `raw` lets a unit explained by few
      atoms carry larger coefficients, which the Phase 2 artifact states in its own
      `weight_semantics`; `row_normalized` gives every unit the same total attention
- [ ] Ranking is deterministic including ties, broken by unit id exactly as the dense retriever does
- [ ] The retriever returns `top_k` hits at the same `top_k = 100` the baselines use, so budget
      filling sees the same depth of candidate list for every system
- [ ] A unit with an all-zero row of `X` can never be retrieved by this system, and that is stated
      rather than discovered. Phase 2 measured zero orphan units at every K, so this is an assertion
      that should hold, not a limitation being introduced

### HU-3: The choice of K, made on dev and reported beside what recall cannot see

**As** the researcher,
**I want** K chosen against dev recall, with the two structural properties of each space reported
next to it,
**so that** the deferral Phase 2 declared is actually resolved by a measurement, and so that a K is
never chosen without knowing that one of its atoms activates on 99.4% of the corpus.

Phase 2 ended with a written instruction to this spec: report the hub share and the thin-concept
count beside dev recall for each K. Both are properties of `X` measured on the corpus, never on the
evaluation split, so reporting them costs nothing in contamination terms.

**Acceptance criteria:**
- [ ] All four spaces (K = 512, 1,024, 2,048, 4,096) are measured on the **dev split**, and the
      selection is made on **conceptual-only gold recall**, not on the fused system. Fusion with a
      strong dense signal masks the differences between spaces, and what is being chosen here is a
      space
- [ ] The primary selection figure is dev gold recall at the **2,048-token budget** - the budget the
      Phase 1 failure analysis was run at - and the full table at all four budgets is reported
      alongside, so a ranking that only holds at one budget is visible as such
- [ ] For each K the report carries, in the same table as recall: the **hub share** (units activated
      by the largest concept, as a fraction of the pool, and its share of row-normalized mass) and
      the **thin-concept count** (concepts supported by fewer than 30 units). All three are read from
      the Phase 2 artifacts, and **nothing is re-embedded, re-induced or recoded** to obtain them
- [ ] **The selection is written into a versioned artifact**, naming the winning K, its dictionary
      key, the metric and budget that chose it, and the runner-up with its margin. A K chosen in
      conversation and remembered is not a decision this project can reproduce
- [ ] If the margin between the best and second-best K is smaller than the dev split can resolve,
      that is stated and the tie is broken by a **declared, structural** criterion - the smaller hub
      - rather than by the larger decimal
- [ ] The test split is not read at any point of the selection

**Corrected during implementation (T12).** The third criterion first said all three figures were read
from the Phase 2 **diagnostics** artifacts. Only one of them is there: `units_per_concept.max /
n_units` gives the hub share. The persisted `SpaceDiagnostics` keeps `units_per_concept` as a
five-number summary rather than the per-concept vector, so it cannot say how many concepts sit below
30 units, and the hub's share of row-normalized mass is absent from it in any form. The other two are
therefore derived from the hash-verified `ConceptMatrix` of each view - one pass over a sparse matrix,
with nothing re-derived from the embeddings - which is the same resolution decision D7 already took
for the damping support and for the same reason: the number is not chosen but checked.
`test_the_structural_columns_reproduce_the_phase_2_results_table` reads all three against the four
induced spaces, so a drift in either direction fails a test instead of becoming a footnote in a
report. The full reasoning, including why the K = 1,024 mass share differs from the one
`2.results.md` prints, is under decision D5 of the phase plan.

### HU-4: Fusion with weights that were fitted, not eyeballed

**As** the researcher,
**I want** the dense and conceptual signals combined under a scheme whose parameters were chosen on
dev by a stated procedure,
**so that** System B's number is not the product of a weight someone liked, and so that the extra
freedom a weighted fusion buys has to prove it was worth having.

The two signals are not on a common scale: dense scores are cosines, conceptual scores are unbounded
sums over `X`. Any fusion must therefore say what it does about that, and saying it is part of the
deliverable.

**Acceptance criteria:**
- [ ] The fusion is invariant to the arbitrary scale of each signal, by an explicitly declared
      mechanism (per-query normalization of the scores, or a rank-based combination). Combining a
      cosine and a raw `X` sum without addressing this is not admissible
- [ ] **A parameter-free fusion is measured as a reference** - reciprocal rank fusion, which has no
      weight to fit - and the weighted fusion is reported against it. A weighted scheme that does
      not beat the parameter-free one on dev has bought a degree of freedom it did not need, and
      that is reported as the finding it is
- [ ] Fusion weights are searched on the **dev split only**, over a declared grid, and the grid, the
      selected value and the dev curve around it are all recorded. A flat optimum and a sharp one
      mean different things about how much the choice will survive the test split
- [ ] The fused retriever also implements the unchanged `Retriever` protocol
- [ ] The dense component of the fusion is the **Phase 1 dense retriever unmodified**, reading the
      same embedding cache. Nothing here re-embeds or re-ranks the corpus

### HU-5: The control that makes the claim falsifiable

**As** the researcher,
**I want** a dense+BM25 hybrid measured in the same harness, at the same budgets, on the same splits,
**so that** "the hybrid beats dense" cannot be reported as evidence for the concept space when it is
a generic property of fusing two signals.

Phase 1 already measured the ingredients: dense and BM25 are complementary, BM25 rescues 6.8% of dev
questions dense loses, and the ceiling of a perfect combination sits near 88% Full Support against
dense's 81.2%. That headroom is available to *any* second signal. Without this control, System B
beating dense is uninterpretable.

**Acceptance criteria:**
- [ ] A dense+BM25 hybrid is measured under the **same fusion mechanism and the same dev-fitted
      procedure** as System B. Giving the control a worse fusion than the system under test would
      manufacture the comparison
- [ ] The results table reports, side by side: BM25, dense, dense+BM25 (control), conceptual-only,
      and System B (dense+conceptual)
- [ ] The report states plainly where System B lands **relative to the control**, and treats
      "System B beats dense but not dense+BM25" as the negative result it is: the concept space did
      not contribute anything a cheap lexical signal did not already give
- [ ] The control is a measurement, not a new system to be optimized. It is not tuned beyond the
      identical procedure, and it is not carried forward into Phase 4

### HU-6: The hub, declared before it is measured

**As** the researcher,
**I want** a concept-rarity damping variant written into this spec before any number is seen,
**so that** if the hub hurts retrieval the remedy is evidence, and not a repair improvised once the
results disappointed.

Phase 2's finding, restated: at K = 2,048 one atom activates on 66.7% of the pool and at K = 4,096
on 99.4%, holding 23.5% of all row-normalized mass. It passes every coherence check - its z-score is
+18.38 - and the label model, shown ten of its 12,914 units, named it by document format:
*"Wikipedia-style entity overview"*. It is the corpus's house style wearing a concept's clothes.

**Acceptance criteria:**
- [ ] A **declared variant** weights each concept in the scoring by its rarity across the pool
      (an IDF-shaped function of its support), measured with and against on the dev split
- [ ] The damping is a **retrieval parameter and leaves the dictionary untouched**. No atom is
      removed, merged or rewritten; the Phase 2 artifacts are read-only inputs
- [ ] The damping function and its parameters are declared in the phase plan before the variant is
      run, and are recorded in the result config
- [ ] The variant is reported whether it helps or not, including on the K where the hub does not
      exist (512, 1,024), where it should do approximately nothing - and if it helps *there* too,
      that is a finding about rarity weighting in general and not about the hub
- [ ] **No concept is pruned in this phase.** Pruning by coherence stays a declared Phase 5 ablation,
      as does removing the hub outright. Selecting concepts by their LLM-given names is excluded
      permanently: retrieval never reads a name, and any removal must key on a measured, regenerable
      property

### HU-7: The dev split spent accountably, the test split read once

**As** the researcher,
**I want** every decision taken against dev counted and listed, and the test split touched exactly
once at the end,
**so that** the phase does not quietly overfit 600 questions across a dozen choices and then report
the result as if it had been predicted.

This phase makes more dev-fitted choices than any other in the project: the query operator, the view
of `X`, K, the fusion scheme, its weights, and the damping variant. Each is defensible on its own.
Together they are a multiple-comparisons problem on a 600-question split, and the honest response is
to write down how many there were.

**Acceptance criteria:**
- [ ] The selection artifact lists **every decision made against dev**, with the alternatives
      considered and the margin that decided each one. The count itself is reported
- [ ] The full configuration is **frozen** before the test split is read, and the freeze is
      observable in the artifact - a recorded configuration with a timestamp, not an intention
- [ ] The test split is evaluated **once**, on the frozen configuration. If a bug forces a re-run,
      the re-run is recorded as a deviation (`3.Y_name.md`) with what changed and why, exactly as
      Phase 1 recorded its post-fix reruns
- [ ] The report states the dev-to-test gap for System B beside the same gap for the Phase 1
      baselines, which were fitted on nothing. A gap materially larger than theirs is the signature
      of dev overfitting and is reported as such
- [ ] No hyperparameter, threshold, weight or K is ever chosen, adjusted or confirmed by a number
      computed on test

### HU-8: Measured in the unchanged harness, and the winning space made readable

**As** the researcher,
**I want** System B's numbers produced by the Phase 1 harness with no modification, and the selected
space described in the report,
**so that** its figures are comparable to the baselines by construction, and so that Phase 5 can
illustrate the winning space rather than a different one.

**Acceptance criteria:**
- [ ] Every system is measured at the same four budgets (512, 1,024, 2,048, 4,096), on the same
      splits, with the same tokenizer and the same `top_k`, through `evaluate_retriever` unmodified
- [ ] The same four metrics are reported: gold recall, Full Support, context precision, and
      recall@{2,5,10}. Full Support remains the headline for a multi-hop benchmark
- [ ] **Cost is recorded per system**: mean query latency and mean units included at the largest
      budget, as Phase 1 did. A conceptual retriever that wins by costing 50x more per query is a
      different result from one that wins for free, and §73 requires the distinction
- [ ] Every result carries the config keys the harness already requires, **plus** those that decide
      what this phase measured: dictionary key, K, view of `X`, query operator, fusion scheme and
      weights, damping setting
- [ ] The **failure analysis of Phase 1 is repeated for System B** on dev at 2,048 tokens: how many
      of the 72 questions that defeated both baselines does System B recover, and how many does it
      lose that dense had. This is the number Phase 4 will be compared against, and it is the one
      that says whether one hop in concept space was ever going to be enough
- [ ] If the selected K is not 2,048, its concepts are labelled for the report only, under the
      Phase 2 rules - cached, non-reproducible by design, never read by retrieval - and the spend is
      confirmed before the run. If the selected K is 2,048, the existing labels artifact is reused
      and nothing is spent
- [ ] `docs/plans/phase_3/3.results.md` records every figure with the artifact it was read from, in
      the shape Phase 1 and Phase 2 established. Nothing is recomputed for the report

## Data contracts

### `ConceptualRetriever` (runtime object, its configuration recorded in every result)

| Field | Type | Constraints |
|-------|------|-------------|
| name | str | `conceptual`; filename-safe, as the harness requires |
| dictionary_key | str | The Phase 2 dictionary this retriever scores against |
| k | int | Dictionary size, carried for the report |
| view | str | `raw` or `row_normalized`; which `X` artifact was loaded |
| query_operator | str | `projection` or `sparse_coding` |
| query_alpha | float \| null | Coding penalty; `null` for projection |
| query_top_m | int \| null | Truncation of the query concept vector; `null` if none |
| damping | str | `none` or the declared rarity function |

**Invariants:**
- Implements `Retriever` unchanged; the harness cannot distinguish it from dense or BM25.
- Reads `X`, the atoms and the pool. It never reads a label, a gold annotation or a split label.
- Deterministic including ties; ties broken by unit id.

### `FusedRetriever` (runtime object)

| Field | Type | Constraints |
|-------|------|-------------|
| name | str | `hybrid-conceptual` (System B) or `hybrid-bm25` (the HU-5 control) |
| components | list[str] | The retriever names being fused, in a fixed order |
| scheme | str | `rrf` or the declared weighted scheme |
| normalization | str | How each signal is put on a common scale; `none` for rank-based |
| weights | dict \| null | Component name -> weight; `null` for parameter-free schemes |
| fitted_on | str | Always `dev`, recorded so the artifact says it rather than the reader assuming it |

**Invariants:**
- Its dense component is the Phase 1 dense retriever, reading the unmodified embedding cache.
- The same scheme, normalization and fitting procedure are used for System B and for the control.
- Deterministic including ties.

### `SelectionReport` (JSON, one per phase, versioned)

| Field | Type | Constraints |
|-------|------|-------------|
| selected_k | int | The chosen dictionary size |
| selected_dictionary_key | str | Its Phase 2 artifact key |
| selection_metric | str | The metric that decided it |
| selection_budget | int | The budget it was read at; separate from the metric so neither has to be parsed back out of the other |
| per_k | dict | K -> dev metrics, hub share, hub mass share, thin-concept count |
| decisions | list | One entry per dev-fitted choice: what, the alternatives, the margin |
| n_dev_decisions | int | The count of the above, reported rather than left to be counted |
| tie_break | str \| null | The structural criterion applied, if the margin was within noise |
| frozen_at | str | ISO-8601 timestamp of the configuration freeze, before test is read |
| config | dict | The complete frozen configuration of System B |
| seed / code_version | int / str | Reproducibility, as every artifact of this project carries |

**Invariants:**
- Every number in it is computed on dev or on the corpus. **No field is ever derived from test.**
- `frozen_at` precedes the `created_at` of every test-split result of this phase.
- Written atomically and never overwritten, following the Phase 1 and Phase 2 artifact pattern.

### `RunResult.config`, extended

The harness already requires `model`, `revision`, `unit_set_hash`, `seed`, `tokenizer`,
`code_version` and `top_k`. Every result of this phase additionally carries `dictionary_key`, `k`,
`view`, `query_operator`, `fusion_scheme` and `damping`, so that a result file states on its own
which of the four spaces produced it and under which decisions.

`query_operator` here is the **arm**, not the primitive: `projection_top16`, `projection_full` or
`sparse_coding`, with `query_alpha` and `query_top_m` beside it. The `ConceptualRetriever` contract
above records the primitive, which is what the object does; a result has to record the alternative,
which is what was chosen. Recording `projection` in a result would merge two of the three arms into
one row nobody can read back, and the arms are one decision with three alternatives (plan, D4).

## Restrictions

- **Platform**: Windows on ARM64, CPU only. Nothing here re-embeds the corpus and nothing re-induces
  a dictionary; both are read from cache. No new dependency is expected - `scipy.sparse`,
  `scikit-learn` and `bm25s` are already installed - and any that turns out to be needed goes
  through the ASK FIRST rule before it is added.
- **The dev sweep must be cheap, and that constrains the design.** A dense query embedding costs
  ~30.7 ms on this machine, so 600 dev questions cost ~18 s per pass; a sweep over four K values,
  two query operators, two views and a fusion weight grid re-embeds the same 600 strings tens of
  thousands of times if nothing is cached. **Dev and test question embeddings are computed once and
  cached on disk**, keyed like every other artifact, and the sweep reads that cache. Without this
  the sweep costs hours for no reason.
- **Phase 1 and Phase 2 artifacts are frozen inputs.** The pool, the embedding cache, the four
  dictionaries, the eight matrices, the diagnostics and the labels are read, never rewritten and
  never invalidated. Recomputing any of them costs hours of CPU that this phase has no reason to
  spend.
- **Determinism**: every stochastic step takes an explicit seed and the seed travels in the config.
  The only non-reproducible thing this phase may produce is a labelling run, and it sits outside
  every metric.
- **Artifact integrity**: everything written follows the rule Phase 1's audit established - verify
  on load, do not merely record. `.npz` and JSON only; no `pickle`, no `joblib`, no
  `allow_pickle=True`.
- **Secrets**: unchanged. `ANTHROPIC_API_KEY` is read from `.env` by the labelling stage only, and
  never printed, logged or written into an artifact.
- **ASCII in `print()`, logging and Python strings.** Markdown may use Unicode.

## Anti-goals (what this phase does NOT do)

- **NO expansion.** No diffusion over `X`, no iteration, no propagation chunk -> concept -> chunk, no
  restart on the query's concepts. System B retrieves in one hop. All of that is Phase 4, and the
  temptation to "just try one round" here would contaminate the comparison Phase 4 exists to make.
- **NO LLM anywhere in the retrieval path.** Not for query rewriting, not for concept extraction,
  not for reranking, not for filtering concepts by their names. The labelling stage stays where
  Phase 2 put it: interpretability and reporting, off the critical path.
- **NO pruning of concepts.** Not by coherence, not by support, not by name. Pruning is a declared
  Phase 5 ablation; this phase damps by a declared rarity function and removes nothing.
- **NO re-induction and no new K.** The sweep is the four spaces Phase 2 produced. Inducing a fifth
  because the four disappoint would be choosing K against the metric that is meant to judge it.
- **NO change to the embedding model or the indexing unit.** Both invalidate the Phase 1 cache and
  make every recorded metric incomparable.
- **NO tuning against test, in any form.** Not a threshold, not a weight, not a K, not a "quick look
  to check nothing is broken". Test is read once, on a frozen configuration.
- **NO answer generation and no answer-quality metrics.** No faithfulness, no completeness, no LLM
  judge. The primary metric stays supporting-fact recall within the budget, which is annotated and
  objective.
- **NO second benchmark.** MuSiQue cross-validation is Phase 5.
- **NO ablation catalogue.** The variants of this phase are the ones written above; the systematic
  ablations - no fusion, no non-negativity, varying K, pruning - belong to Phase 5.
- **NO comparison at fixed K instead of fixed budget.** Every system is measured at equal tokens
  sent, as the founding decision requires.
- **NO hierarchy signal.** §56's fourth signal is Phase 6 material and the benchmark cannot exercise
  it: Wikipedia offers only article -> paragraph -> sentence.

## Existing code context

- `src/concept_embeddings_rag/retrieval/base.py` - the `Retriever` protocol every system of this
  phase implements. It is not to be modified; if it cannot express a conceptual retriever, that is a
  finding, not a licence.
- `src/concept_embeddings_rag/retrieval/dense.py` - the dense component of System B and the model
  for how a retriever in this project behaves: `argpartition` for the top-k, ties broken by unit id.
- `src/concept_embeddings_rag/retrieval/bm25.py` - the HU-5 control's lexical component, unchanged.
- `src/concept_embeddings_rag/evaluation/harness.py` - `evaluate_retriever` and `RunResult`, which
  already validates provenance and writes append-only. This phase adds config keys to a result, not
  code to the harness.
- `src/concept_embeddings_rag/evaluation/budget.py` - budget filling, identical for every system.
- `src/concept_embeddings_rag/concepts/coding.py` - `load_matrix`, the two views, and
  `WEIGHT_SEMANTICS`, which is the authority on what a weight of `X` means and therefore on what
  scoring over it is allowed to assume.
- `src/concept_embeddings_rag/concepts/dictionary.py` - `load_dictionary` and `encode`, the two
  routes a query has into the space (atoms for the projection, `encode` for the sparse coding).
- `src/concept_embeddings_rag/concepts/diagnostics.py` - `load_diagnostics`, the source of the hub
  share and the thin-concept counts HU-3 reports beside recall. Read, never recomputed.
- `src/concept_embeddings_rag/config.py` - every constant that decides what an experiment measures.
  The fusion grid, the damping parameters, the query truncation and the selected K belong here.
- `src/concept_embeddings_rag/cli.py` - the staged pipeline. This phase adds a dev-selection stage
  before `evaluate`, refusing to run when its input is missing and naming the stage to run first.
- `docs/plans/phase_1/1.results.md` - the baselines, the budgets and the failure analysis whose 72
  questions HU-8 revisits.
- `docs/plans/phase_2/2.results.md` - the four spaces, the hub, the thin-concept counts, and the two
  instructions this spec was required to carry.
