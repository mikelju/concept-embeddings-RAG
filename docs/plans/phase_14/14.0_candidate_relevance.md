# Phase 14: ordering the hop's candidates by their similarity to the question — implementation plan

> Functional spec: [`14.spec.md`](14.spec.md), approved 2026-09-28 and frozen. This plan is
> **approved by the author on 2026-09-28**. It decides HOW; a change to any spec rule is a written
> deviation `14.Y_*.md`.
>
> Simplification rule: one question, **seven steps**, no `14.tasks.md`, reuse before
> generalization. Everything runs on the laptop; no money is spent (R1). Code for a step past a
> stop state is not written: a stage that can never run breaks the simplification rule (the
> Phase 12 and 13 precedent).

## Objective

> Does ordering the Entity Hop's candidates by a score that mixes their rarity overlap with P1
> and their BGE similarity to the question retrieve the full multi-hop evidence more often than
> P10-C at FullWiki scale?

Primary endpoint: Full Support @2,048 on `test-11` (5,000 HotpotQA train `hard` questions), P14
against frozen P10-C, one two-sided exact McNemar test, α = 0.05 (D6). Preregistered secondary:
P14 against P10-B, same test; it cannot change the label (D7). Terminal states: `DEV_STOP`,
`CANDIDATE_RELEVANCE_SUPPORTED`, `CANDIDATE_RELEVANCE_NOT_SUPPORTED`,
`CANDIDATE_RELEVANCE_REGRESSION`.

## Author stop points

1. **A D1 integrity miss (S3)**: some dev question's recomputed `sim(P1)` differs from Phase 10's
   recorded Dense score for P1 by more than 1e-5.
2. **A D3 reproduction miss (S3)** or **`DEV_STOP` (S4)**.
3. **Before the held-out pass (S5).** It opens `test-11`. It runs once, after `fit.json` is
   committed, and only on explicit authorization.
4. Two attempts without progress.

## Implementation steps

  third-slot stage (it requires the stage to be named `seeded-hop`); `relevance-hop` names the
  component in the dev lists and the fit.
  - Add the Phase 14 constants to `config.py`:
    - `PHASE_14_DIR`, the set names (reusing the Phase 11 names);
    - `PHASE_14_ALPHAS = (0.0, 0.25, 0.5, 0.75, 1.0)`, the grid step, the P10-C point

  - Add a new `evaluation/phase14.py`, pure functions over plain arrays:

    - `alpha_key(α)`, `grid_points()` (5 `α` × `phase12.weight_grid()` = 330),

    - `integrity_verdict(recomputed, recorded, tolerance)` (D1);
    - `dense_rank_class(rank)` (1-10, 11-100, beyond 100) and `coverage_changes(...)` for D8;
    - `label(wins, losses, p)` (D6); the secondary comparison takes no part in it.
  - → `config.py`, `evaluation/phase14.py` (new).
  - Test: `tests/evaluation/test_phase14.py`:
    - `min_max` on a constant term gives 0; `mixed_scores` at `α = 1` equals `ŝ`;
    - `rank_cut` breaks ties by unit id and keeps the tied rows at the cut exactly as a full sort
      would;

    - the integrity verdict at the tolerance and just past it;
    - the label on constructed counts (both directions, p at and past 0.05).

## Technical notes

- **Reuse.** Inputs: `_p13_phase10_dev_lists`, `_p11_dev_inputs`, `_p11_entity_index`,
  `_p12_dev_question_vector`, `EmbeddingCache.load`, `_phase_9_inputs`, `phase11.load_test_11`.
  Hop and fusion: `node_weights`, `arm_columns`, `node_hop_columnwise`, `fuse_lists`,
  `QueryTripleFusedRetriever`. Measurement: `_p10_replay_records`, `phase10.supported`,
  `gold_recall_sum`, `phase9.measure_system`, `write_run`, `latency_summary`,
  `exact_two_sided_p`, `budget.fill_context`. Checks: `_p10_fit_is_committed`, the write-once
  helpers, `phase13.reproduction_verdict`, `phase13.screen_population`, `phase12.weight_grid`.
  No Phase 9-13 function is modified.
- **Why the identity holds.** At `α = 0` the stage does not compute a new score: it calls
  `node_hop_columnwise`, the function behind Phase 10's lists, and returns its output. S2 tests
  it; D3 checks it on all 7,405 dev questions. The `α > 0` path recomputes the same rarity sums
  in the same node order, so its `r(c)` equals Phase 9's.
- **Arithmetic.** `sim` is taken in float32 from the gathered rows (D1); `r̂`, `ŝ` and `score_α`
  are computed in float64 from those values. The same code runs on dev and on `test-11`.
- **The full candidate set.** `C(q)` is every positive row outside `read(q)`, before the depth
  cut: up to 395,922 rows for one dev question. Gathering them is `|C(q)| × 384` float32 reads,
  about 0.6 GB at the maximum, freed per question.
- **P1's score in the Phase 10 lists** is Dense's score for its first unit; D1 compares against
  it directly. P1 itself is in `read(q)`, so it is never a candidate.
- **A constant term** (all of `C(q)` sharing the same rarity, or `|C(q)| = 1`) is 0 for everyone,
  per D2; no extra guard is added.
- **D8 coverage.** "Coverage changed" means the gold paragraph enters the 2,048-token context of
  one system and not the other, as `fill_context` packs the fused ranking. Dense rank comes from
  the Phase 10 Dense list (depth 100); a gold paragraph absent from it is "beyond 100".
- **Latency (D9).** `measure_system` times the whole `retrieve`; the stage times its own `sim`
  work per question; the report shows `retrieve` without it, the `sim` time and their sum, so D9
  stays comparable with Phase 10.
- **Time (projection, not measurement).**
  - S3: loading the 8.04 GB passage NPZ and the index takes a few minutes; the lists take about
    20-45 min (the spec's figure: 205 M candidate pairs, Phase 13's 741 s for four hop lists).
  - S4: Phase 13 fitted 264 points in 956 s; 330 points take about 20 min.
  - S5: four systems × 5,000 questions on the laptop, about 2-3 h.
- **Memory (projection).** About 16 GB peak of 31.6 GB: the passage vectors (8.04 GB), the
  entity index with its CSC copy, and one question's gathered rows. BM25 is not built for S3 and
  S4. Stages never run at the same time.
- **No new dependencies.**
