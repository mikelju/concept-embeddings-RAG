## Decisions fixed before any measurement

The spec's ten decisions are closed and are not restated here. These are the **implementation**
decisions this plan makes, each one settled now so it is not improvised mid-run.

### D1 — `EMBEDDING_MODEL` is **not** swapped; Phase 8 declares its own constants

The tempting reading of the spec is "point `EMBEDDING_MODEL` at Qwen3". **That is rejected.**
`cer evaluate`, `cer cheap-eval`, `replacement_inputs.py` and `_cheap_inputs` all default to
`SentenceTransformerBackend()`, which reads `config.EMBEDDING_MODEL`; repointing it would make every
inherited stage look for a corpus cache that does not exist and die — directly against **R4** ("the
existing suite must still pass unchanged").

So `EMBEDDING_MODEL` / `EMBEDDING_REVISION` / `EMBEDDING_DIM` keep describing the Phase 1–7 dense
model, and Phase 8 adds `PHASE_8_DENSE_MODEL`, `PHASE_8_DENSE_REVISION`, `PHASE_8_DENSE_DIM`. The
Phase 8 stages construct their backend explicitly. Nothing else in the project changes model by
accident, which is the property R4 is protecting.

### D2 — The budget ruler is decoupled **semantically, at identical values**

`TOKENIZER_ID = EMBEDDING_MODEL` becomes two literals:

```text
BUDGET_TOKENIZER_ID       = "BAAI/bge-small-en-v1.5"
BUDGET_TOKENIZER_REVISION = "5c38ec7c405ec4b44b94cc5a9bb96e735b38267a"
TOKENIZER_ID              = BUDGET_TOKENIZER_ID      # the name four provenance sites already record
```

`TokenCounter`'s defaults become `(BUDGET_TOKENIZER_ID, BUDGET_TOKENIZER_REVISION)` instead of
`(TOKENIZER_ID, EMBEDDING_REVISION)`. Combined with D1, **every value stays exactly what it is
today** — this is a change of meaning, not of number, so no inherited artifact moves and no
inherited test breaks. A data-dependent test then pins it: the budget tokenizer resolves to
`bge-small` at the Phase 1–7 revision *independently of* the Phase 8 dense model.

`data/token_counts.json` is never rewritten: the Phase 8 embedding stage does not call
`TokenCounter` at all (D5), and `cer embed` is not run again.

### D3 — The query-prompt hook: one optional attribute, applied to queries only

`SentenceTransformerBackend` gains `query_prompt: str = ""`.

- On load, if `query_prompt` is non-empty: read `model.prompts["query"]` and assert **exact** string
  equality against it. On any mismatch — including a missing key — raise **before a single vector is
  produced**. Encoding then goes through `prompt_name="query"`; what is recorded and what enters the
  cache key is the **resolved** string read from the model, so provenance records what was used, not
  what was expected.
- `embed_units` **refuses** a backend whose `query_prompt` is non-empty. Documents are unprefixed
  (the pinned revision stores `"document": ""`), and the guard makes that structural instead of a
  convention someone can forget. Two backend instances are constructed in the stage: one for the
  corpus, one for the questions.

### D4 — The prompt enters `question_cache_key` **only when non-empty**

`question_cache_key` gains a trailing `query_prompt: str = ""` parameter, appended to the hashed
payload **only when it is non-empty**:

```text
prompt == ""   ->  "question|{model}|{revision}|{question_set}|{split}|{normalized}"    (unchanged)
prompt != ""   ->  "question|{model}|{revision}|{question_set}|{split}|{normalized}|{prompt}"
```

Appending it unconditionally would change every Phase 1–7 question key and orphan every existing
question cache — an invalidation by arithmetic rather than by deletion, and just as much a breach of
R4. The corpus key is **not** touched: a query-only parameter has no business invalidating 19,366
paragraph embeddings (Decision 5).

**The sidecar carries the prompt and is verified against it.** When `query_prompt` is non-empty, the
resolved string is written into the question sidecar metadata and `_verify_question_sidecar` adds it
to the fields it checks, so a cache whose sidecar disagrees with the prompt in hand is refused rather
than used. A sidecar is only worth writing if something reads it back and disagrees when it must —
that was the whole content of the Phase 1 audit, and a silently different prompt would change every
query vector while leaving provenance looking correct.

When `query_prompt` is empty the behaviour is **exactly** what it is today: no field written, no
field checked, keys byte-identical. Phase 1–7 question caches keep loading and verifying unchanged.

### D5 — `cer strong-embed`: one stage, two modes, with the dev gate between them

One CLI stage, run on the rented RTX 4090, in **two modes separated by the dev gate**. The test
questions are not encoded — not merely not measured — until `Strong Dense` has proved itself on dev.

**Mode 1, `cer strong-embed`** (the initial pass):

1. run the provenance checks that need no measurement (D11) — **before the model is loaded**;
2. load the frozen pool and check it against the manifest;
3. embed the 19,366 units with the corpus backend (no prompt) → new corpus cache key;
4. embed the **600 dev** questions with the query backend (prompt) → new dev question cache key;
5. assert `vectors.shape[1] == config.PHASE_8_DENSE_DIM == 1024` for both blocks, and **abort** on
   any mismatch before writing anything;
6. write `data/phase8/embedding.json`, the `Phase8Embedding` contract.

**The gate then runs**: `cer strong-dense` (D6, D10). Nothing about the test split has been touched.

**Mode 2, `cer strong-embed --test`** (only if the gate passed):

- refuses without a digest-valid `dev.json` whose stop-rule `verdict` is `pass`;
- embeds the **1,400 test** questions → new test question cache key, same dimension assertion;
- writes `data/phase8/embedding-test.json`, which carries the test question cache key, its timings
  and cost, and **both** `embedding_digest` and `dev_digest` — so the artifact itself records that
  the gate authorized it.

> **Why a second file instead of appending to `embedding.json`.** `dev.json` anchors the chain on
> `embedding.json`'s digest. Re-digesting that file to append the test key would break the link, and
> preserving a stale digest inside a rewritten file is exactly the kind of quiet provenance drift
> the project refuses. So `embedding.json` is written once and never rewritten; the test encoding
> gets its own small artifact that points back at it. Same stage, same session, immutable chain.

Run on the rented RTX 4090, **in the same session if it is still open** — mode 2 is minutes of work
on 1,400 strings. If the session has closed, it is a short second rental, and that is a cost
question, not a scientific one. The hardware actually used is recorded in each artifact
independently, so the two modes may honestly report different machines.

The stage **never** writes `data/token_counts.json` and never touches an existing cache file.

`weights_sha256`: SHA-256 over the bytes of `model.safetensors` in the snapshot directory
`huggingface_hub` actually served, computed in the stage and recorded. `max_seq_length`: read from
the loaded `SentenceTransformer`, never copied from the card. Both are recorded whatever they turn
out to be.

### D6 — `cer strong-dense` and `cer strong-dense --test`: one runner, two paths

Mirrors the `cheap-eval` / `cheap-eval --test` shape Phase 7 proved, in a new module
`evaluation/strong_dense.py`. `evaluation/cheap_extraction.py` is **read for its wiring and not
edited** — it verifies Phase 7 invariants and belongs to a closed phase.

**Dev path** (`cer strong-dense`):

- build `DenseRetriever` from the Phase 8 corpus cache + a `CachedQueryBackend` over the dev question
  cache — **no model is loaded**, so this path runs on the ARM64 laptop;
- `BM25Retriever(units)`, unchanged;
- load the Phase 7 GLiNER index with `load_node_index(data/phase7/gliner/,
  extraction_digest=…, expected_unit_ids=…)` and **refuse** unless `index.digest` equals the pinned
  `PHASE_8_GLINER_INDEX_DIGEST`; nothing is written into `data/phase7/`;
- `check_dev_only(questions)`;
- `fit_fusion_weight([dense, bm25])` and `fit_fusion_weight([dense, EntityHopStage(...)])`, both with
  the inherited objective (Gold Recall @2,048), `FUSION_WEIGHT_GRID`, RRF on the same questions;
- `evaluate_retriever` for all three systems at all four budgets;
- diagnostics (D7);
- write `data/phase8/dev.json`, refusing to overwrite an existing one.

**Test path** (`cer strong-dense --test`): refuses without a digest-valid `dev.json`; refuses if the
stop rule fired; refuses a non-test split; refits nothing — it reads each hybrid's scheme and weight
out of `dev.json`, measures the three systems once, and writes `data/phase8/test.json`.

### D7 — Diagnostics, all from machinery that already exists

- Hop behaviour: `RecordingHybrid` + `records_of` + `fragmentation`, exactly as
  `evaluate_candidate` uses them — `P(q)` mean / median / share at zero, `p1`s with no entity node,
  introduced context units at `SELECTION_BUDGET`.
- **`p1` change**: rebuild the BGE-small `DenseRetriever` from its *existing* corpus and question
  caches and compare top-1 per question against Strong Dense's. **No model is loaded and nothing is
  re-embedded** — both caches are on disk. Reported on dev and on test; it is descriptive, fits
  nothing.

### D8 — Artifacts and the digest chain: Phase 7's shape, no more

```text
data/phase8/
├── embedding.json        # Phase8Embedding: model, digests, corpus + dev keys, cost, projection
├── embedding-test.json   # the gated test-question encoding: test key, cost, both parent digests
├── dev.json              # Phase8Dev:  two fits + three systems + diagnostics + stop-rule verdict
├── test.json             # Phase8Test: three systems once + surviving-gain arithmetic
└── run-*.json            # the harness RunResult files, one per system per split
```

Chain, using `digest_of_payload` from `evaluation/selection.py`:

```text
embedding.json.digest       -> dev.json.embedding_digest
GLiNER index.digest         -> dev.json.node_index_digest
dev.json.digest             -> embedding-test.json.dev_digest     (the gate authorizing the encoding)
embedding.json.digest       -> embedding-test.json.embedding_digest
dev.json.digest             -> test.json.dev_digest
embedding-test.json.digest  -> test.json.embedding_test_digest
```

**Every system, in both splits, records `run_file` and `run_digest`** — the harness `RunResult` file
it was measured into, and `digest_of_payload(asdict(result))` over that result — so each of the three
figures is individually traceable to the run that produced it, not merely to the artifact that
summarizes all three. This is the shape Phase 7 used for its single system, applied per system here.

A test figure therefore cannot be detached from the embedding configuration, the entity index, the
dev fit that authorized it, or its own run file. No freeze/supersede protocol, no decision state
machine, no McNemar.

**Costs are recorded as three separate things, because they are three different numbers.**
`embedding.json` (and `embedding-test.json` for its own pass) records:

```text
hourly_rate_usd     the rented machine's advertised hourly rate
embedding_seconds   wall clock of the encoding pass itself
embedding_usd       hourly_rate_usd * embedding_seconds / 3600, attributable to this pass
```

The **total RunPod session charge** — which includes image pull, model download, upload, idle time
and anything else the session did — is a different quantity, known only from Billing and usually
after the fact. It is reported in `8.results.md` beside the attributable figure, clearly labelled as
the session total. **Learning it later never requires rewriting `embedding.json`**, which is exactly
why the two are not conflated into one field.

### D9 — Where each pass runs

| Pass | Machine | Why |
|---|---|---|
| `strong-embed` (corpus + dev) | Rented Linux x86_64 RTX 4090 (RunPod path, Phase 7) | The only steps that load the model. Upload `pool.json`; download the `.npz` + sidecars + `embedding.json` (~80 MB at 19,366 x 1024 float32) |
| `strong-embed --test` (gated) | The same rented session if still open, else a short second rental | 1,400 strings, minutes of work — but only after the dev gate passes |
| `strong-dense`, `strong-dense --test` | The ARM64 laptop | Reads cached vectors only; `CachedQueryBackend` means no model load |

The order is therefore: **embed corpus + dev → run the dev gate → only then encode test**. Hardware
and cost are recorded per pass (D8), so the two encoding passes report themselves independently and
honestly even if they ran on different machines.

### D10 — The stop rule is code, not intention, and it is counted in whole questions

The comparison is made **in whole questions**, never on floats:

```text
inherited baseline   487 / 600   (dense dev Full Support @2,048 = 0.8116666666666666)
Strong Dense passes  >= 488 / 600
```

487 is a tie, and a tie is not "substantially stronger" — the rule passes only on a strict
improvement, which in counted terms means at least one more supported question. Comparing rounded
shares instead would make the verdict depend on float formatting, the same reasoning that made
Phase 7 apply its retention bar as `517` rather than as `0.8617`.

`dev.json` records the three of them together:

```text
stop_rule: {count, n_questions, share, baseline_count, baseline_share, required_count, verdict}
```

`verdict` is `pass` or `stop`. The dev stage writes it whatever it says; `strong-embed --test` and
`strong-dense --test` both refuse to run unless it is `pass`. **A `stop` verdict means the held-out
split is neither measured nor encoded**, and the phase closes on its dev figures. No other encoder is
tried inside Phase 8.

### D11 — Provenance checks run before the model load, not only in the write-up

S6 is where the targeted review is **documented**; it is not where the checks first happen. Every
check that needs no measurement runs **inside `strong-embed`, before the first model load and before
a single vector exists**:

- the configured revision is a 40-character commit SHA, never a branch name;
- `resolved_revision` from the Hub equals the pinned revision;
- the snapshot serves `model.safetensors`, and its SHA-256 is computed over those bytes;
- `trust_remote_code` is not passed anywhere in the call path.

A provenance check that only happens while writing the report is a check that cannot stop a bad run.
These abort the stage. What S6 adds is the written review and the statement that the surface was
examined — the spec's single `/8-auditar` trigger, closed on paper after it was already closed in
code. The resolved `max_seq_length` and the query-prompt equality assertion (D3) are read at load
time, the earliest point at which they exist.

## Tests

The spec's list, and nothing invented beyond it:

1. the new embedding configuration produces **distinct corpus and question cache keys** resolving to
   no existing artifact, and the pinned revision is checked against the resolved one;
2. the loaded GLiNER node index matches its pinned digest and the frozen pool's unit ids, and the
   runner refuses any other index;
3. the runner refuses test questions during fitting, and refuses a node index built over another
   pool;
4. **the query prompt**: the equality check aborts **before any embedding** on a mismatch; documents
   are encoded **without** the prompt and queries **with** it; it enters `question_cache_key` and
   **not** the corpus cache key; the string recorded is the exact resolved one; the sidecar carries
   it and `_verify_question_sidecar` refuses a cache whose sidecar disagrees — while an empty prompt
   leaves keys, sidecars and verification byte-identical to Phases 1–7;
5. **the budget ruler is pinned**: it resolves to `BAAI/bge-small-en-v1.5` at the Phase 1–7 revision
   independently of the Phase 8 dense model, so changing Dense cannot move the context budget or
   rewrite `data/token_counts.json`;
6. **the encoded width**: a vector block whose dimension is not `PHASE_8_DENSE_DIM` aborts
   `strong-embed` before a cache or artifact is written;
7. **the gate ordering**: `strong-embed --test` and `strong-dense --test` both refuse a `stop`
   verdict and both refuse a `dev.json` that fails its digest;
8. the existing suite, `ruff check .` and `mypy src` still pass unchanged.

No test loads a model or reaches the network: the backend is stubbed, exactly as the existing suite
already does.

## Notes and technical decisions

**Latency is comparable only if measured the same way.** Phase 6's `0.891 / 1.508 / 10.447 ms/query`
were measured with a `CachedQueryBackend` — they are **retrieval** latency and exclude query
encoding. Phase 8 measures the same way, so the comparison holds; what moves is the dot product,
384 → 1024 dimensions. `8.results.md` must say "retrieval latency, query encoding excluded, both
rows" rather than let a reader take it for end-to-end cost. Query *encoding* under a 0.6B model is a
genuinely different cost and is reported separately, from `embedding.json`.

**Why a new stage rather than reusing `cer embed`.** `cmd_embed` unconditionally rewrites
`data/token_counts.json` after embedding. Under D1+D2 that rewrite would be byte-identical, but
"byte-identical" is a property we would be relying on rather than enforcing, and R1 names this the
largest integrity risk in the phase. A stage that never calls `TokenCounter` cannot rewrite the file
at all.

**Dimension is validated in the stage, not in the retriever.** Nothing in the project checks
embedding width today: `EMBEDDING_DIM` is only a `SentenceTransformerBackend` default, and
`DenseRetriever` takes whatever vectors it is given — which is why 1024-dim vectors need no change to
retrieval or fusion, and why `DenseRetriever` is **not** touched. But a silent width change is a real
failure mode for this model specifically, since Qwen3-Embedding supports MRL truncation and the spec
pins full 1024 dimensions with no truncation. So `strong-embed` asserts
`vectors.shape[1] == config.PHASE_8_DENSE_DIM == 1024` for every block it encodes and aborts on
mismatch, before writing a cache or an artifact. The guard sits where the vectors are produced; the
recorded `dim` remains provenance.

**The two fits are independent.** `Strong Dense + BM25` and `Strong Dense + Entity Hop` each get
their own `fit_fusion_weight` call over the same grid with the same objective, as Phase 3's D9
requires — giving either one a shorter grid or a weaker reference is the easiest way to manufacture
a headline.

**What a weak result does not license.** If the gain shrinks or disappears, that is the finding. No
canonicalization, no relations, no extra hops or seeds, no query-aware filtering, no reranker, no
second extractor, no model swap. The phase closes on the number it measured.

**GLiNER, not spaCy.** Settled by a rule frozen before any Phase 7 candidate ran. Re-opening it
belongs to the deferred scale-and-representation experiment, not here.

### Post-closure note — deviation 8.1

Deviation 8.1 did not reopen this phase or its failed gate. It tested only whether the C19 Dense
ordering that triggered the stop was sensitive to retrieval-corpus scale. On the same 600 dev
questions, BGE/Qwen Full Support @2,048 measured **487/446 at C19, 463/420 at C100, 440/393 at C250
and 423/366 at C500**. The pre-declared classifier returned **`STABLE_RANKING` (rule A)**.

Accordingly, BGE-small is the task-validated primary Dense candidate carried into Phase 9; the
Phase 9 spec decides whether Qwen remains as an external-comparability control. This does not turn
Phase 8 into a success and does not answer its stronger-Dense Entity-Hop question.

Full record: [`8.1_results.md`](8.1_results.md).
