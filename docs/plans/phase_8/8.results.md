## Result

**Phase 8 stopped at the pre-declared dev gate because `Qwen/Qwen3-Embedding-0.6B` did not
outperform the inherited BGE-small Dense baseline. The held-out split was neither encoded nor
measured.**

The spec fixed the rule before any Phase 8 number existed (Decision 4, plan D10): Strong Dense alone
must support **strictly more** dev questions than the inherited Dense reading, because 487 of 600 is
a tie and a tie is not "substantially stronger". From `dev.json` → `stop_rule`:

```text
baseline_count   487        (inherited BGE-small Dense dev Full Support @2,048 = 0.8116666666666666)
required_count   488
count            446        (share 0.7433333333333333)
metric           full_support at budget 2048
verdict          stop
```

The premise of the phase failed: the model chosen a priori as "substantially stronger" is, on this
corpus, substantially weaker. Per the settled rule, **no second encoder was tried inside Phase 8** —
swapping models after seeing dev would be choosing a model on dev performance, the leaderboard the
master plan forbids and the error Phase 7's record exists to prevent.

### Dev Full Support @2,048, the four numbers that decide it

| System | Questions | Share | vs Qwen Dense |
|---|---:|---:|---:|
| **Inherited BGE-small Dense** | 487 / 600 | 0.8117 | — |
| **Qwen Strong Dense** | 446 / 600 | 0.7433 | — |
| **Qwen + BM25** | 489 / 600 | 0.8150 | +43 |
| **Qwen + Entity Hop** | 494 / 600 | 0.8233 | +48 |
| Gate | **488 / 600** required | | |
| Verdict | **STOP** | | |

Expressed as differences, in whole questions and in percentage points:

```text
Qwen Dense vs BGE-small Dense       -41 questions   -6.83 pp
BM25 over Qwen Dense                +43 questions   +7.17 pp
Entity Hop over Qwen Dense          +48 questions   +8.00 pp
Entity Hop vs BM25, under Qwen       +5 questions   +0.83 pp   descriptive only
```

The last line is **not** a Phase 8 conclusion. It is a dev observation under a Dense model that
failed the phase's prerequisite, and it is reported because the run produced it, not because it
settles anything.

## Interpretation

**Phase 8 does not establish whether Entity Hop remains complementary to a substantially stronger
Dense retriever, because the selected Dense retriever failed the phase's prerequisite: it was not
stronger on the frozen 19,366-paragraph corpus.**

The spec named three possible outcomes for the held-out reading — Entity Hop remains strongly
positive, the effect shrinks but survives, or the effect disappears. **Phase 8 reaches none of them.**
The question they answer was never opened, because the condition they are conditional on was never
met. Writing "Entity Hop survived" or "Entity Hop disappeared" here would be a claim about an
experiment that did not run.

What can be said, and only on dev:

> On dev, both BM25 and Entity Hop substantially recover Qwen's Dense failures, with Entity Hop
> producing 5 more full-support questions than BM25. These are descriptive dev observations only.

Both second signals lift a weak Dense back to roughly the level of the inherited BGE-small Dense
baseline — 489 and 494 against 487 — without either hybrid approaching the inherited BGE-small
hybrids, which both stood at 518 of 600. That is consistent with the structural signal doing what it
did in Phase 6, on a worse seed, and it is consistent with other explanations too. Dev evidence under
a failed premise does not adjudicate between them.

## Why this does not imply Qwen is generally worse

**The result is bounded to the frozen 19,366-paragraph HotpotQA distractor pool. It does not
establish that BGE-small is generally superior to `Qwen3-Embedding-0.6B`, nor that the same ordering
will hold as the retrieval corpus approaches FullWiki scale.**

Three reasons to hold the conclusion tightly:

- **The pool is a distractor pool, not a search space.** Each question's 19,366-paragraph haystack is
  built from HotpotQA's own distractors: paragraphs selected, by construction, to be lexically and
  semantically confusable with the gold ones. A corpus of near-misses is an unusual environment, and
  nothing says a model's ranking on it predicts its ranking on an open corpus.
- **`p1` changed on 22.67% of questions**, so the two models genuinely disagree about what is most
  relevant. This is a difference in behaviour on this distribution, measured; it is not a measurement
  of general retrieval quality.
- **The published scores are not comparable and were never treated as evidence** (gap G1). Qwen3's
  MTEB v2-era figures cannot be read against the older 56-task BGE averages. They ranked plausibility
  before the choice; the only number this project trusts is its own measured Full Support, and that
  number is bounded to this corpus.

**This limitation is exactly what deviation 8.1 is opened to probe.** The phase measured one model on
one corpus of one shape; whether the ordering is a property of the models or of the corpus is a
different question, and it is now an open one rather than an assumed one.

## Declared gaps

- **G1 — Published model scores are not comparable to one another.** Stated in the spec, and it
  survived contact with the experiment: Qwen3's higher published figures did not predict its
  behaviour here.
- **G2 — No prior measured embedding cost existed for any candidate on this corpus.** Now measured
  for one: 247.062 paragraphs/s on an RTX 4090.
- **G3 — Truncation is moot for this model.** `max_seq_length 32768` resolved from the loaded model,
  far above the pool's longest paragraph, so **no paragraph was truncated** and no part of any
  difference is attributable to Dense having read less than the Entity Hop did. Verified, not assumed.
- **G4 — Phase 5's Claude extraction wall-clock time was never recorded.** Inherited, still open,
  irrelevant here.
- **G5 — NER quality is still unmeasured.** Every Entity Hop figure is conditional on whatever GLiNER
  read.
- **G6 — One Dense model, one corpus.** Cannot generalize to other strong encoders, other multi-hop
  datasets, or FullWiki scale.
- **G7 — The exact RunPod session charge could not be recovered from Billing.** The ~0.40 USD total is
  an approximation and is labelled as one everywhere it appears. The attributable figure in
  `embedding.json` is exact; the session total is not.
- **G8 — The hardware block reports the RunPod host, not the container.** `cpu_count 96`,
  `torch_threads 48` and `ram_bytes 270075957248` (~270 GB) are host figures. The GPU line is correct
  and is what the throughput figure depends on; the CPU fields must not be read as the machine that
  did the work. Same caveat Phase 7 declared.

## Closure

**Phase 8: STOP at dev gate. Deviation 8.1 opened for corpus-scale sensitivity.**

What the phase hands forward:

- a measured, reproducible dev reading for three systems under a second Dense model, with full
  provenance and a verified weight digest;
- a **negative answer to its own prerequisite**, not to its research question, which remains open;
- the observation that motivates 8.1: the ordering between the two encoders is bounded to a
  19,366-paragraph distractor pool, and nothing measured here says it survives a change of corpus
  scale or shape.

Phase 9 does **not** inherit a Dense model from Phase 8. That selection was the phase's declared
output and it was not produced.
