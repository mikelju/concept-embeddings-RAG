## Context

Phase 8 asked whether Entity Hop still adds complementary signal when Dense itself is substantially stronger than the historical `BAAI/bge-small-en-v1.5` baseline.

The Strong Dense model was fixed before measurement as:

```text
Qwen/Qwen3-Embedding-0.6B
revision 97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3
1024 dimensions
```

with the exact asymmetric query prompt declared in `8.spec.md`.

The experiment ran on the frozen Phase 1 corpus of **19,366 whole paragraphs** and the same **600 dev questions** used by Phases 1-8.

The pre-declared Phase 8 stop rule required Strong Dense to beat the inherited BGE-small dev result:

```text
487 / 600 = 0.8117 Full Support @2,048
```

before the held-out split could be encoded.

The measured dev result was:

| System | Full Support @2,048 | Questions |
|---|---:|---:|
| inherited Dense (`bge-small`) | 0.8117 | 487 / 600 |
| Strong Dense (`Qwen3-Embedding-0.6B`) | 0.7433 | 446 / 600 |
| Strong Dense + BM25 | 0.8150 | 489 / 600 |
| Strong Dense + Entity Hop | 0.8233 | 494 / 600 |

Strong Dense therefore missed the gate by 42 questions and trailed the inherited Dense baseline by **41 questions / 6.83 percentage points**.

Phase 8 stopped exactly as specified:

- the 1,400 held-out questions were neither encoded nor measured;
- no second encoder was tried inside Phase 8;
- no measured Phase 8 artifact is modified by this deviation.

See `8.results.md` and `data/phase8/dev.json`.

The C19 result is valid for the frozen 19,366-paragraph pool. It does **not** establish that BGE-small is generally a better embedding model than Qwen3-Embedding-0.6B, and it does not establish that the same ordering will hold when retrieval approaches the standard HotpotQA FullWiki search space.

---

## Problem

Phase 8 correctly answered its own question: its chosen Strong Dense candidate failed the precondition required to continue.

That result creates a **new methodological uncertainty before Phase 9**:

> **Does the relative ranking of BGE-small and Qwen3-Embedding-0.6B change as the retrieval corpus grows from the frozen 19,366-paragraph pool toward FullWiki scale?**

Every Phase 1-8 Dense comparison searched the same C19 pool. That is suitable for controlled ablations but does not test whether the relative behavior of the two encoders changes as the number of distractors grows by one or more orders of magnitude.

The uncertainty is specifically about **scale sensitivity of the Dense-vs-Dense ordering**.

It is not a reason to reopen:

- Entity Hop;
- BM25;
- fusion weights;
- extractor choice;
- query prompts;
- the Phase 8 held-out split.

A second issue is corpus comparability. Phase 9 is intended to move to the standard HotpotQA FullWiki setting. Before using larger retrieval pools, the project needs a deterministic connection between the frozen C19 benchmark units and the official FullWiki corpus rather than silently mixing unrelated Wikipedia representations.

---

## Root cause

The immediate cause is known:

> The Dense model chosen a priori for Phase 8 did not satisfy the phase's own premise on the frozen C19 corpus.

The **reason** Qwen underperformed BGE-small is **not known**.

Nothing measured so far establishes that corpus size caused the reversal. This deviation must not assume that explanation.

What is known is a limitation of the Phase 8 design: corpus size was intentionally fixed so that only the Dense retriever changed. That was the correct design for Phase 8, but it contains no evidence about the interaction between encoder choice and distractor-pool size.

The project therefore **chooses** to run one bounded scale-sensitivity diagnostic before selecting the Dense configuration carried into Phase 9.

This is a methodological decision, not a correction of a Phase 8 error.

## Completion criteria and valid terminal states

Deviation 8.1 is considered **measured and complete** when all of the following hold:

- the official FullWiki source identity and checksums are recorded;
- the C19-to-FullWiki reconciliation gate passes;
- the deterministic nested corpus selection is frozen before any scale retrieval result is read;
- both Dense models are pinned with the declared configuration and provenance;
- the C19 reproduction gate passes at both levels: the new evaluation path reproduces `487 / 600`
  (BGE-small) and `446 / 600` (Qwen) exactly against the historical caches, and the re-encode agrees
  with it to within the declared 1-question tolerance;

- exactly one pre-declared measured outcome is assigned:

  - `CROSSOVER`;

- no historical artifact or Phase 8 held-out question is modified/opened;
- focused tests plus project validation pass.

Two protocol-valid early terminal states also exist:

### `DATA_STOP`

More than 50 frozen C19 units cannot be reconciled reliably and uniquely against the official FullWiki corpus under the pre-declared reconciliation rules, so conservative title exclusion is no longer a proportionate remedy.

Consequences:

- no large-corpus embedding;
- no C100/C250/C500 interpretation;
- record the mismatch;
- Phase 9 remains blocked.

### `REPRODUCTION_STOP`

The new evaluation path does not reproduce both historical C19 counts against the historical caches
(Level 1), or the re-encode diverges from it by 2 or more questions in either model (Level 2):

```text
BGE-small   487 / 600
Qwen        446 / 600
```

Consequences:

- no C100/C250/C500 interpretation;
- identify and document the infrastructure discrepancy;
- do not alter the gate after seeing larger-scale results;
- Phase 9 remains blocked.

A stop is not silently converted into a weaker success criterion.

### Added distractors are built exactly like C19 units

Every added FullWiki paragraph becomes an `IndexingUnit` through the **existing** project
constructors: `unit_id_for(title, sentences)` for identity and
`indexable_text = f"{title}. {' '.join(sentences)}"` for what the encoder reads.

This is not a detail. C19's indexed text carries the article title, and `pool.py` documents why: the
title carries the entity a multi-hop question usually needs to bridge. Indexing the added
distractors without it would encode the two populations of the same corpus differently, biasing every
scale in favour of C19 units — a silent asymmetry that would contaminate all four readings and be
invisible in the results.

Reusing `unit_id_for` has a second effect that the reconciliation gate below depends on: a
byte-identical FullWiki duplicate of a C19 paragraph hashes to the **same** unit id and collapses into
one unit, exactly as `build_pool` already deduplicates.

A modern Wikipedia snapshot, generic Wikipedia dataset or independently reconstructed corpus cannot replace this source inside 8.1 without another written deviation.

## C19 reconciliation gate

### Purpose

Reconciliation answers:

> Which official FullWiki paragraph corresponds to each frozen C19 unit?

It is used only to:

- prove correspondence;
- exclude paragraphs already represented by C19 from the added-distractor pool;
- verify that the benchmark evidence exists in the official source;
- record provenance.

### Why the gate is strict: gold twins

The reason reconciliation must be exhaustive is narrower and more serious than bookkeeping, and it is
recorded here so nobody later relaxes the gate without knowing what it was protecting.

Evaluation matches retrieved units against `Question.gold_unit_ids`, **by unit id**. A byte-identical
FullWiki duplicate of a C19 paragraph is harmless: `unit_id_for` is a content hash, so it collapses
into the same unit. The danger is the **near**-duplicate — a paragraph that needs normalized matching,
or one that fails to match at all. Its bytes differ, so it hashes to a different id, and it enters the
distractor pool as a separate unit.

If such a twin is a **gold** paragraph, a model can retrieve it, rank it highly, and receive **no
credit**, because the id does not match. That penalty grows with corpus size, applies to both
encoders, and would be indistinguishable in the results from genuine degradation — it could
manufacture `CONVERGENCE` or `BOTH_DEGRADE` out of nothing.

So the gate is all-or-nothing by design: a fully resolved mapping is what guarantees no twin exists.

### Critical rule: C19 is never reconstructed

The frozen Phase 1 C19 corpus remains **byte-for-byte/content-for-content the current project corpus**.

A FullWiki match — exact or normalized — does **not** replace:

- C19 title;
- C19 sentence sequence;
- C19 unit id;
- C19 `indexable_text`.

This separation is intentional.

Therefore:

```text
C19 used for retrieval/evaluation
=
the existing frozen 19,366 units
```

not a rebuilt FullWiki-derived approximation.

This makes the later C19 reproduction gate unambiguous: a mismatch there is an evaluation/embedding/alignment problem, not an allowed side-effect of corpus reconciliation.

### Matching rule

Current project identity is content-derived from:

```text
title + "\n" + " ".join(sentences)
```

and current `indexable_text` is:

```text
"{title}. {paragraph text}"
```

Reconciliation proceeds in two levels.

#### Exact match

Require:

- same title;
- same reconstructed paragraph plaintext / sentence sequence representation.

#### Normalized unique match

Only when exact match fails:

- title → Unicode NFC, whitespace collapse, then `casefold()`;
- paragraph plaintext → Unicode NFC and whitespace collapse;
- both normalized title and full paragraph must match;
- the match must be unique.

No:

- fuzzy threshold;
- edit-distance fallback;
- embedding similarity;
- manual semantic repair.

### Reconciliation artifact

Record at least:

- total C19 units: 19,366;
- exact matches;
- normalized unique matches;
- ambiguous matches;
- unmatched units;
- dev gold units matched / unmatched;
- digest of the final mapping.

### Gate

All **19,366** C19 units must resolve uniquely by exact or declared normalized matching.

All dev gold paragraphs must therefore also resolve.

### Conservative title exclusion, instead of stopping on a handful

Halting a whole experiment because a few 2017-era paragraphs will not reconcile is a poor trade when
a strictly safer remedy exists. **Over-exclude rather than stop**, within a ceiling fixed now:

```text
unmatched or ambiguous C19 units <=  50   ->  conservative title exclusion, recorded, continue
unmatched or ambiguous C19 units  >  50   ->  terminal state = DATA_STOP
```

50 is 0.26% of 19,366 — small enough that the added distractor pool loses nothing that matters, and
large enough to absorb ordinary source drift rather than ordinary source drift killing the experiment.

Conservative title exclusion means: for every C19 unit that does not resolve, **every FullWiki
paragraph sharing its article title is excluded from `D` in full**, matched or not. A twin can only
carry the same title as its original, so removing the title removes the twin. The cost is
over-exclusion of a few legitimate distractors, which is bounded, recorded, and cannot bias either
encoder — both search the same corpus.

The reconciliation artifact must record, separately: how many units were excluded this way, how many
of them were **gold**, and how many FullWiki paragraphs the exclusion removed in total.

If the ceiling is exceeded:

```text
terminal state = DATA_STOP
```

No new reconciliation rule is invented after retrieval results exist, and the ceiling is never raised
after seeing how many units missed.

## Deterministic nested corpora

After reconciliation passes, construct:

```text
C19   =  19,366
C100  = 100,000
C250  = 250,000
C500  = 500,000
```

with:

```text
C19 ⊂ C100 ⊂ C250 ⊂ C500
```

### Exact construction

The first block is always the existing frozen C19 corpus, in its existing stable order.

Additional distractors come only from official FullWiki units not already mapped to C19.

Let:

```text
D = official FullWiki paragraphs excluding every paragraph mapped to C19
```

Order `D` once by the stable key:

```text
sha256(
    "42\n"
    + official_title
    + "\n"
    + official_plaintext
)
```

`42` is a fixed **salt**, not RNG state.

There is no random sampling call.

Use a deterministic secondary tie-break on official paragraph identity if two digest keys were ever equal.

Then:

```text
C100 = C19 + first 80,634 units of D
C250 = C19 + first 230,634 units of D
C500 = C19 + first 480,634 units of D
```

Thus all larger corpora are prefixes of one single frozen ordering.

Record before Dense scale evaluation:

- source SHA-256;
- reconciliation digest;
- ordering rule version/string;
- salt `42`;
- ordered-selection digest;
- exact selected counts.

No resampling after results are observed.

## Mandatory C19 reproduction gate

Before any C100/C250/C500 result is interpreted, the 8.1 execution path must reproduce, on the
**unchanged frozen C19 corpus**:

```text
BGE-small   487 / 600 = 0.8117 Full Support @2,048
Qwen        446 / 600 = 0.7433 Full Support @2,048
```

The gate uses the current frozen C19 units, not FullWiki-reconstructed replacements.

### Two levels, because two things changed

The naive single gate compares a number produced by new evaluation code **and** new vectors against a
number produced by old code and old vectors. When it fails it cannot say which moved, and it can fail
for a reason that is not a defect: C19 vectors taken as a prefix of a fresh C500 encode are computed
on different hardware with a different batch size, and float non-determinism can move a near-tie
across the top-k boundary and shift a count by one. Stopping the experiment on that would be wrong;
so would waving it through.

So the gate is two checks with two different consequences.

**Level 1 — the evaluation path (blocking).** Run the new 8.1 evaluation and retrieval code against
the **existing historical caches**, which are already on disk:

```text
BGE-small   data/cache/embeddings-<phase 1-7 corpus key>.npz  + its dev question cache
Qwen        data/cache/embeddings-66ef5c19a95f6cbe.npz        + data/cache/questions/embeddings-c9c589c29c226fb3.npz
```

Vectors are then held identical to the historical runs, so the only variable is the new code, and
both counts **must match exactly**:

```text
BGE = 487 / 600      Qwen = 446 / 600
```

Any difference is a defect in the new path. Inspect vector alignment, query encoding, token budgets,
score semantics and tie-breaking; record the discrepancy before changing implementation.

```text
terminal state = REPRODUCTION_STOP
```

**Level 2 — the re-encode (diagnostic).** Evaluate C19 again from the **prefix of the new C500
encode**, and compare against Level 1.

- Identical counts: nothing to report beyond the confirmation.
- A difference of **1 question in either model**: record it, attribute it, and continue. State the
  residual in the results as a measurement caveat on every scale figure.
- A difference of **2 or more questions in either model**: this is no longer float noise.
  `REPRODUCTION_STOP`, and diagnose before interpreting any scale result.

Recording the Level 1 and Level 2 counts separately is what makes the diagnosis possible at all.

The required equality is at the metric/count level, not byte-for-byte embedding equality. These
thresholds are fixed now and are not adjusted after seeing larger-scale results.

## Pre-declared interpretation

The 500k experiment does **not** establish which encoder will perform better at 5M paragraphs.

Its claim is limited to whether the C19 ordering remains stable while the retrieval space grows by more than one order of magnitude.

### The floor guard, fixed before measurement

Both encoders necessarily lose Full Support as distractors grow: the metric requires **both** gold
paragraphs inside a 2,048-token context, and that context holds roughly 16 paragraphs whether the
haystack is 19,366 or 500,000. So the absolute Qwen − BGE deficit compresses mechanically as both
models approach the floor, and a shrinking deficit is **not** by itself evidence that the models
converged.

Worked example of the failure this prevents: BGE 487 → 300 and Qwen 446 → 285 gives a C500 deficit of
15 questions, which would satisfy the `CONVERGENCE` rule below while describing two models that both
collapsed rather than two models that converged.

**Guard, fixed now and not after seeing any scale result:**

```text
BGE retention floor at C500 = 244 / 600
```

244 is half of BGE's C19 reading of 487, rounded up — the same "at least half" arithmetic that sets
the 20-question convergence threshold against the 41-question initial deficit. If BGE supports fewer
than 244 questions at C500, the deficit has lost its meaning as a comparison and `CONVERGENCE` may
not be assigned.

The guard decides only between `CONVERGENCE` and `BOTH_DEGRADE`; `CROSSOVER` and `STABLE_RANKING` are
unaffected by it. But **every** outcome must report each model's own C19 → C500 drop in whole
questions alongside the deficit, so a reader can always see the absolute level any difference sits on.

Evaluate outcomes in this order.

### C — `CROSSOVER`

If Qwen equals or exceeds BGE in Full Support @2,048 at **any** of:

```text
C100
C250
C500
```

Permitted reading:

> The Dense ordering measured at C19 does not generalize across the tested retrieval-corpus scales.

Propagation:

> Phase 9 must evaluate both BGE-small and Qwen.

---

### B — `CONVERGENCE`

If there is no crossover, Qwen remains behind, the absolute deficit at C500 is **20 questions or
fewer**, **and BGE supports at least 244 of 600 at C500** (the floor guard above).

The C19 deficit is 41 questions.

The 20-question threshold is an operational threshold fixed before scale measurement, approximately representing removal of at least half the initial deficit.

It is **not** a significance test.

Permitted reading:

> Corpus size materially affects the Dense-model comparison over the tested range.

Propagation:

> Phase 9 must evaluate both BGE-small and Qwen.

---

### BD — `BOTH_DEGRADE`

If there is no crossover, the absolute deficit at C500 is **20 questions or fewer**, but BGE supports
**fewer than 244 of 600** at C500.

Permitted reading:

> Both encoders degraded substantially over the tested range, and the narrowed deficit at C500 cannot
> be distinguished from a floor effect. The scale sensitivity of the ordering is **not** established.

Not permitted:

> The two models converged.

Propagation:

> Treated as inconclusive for the Dense choice. Phase 9 must evaluate both BGE-small and Qwen, and
> the Phase 9 spec must account for the absolute retrieval degradation this outcome measured, which
> is a finding about the task at scale rather than about either encoder.

---

### A — `STABLE_RANKING`

If BGE remains ahead at C100, C250 and C500 and the Qwen deficit at C500 is **more than 20 questions**.

Permitted reading:

> No evidence was found up to 500k paragraphs that Qwen's Phase 8 deficit was an artefact of the 19k retrieval pool.

Not permitted:

> BGE will necessarily beat Qwen at 5M paragraphs.

Propagation:

> BGE becomes the task-validated primary Dense candidate for Phase 9. The Phase 9 spec decides whether Qwen is additionally retained as an external-comparability control.

## Lightweight implementation plan

This embedded plan satisfies the project rule that the implementation path is documented before code while avoiding a new `8.1.spec.md` / `8.1.0_*.md` hierarchy for a bounded deviation.

Aim for seven steps.

### S1 — Acquire and verify FullWiki

- download or stage the official archive;
- verify published size and MD5;
- compute SHA-256;
- inspect/stream safely;
- write source provenance.

No Dense measurement.

### S2 — Reconcile frozen C19

- implement exact then normalized-unique mapping;
- keep current C19 content untouched;
- write reconciliation artifact/digest;
- apply `DATA_STOP` if the gate fails.

### S3 — Freeze nested C100/C250/C500

- exclude FullWiki units mapped to C19;
- order remaining distractors with the exact salted SHA-256 rule;
- persist selection manifest/digest;
- derive the three prefixes.

No Dense result is read before this selection is frozen.

### S4 — Prepare exact scale retrieval

- reuse current `DenseRetriever` if practical;
- otherwise implement only a blockwise exact GPU path;
- test score/ranking equivalence against the existing retriever on a manageable corpus;
- preserve unit-id tie-breaking.

### S5 — C19 reproduction gate, level 1

Run the new 8.1 evaluation path over the unchanged C19 corpus using the **existing historical
caches**, so the only variable is the new code.

Require exactly:

```text
BGE  = 487 / 600
Qwen = 446 / 600
```

If not, write `REPRODUCTION_STOP`.

Do not continue to scale interpretation. Level 2 — the same evaluation from the new C500 prefix — runs
inside S6, once those vectors exist, under the 1-question tolerance declared above.

### S6 — Encode C500 once and measure scale

On the rented RTX 4090 environment:

- encode C500 once with BGE;
- encode C500 once with Qwen;
- encode the 600 dev queries once per model;
- **run reproduction gate level 2**: evaluate C19 from the new C500 prefix and compare against S5;
  stop at 2 or more questions of divergence in either model;
- evaluate C100 / C250 / C500 from aligned prefixes;
- record metrics, each model's own C19 → C500 drop, throughput, cache sizes and costs.

Do not touch held-out.

### S7 — Report, verify and propagate

Write the 8.1 result record with:

- data gate result;
- reproduction gate result;
- headline scale table;
- Recall@k;
- curve;
- cost/provenance;
- one terminal state.

Then:

- run focused tests;
- `uv run pytest`;
- `uv run ruff check .`;
- `uv run mypy src`;
- run targeted `/8-auditar`;
- update `8.0`, master plan, roadmap and `CLAUDE.md`;
- propagate the terminal state into the Phase 9 specification.

Do not create `8.1.tasks.md` unless implementation genuinely grows beyond this bounded shape.

## Final boundary

Deviation 8.1 may establish one of these bounded claims:

- the C19 ordering stayed stable through C500;
- the two Dense models converged materially as scale increased, while both stayed above the declared
  retention floor;
- both encoders degraded so far that the narrowed deficit cannot be distinguished from a floor effect;
- the ordering crossed at one of the tested scales;
- or the experiment stopped before interpretation because its data/evaluation preconditions failed.

It may **not** establish:

- that one model is generally superior;
- what necessarily happens at 5M paragraphs;
- that Entity Hop scales;
- a new Phase 8 held-out result;
- a new model leaderboard.

The purpose of 8.1 is only to make the Dense choice entering Phase 9 better grounded than a single 19k-pool comparison.
