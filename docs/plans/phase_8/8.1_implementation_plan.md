> **Why this filename.** The deviation record
> [`8.1_dense_scale_sensitivity.md`](8.1_dense_scale_sensitivity.md) deliberately refuses to open an
> `8.1.spec.md` / `8.1.0_*.md` namespace: a bounded post-closure diagnostic does not need a second
> phase-plan hierarchy. That same document also says its expected implementation surface may be
> refined **"in the code plan"** when the existing architecture requires it. This is that code plan.
> It is named `8.1_implementation_plan.md` — one flat file beside the deviation, no new numbering
> scheme — at the author's choice.
>
> **Division of labour.** `8.1_dense_scale_sensitivity.md` is the deviation record, the functional
> specification and the seven-step outline: it fixes the **question, the constraints, the rules and
> the terminal states**, and it is **not modified by this plan**. This document decides **HOW**:
> which modules, which functions, which artifacts, which tests, which host. It reopens nothing the

> judgement call at the keyboard.
>
> Simplification rule (Phase 7 onward): one question, **seven implementation steps**, no
> `8.1.tasks.md`, no Phase 6 protocol machinery, reuse before generalization.

## Objective

Answer one question, specified in full by the deviation:

> **Does the relative ranking of `BAAI/bge-small-en-v1.5` and `Qwen/Qwen3-Embedding-0.6B` change as
> the number of retrieval distractors grows from 19,366 paragraphs to 500,000?**

Dev-only. Two encoders already recorded by the project, four nested corpora, one scientific variable
(retrieval-corpus size), exactly one pre-declared terminal state at the end. Phase 8 stays closed
with its `STOP`; the 1,400 held-out questions stay unopened.

### The two early terminal states are first-class outputs, not failures

- [ ] **`DATA_STOP`** — more than 50 C19 units unmatched or ambiguous. Written by S2 into
      `reconciliation.json` as `terminal_state`. Consequences, enforced in code: no large-corpus
      embedding (S6 refuses without a passing `reconciliation.json`), no C100/C250/C500
      interpretation, the mismatch recorded, Phase 9 stays blocked. `scale-outcome` refuses to
      classify.
- [ ] **`REPRODUCTION_STOP`** — Level 1 fails to reproduce both historical counts exactly, or Level 2
      diverges from Level 1 by **2 or more questions** in either model. Written into
      `reproduction.json` (Level 1) or `scale-<model>.json` (Level 2). S6 refuses to measure any
      scale after a Level-1 stop; `scale-outcome` refuses to classify after either. The gate is
      **never** relaxed after a larger-scale number has been seen — the thresholds are constants
      frozen in `config.py` before the first run.

A stop is not silently converted into a weaker success criterion. `scale-outcome` has no branch that
can produce one of the four terminals when an upstream artifact records a stop.

## Design decisions

### D1 — Four CLI stages, one host and one precondition each

Precedent: Phase 8 split `strong-embed` (rented GPU) from `strong-dense` (laptop) *because the host
differed*, and put the gate between them so a failed premise could not be stepped over. Phase 7 split
`cheap-extract` from `cheap-eval` for the same reason. 8.1 has three host/gate boundaries, so it gets
four stages:

```text
LAPTOP   cer scale-corpus --archive <path> ...      S1 + S2 + S3    -> source/reconciliation/selection
           |                                        DATA_STOP possible
LAPTOP   cer scale-repro                            S5 level 1      -> reproduction.json
           |                                        REPRODUCTION_STOP possible
POD      cer scale-run --model bge                  S6              -> embedding-bge.json,  scale-bge.json
POD      cer scale-run --model qwen                 S6              -> embedding-qwen.json, scale-qwen.json
           |                                        REPRODUCTION_STOP possible (level 2)
LAPTOP   cer scale-outcome                          S7              -> outcome.json (one terminal state)
```

Why not fewer:

- **S1 is not its own stage.** Verification and reconciliation both stream the same archive; splitting
  them would double the parse. `source.json` is written first, written once, and reused by a re-run,
  so a reconciliation bug does not cost a second verification pass.
- **Encoding and evaluation are one stage**, unlike Phase 8. There, the measurement ran on the laptop,
  so the vectors had to be shipped. Here the deviation puts *all* evaluation on the rented host, so
  the 2 GB Qwen block never needs to move: one stage, one model, encode then measure. A re-run reuses
  the cache rather than re-encoding, and refuses to record a wall clock for work it did not do (the
  Phase 8 `_refuse_existing_cache` property, restated in D9).
- **`scale-outcome` is separate** because it is the only step that reads *both* models, and because a
  terminal classification that could be produced inside a per-model stage would be a classification
  that could be produced from half the evidence.

Argument surface stays minimal: `--model {bge,qwen}` (required, no default — the model is never
implicit), `--hourly-rate-usd` (Phase 7/8 semantics, `0.0` default is honest only on owned hardware),
`--archive PATH`, `--published-bytes N`, `--published-md5 {hex|none}`, and no others. No `--force`,
no `--skip`, no threshold overrides: everything a threshold could be is a constant in `config.py`.

### D2 — Three new modules, and no edit to any file behind a frozen result

| Module | Job | Why separate |
|---|---|---|
| `corpus/fullwiki.py` | The **untrusted** archive: identity, safe streaming, ceilings, record parsing, layout probe | This is the whole `/8-auditar` surface. Keeping it in one small module means the audit reads one file, not a phase |
| `corpus/scale_corpus.py` | The **deterministic** corpus: reconciliation, salted ordering, prefix freeze, units archive, token counts | Nothing here touches the network or an archive; it is pure, testable arithmetic over records |
| `evaluation/scale_sensitivity.py` | The **experiment**: pins, reproduction gate, per-model scale measurement, outcome classifier, artifacts | Mirrors `evaluation/strong_dense.py` one-to-one; Phase 8's closest precedent |

`retrieval/dense.py`, `evaluation/harness.py`, `evaluation/budget.py`, `evaluation/metrics.py`,
`evaluation/selection.py`, `embeddings/cache.py`, `embeddings/backend.py` and `corpus/pool.py` are
**read and reused, not edited**. Every number of Phases 1–8 was produced by them; a refactor that
happened to be behaviour-preserving would still be a property we relied on instead of enforced. The
only edits are additive: `config.py` (a new constant block), `cli.py` (four stages), `artifacts.py`
(nothing — its helpers already suffice).

### D3 — Reuse `DenseRetriever`; the blockwise path is a fallback, not a plan

The deviation permits a blockwise exact GPU path *"if the existing NumPy implementation is impractical
at C500"*. Read against the code, it probably is not impractical:

- `DenseRetriever.retrieve` computes `self.vectors @ query_vector`. At C500 that reads 2.05 GB
  (Qwen, 500,000 x 1024 float32) and allocates a 500,000-element score vector — **2 MB**, not 2 GB.
  Peak memory is the corpus block itself, which has to exist either way.
- Cost is memory bandwidth, not FLOPs: 600 queries x (0.4 + 1.0 + 2.05) GB ≈ 2.1 TB per model over the
  three scales. On the Phase 8 pod (96 cores, 270 GB RAM) that is minutes, not hours, and a few cents.
- A row block of a matvec computes each output element from one row, so **splitting by rows cannot
  change any individual dot product**. That is what makes a blockwise path *equivalent* rather than
  *approximately equivalent* — but it is also why it buys nothing here.

So S4's deliverable is **not** a new retriever. It is:

1. `corpus_prefix()` — the aligned-prefix construction, with the C19 block asserted to be the frozen
   pool in its existing order;
2. a `ScaleDense` wrapper that gives each (model, scale) pair a distinct `name`, so the harness's
   `run-{system}-{split}-{stamp}.json` files are individually traceable (`dense-bge-c250`, …) with
   **no change to the harness**;
3. a measured feasibility probe (queries/s at C500, peak RSS) recorded in `scale-<model>.json`;
4. the fallback, specified and test-first: **only if** the probe exceeds the declared budget
   (`PHASE_8_1_QUERY_SECONDS_CEILING`) does `BlockwiseDenseRetriever` get written, in a new module
   `retrieval/dense_scale.py`, with the same `(-score, unit_id)` tie-break and an equivalence test
   against `DenseRetriever` on a small corpus **before** it is used for any figure.

Writing the fallback unconditionally would violate the simplification rule's point 5: no branches for
failures that have not occurred.

### D4 — The archive is streamed and never extracted

`tarfile.open(path, "r|bz2")` gives sequential access to members without random seeks. Members are
read into memory with `tar.extractfile(member)` and parsed; **nothing is ever written to disk**, so
path traversal is structurally impossible rather than defended against. Additionally:

- only regular files are considered; directories, links, devices and anything else are skipped and
  counted;
- member names must match `^[A-Za-z0-9_.-]+(/[A-Za-z0-9_.-]+)*$` — no leading `/`, no `..`, no drive
  letters, no backslashes — and a name that does not is a refusal, not a skip;
- every decompression is bounded: `PHASE_8_1_MAX_MEMBER_BYTES` per member payload,
  `PHASE_8_1_MAX_TOTAL_RECORDS` over the archive, `PHASE_8_1_MAX_LINE_BYTES` per JSON line. A bz2
  member that expands past its ceiling raises rather than filling memory (the `MAX_CORPUS_BYTES`
  precedent in `corpus/download.py`, applied to a nested archive);
- payloads are parsed with `json.loads` only. No pickle, no `eval`, no `allow_pickle=True`, no
  `tarfile.extractall`.
- MD5 is computed with `hashlib.md5(..., usedforsecurity=False)`: it exists **only** to match a
  checksum the publisher printed, and the local record is the SHA-256. Without the flag `ruff`'s S324
  rejects it, and rightly — the comment in the code must say which of the two is the integrity
  record.

**The inner layout is discovered, not assumed.** The plan does not encode a belief about whether
members are `AA/wiki_00.bz2` or plain JSON lines, nor about the record schema. `probe_layout()` reads
the first `PHASE_8_1_PROBE_MEMBERS` members, records their names, whether each payload starts with the
bz2 magic `BZh`, and the sorted key set observed on the first records, and writes all of it into
`source.json`. The parser then dispatches on the recorded fact. This is the same discipline the
deviation applies to the size and the MD5: a recollection is a claim until the bytes are read.

### D5 — New token counts: NPZ plus a JSON sidecar

`data/token_counts.json` is untouchable and covers the 19,366 C19 units. The 480,634 added
distractors get their own artifact:

```text
data/phase8_1/token-counts.npz     unit_ids (str_), counts (int32), aligned by index
data/phase8_1/token-counts.json    tokenizer id, tokenizer revision, selection digest, n_units,
                                   the npz digest, and the alignment rule
```

Why NPZ and not JSON: 480,634 entries is ~12 MB of JSON against ~2 MB compressed NPZ, `*.npz` is
already git-ignored so a regenerable derivative cannot drift into the repository, and
`savez_compressed_atomic` already exists in `artifacts.py`. The JSON sidecar is what carries
provenance and is what a reader checks. Loading merges the two sources into one `dict[str, int]` and
asserts the key sets are **disjoint** and their union is exactly the corpus — a distractor that
collided with a C19 unit would have been excluded by reconciliation, so a collision here is a defect,
not a case to handle.

Tokenization runs on the **laptop**, with the pinned budget tokenizer
(`BUDGET_TOKENIZER_ID` / `_REVISION`), in batches: `TokenCounter.count_units` tokenizes its whole
input in one call, which is correct for 19,366 texts and would be a memory fault for 480,634. The
batching wrapper lives in `scale_corpus.py`; `budget.py` is not edited.

### D6 — What crosses the network, and in which direction

To the pod (~215 MB): `data/pool.json`, `data/manifest.json`, `data/token_counts.json`,
`data/phase8_1/{source,reconciliation,selection,reproduction}.json`,
`data/phase8_1/c500-distractors.jsonl.gz`, `data/phase8_1/token-counts.{npz,json}`, and the four
historical caches Level 1 reads.

**Not** to the pod: the 1.5 GB archive. Re-deriving the selection on the rented host would spend
metered minutes re-parsing 5M paragraphs and would then have to be proved identical to the frozen
one. Shipping the frozen units and verifying them against `selection.json`'s digest proves the same
thing for 120 MB and no compute.

From the pod: `embedding-*.json`, `scale-*.json`, `run-*.json`, and — recommended — the four new
vector caches (~2.7 GB). They are regenerable in principle, but the project's caching rule exists
precisely so an expensive deterministic computation is not paid for twice, and once the pod is
destroyed the only way back is another rental. They stay untracked (`*.npz` is git-ignored).

### D7 — `data/phase8_1/` is untracked, like `data/phase8/`

`.gitignore` ignores `data/*` and Phase 8 added no exception, so `data/phase8/dev.json` — the artifact
behind the Phase 8 `STOP` — is already local-only, with `8.results.md` carrying its figures and
digests. 8.1 follows that precedent unchanged. Versioning the 8.1 JSONs would additionally require
extending `.github/detect_secrets_filters.py`, whose path regex covers `data/replacement/` alone, and
whose allow-list is deliberately hard to widen — touching the security gate to publish a diagnostic's
intermediate files is a poor trade. See **OQ-1** if the author wants the opposite.

### D8 — Zero new dependencies

`tarfile`, `bz2`, `gzip`, `hashlib`, `unicodedata`, `heapq`, `json` are standard library. `numpy`,
`httpx`, `sentence-transformers`, `transformers` are already dependencies. The archive **download**
is done by the operator with `curl`, not by project code: `corpus/download.py`'s `_http_fetcher`
buffers the whole body in memory under a 512 MB ceiling and would have to be rewritten as a
streaming-to-disk fetcher to handle 1.5 GB — new code on the untrusted-input path, to save one shell
command. The stage takes `--archive PATH` and verifies what it was handed.

### D9 — A stage never records a measurement it did not take

Phase 8's `_refuse_existing_cache` refuses to write a timing when the cache is already on disk. 8.1
keeps the property with the shape a combined encode+measure stage needs:

- `embedding-<model>.json` **exists and is digest-valid and its cache key matches** → the encode is
  skipped, the recorded timings are reused unchanged, and the stage proceeds to measurement;
- the cache exists but the artifact does **not** → refusal, naming the file to delete deliberately;
- neither exists → encode, time it, write the artifact once.

`scale-<model>.json` is written once and never overwritten, exactly like `dev.json` in Phase 8.

- **Why the gate is strict — the gold twins, and why this is not bookkeeping.** Evaluation matches
  retrieved units against `Question.gold_unit_ids` **by unit id**, and `unit_id_for` is a content
  hash. A byte-identical FullWiki duplicate of a C19 paragraph is therefore harmless: it collapses
  onto the same id. The danger is the **near**-duplicate. Its bytes differ, so it hashes to a
  different id and enters the distractor pool as a separate unit. If such a twin is a **gold**
  paragraph, a model can retrieve it, rank it first, and score **zero credit** — and that penalty
  grows with corpus size, applies to both encoders, and is indistinguishable in the results from
  genuine degradation. It could manufacture `CONVERGENCE` or `BOTH_DEGRADE` out of nothing. A fully
  resolved mapping is the only thing that guarantees no twin exists, which is why the gate is
  all-or-nothing, and why the remedy for a residue is to delete the whole title rather than the
  paragraph: a same-title twin cannot survive its title's removal. Over-exclusion costs a few
  legitimate distractors, is bounded at 50 titles, is recorded, and cannot bias either encoder
  because both search the same corpus.
- **Tests** (`tests/corpus/test_scale_corpus.py`): exact beats normalized; a normalized match that is
  not unique is counted ambiguous and **not** accepted; 50 unresolved → exclusion and continue, 51 →
  `data_stop` and no selection is written; title exclusion removes **every** official paragraph
  carrying an unresolved unit's title, matched or not; the pool is unchanged; the artifact's digest is
  a function of the mapping and changes when the mapping does.

## Notes, technical decisions and real gotchas found in the code

**The historical cache keys are concrete, and they are these.** The deviation writes the BGE key as a
placeholder. Read off `data/cache/`: BGE corpus `bacd74e7f468f0d4` (384 dim, revision-pinned; the
older `a28365b7ed90ed10` holds the *same vectors* under `revision: "main"` and is a migration
artifact, **not** the file to read), BGE dev questions `35329d9e75da1d4f`, Qwen corpus
`66ef5c19a95f6cbe`, Qwen dev questions `c9c589c29c226fb3` (with `query_prompt` in its sidecar).

**`question_cache_key` ignores the corpus, so the 8.1 question vectors would collide with the
historical ones.** The single most dangerous integrity trap in this deviation, and the reason for the
separate cache directories in S6. Under the same model, revision, split, normalization and prompt, the
600 dev questions hash to the same key whatever the corpus is — so a naive `scale-run` would write
GPU-encoded vectors over `embeddings-35329d9e75da1d4f.npz`, the file behind `487 / 600`.

**`TokenCounter.count_units` tokenizes its entire input in one call.** Correct at 19,366 texts, a
memory fault at 480,634. Batching lives in the new module; `budget.py` is not edited.

**`config.py` is on the import closure of `evaluation/selection.py`, and that closure may not contain
the string literals `"test"` or `"train"`.** `tests/evaluation/test_no_test_contamination.py` asserts
it statically over the whole closure. The 8.1 constant block must therefore key its dictionaries by
model and by outcome, never by split name — `{"bge": 487}`, not `{"dev": ..., "test": ...}`.

**`ruff`'s bandit rules will bite twice.** S324 rejects `hashlib.md5(...)` without
`usedforsecurity=False`; MD5 is here to match a publisher's checksum and the local record is SHA-256,
which the code comment must say. S202 rejects `tarfile.extractall` without validation — the plan never
extracts at all, which is the stronger answer.

**`DenseRetriever`'s tie-break is deterministic in its ordering but arbitrary at the `argpartition`
boundary.** `np.argpartition` selects *some* k-best set; exact score ties straddling position `k`
could put either of two tied units inside the cut. With float32 dot products over distinct paragraphs
this effectively never happens, and it is not a new risk — every Phase 1–8 figure rests on the same
code. It matters only for the blockwise fallback's equivalence test, which must therefore include a
deliberate exact tie.

**Level 1 and Level 2 do not run on the same host as specified**, which is exactly what Level 2's
1-question tolerance exists for: a C19 prefix of a fresh C500 encode is computed on different
hardware, with a different batch size, and float non-determinism can move a near-tie across the
top-100 boundary. D-L1 in S6 is the cheap way to separate host from vectors; without it, a 1-question
residual is recorded but not attributable.

**Conservative title exclusion covers the twin the deviation argues about, and only that one.** A twin
must share its original's title to be a twin of it, so removing the title removes it. A *differently
titled* near-duplicate of a C19 gold paragraph — a disambiguation variant, say — is outside the
declared remedy's reach. That is a residual limitation of the design, not of this plan, and
`8.1_results.md` should state it rather than let the gate's strictness imply more than it delivers.

**Expected pod time, labelled as a projection and never as a measurement.** Phase 8 measured
`247.062 paragraphs/s` for Qwen on the RTX 4090 over 19,366 paragraphs. Linearly, 500,000 paragraphs
project to ~33.7 minutes; BGE-small is a much smaller model and should be well under that; retrieval
over the three scales is minutes. So one rental of roughly 1.5–2 hours covers both models with slack.
This paragraph is arithmetic on a measured figure, is a **projection**, and is not a budget or an
authorization — S6 measures its own.

**Disk and memory on the pod.** ~2.7 GB for the two new corpus caches plus ~120 MB of uploaded
selection plus the two model snapshots: 40 GB is comfortable, as in Phase 8. Peak RSS while measuring
Qwen C500 is ~2.1 GB for the vectors plus the 500,000-entry token-count dict; the Phase 8 host
reported 270 GB of RAM.

**No BM25, no Entity Hop, no fusion at any scale.** The deviation excludes them, and there is no
GLiNER index over FullWiki paragraphs to hop through even if it did not. `scale_sensitivity.py`
imports neither `bm25.py` nor `entity_hop.py` nor `fusion.py`, and a test asserts it.

**No `8.1.tasks.md`.** Seven steps, four stages, three new modules, five new test files. If
implementation genuinely grows past that shape, that is a finding to record — not a reason to spawn a
task hierarchy.

## Further decisions closed by the author, 2026-09-20

Three questions arose during implementation and were answered before S1 was run. None of
them changes a scientific rule, a threshold, an outcome or the specification.

- **The uniqueness rule stays bidirectional.** `_enforce_one_to_one` in
  `corpus/scale_corpus.py` is confirmed as implemented: when one official paragraph is the
  unique normalized candidate of two different C19 units, **neither** is accepted and both
  count as ambiguous against the ceiling of 50. This is the conservative reading of the
  deviation's "the match must be unique", in both directions.
- **The obsolete Phase 8 cache test was repaired, not skipped.** It asserted that no Phase 8
  cache existed, which stopped being true when Phase 8 was measured. It now asserts what
  restriction R3 actually protects - that a Phase 8 cache key can never collide with an
  inherited one - with the expected keys still recomputed, no conditional skip, and no
  measured Phase 8 artifact touched.
- **`uv run ruff format .` is NOT run.** It reformats files behind closed phases, including
  Python code blocks inside Markdown such as `docs/plans/phase_6/6.0_dense_entity_navigation.md`
  (verified by reverting that file and re-running the formatter). Only 8.1's own new or
  modified files are formatted. The global validation remains `uv run ruff check .`,
  `uv run mypy src` and `uv run pytest`, none of which rewrites a file.
