# Phase 2: Concept space - dictionary and matrix X

> Functional spec: `docs/plans/phase_2/2.spec.md`
> This plan implements the requirements defined in that spec.

## Objective

Represent the 19,366 frozen paragraphs of Phase 1 in a second coordinate system whose dimensions
are concepts induced from the corpus itself, and ship a sparse non-negative matrix `X = chunks x
concepts` that Phase 3 can retrieve over and Phase 4 can diffuse across. The deliverable is the
representation plus an honest inspection of it. **Nothing here measures recall**, and no number
produced in this phase is comparable to the dense or BM25 baselines.

**HU-1 - Dictionary induced by non-negative sparse coding**
- [ ] Induced with `MiniBatchDictionaryLearning`, `positive_code=True`, explicit `random_state`
- [x] `positive_dict` is **False**, against the letter of the original spec and on measured
      evidence - see decision D1. Approved by the author; HU-1 of the spec and the Phase 2 bullet

- [ ] The sweep runs for K in {512, 1024, 2048, 4096} into four independent artifacts; none
      overwrites another
- [ ] **No K is chosen here.** The choice is Phase 3's, against dev recall, and that deferral is
      deliberate
- [ ] Same K + same seed + same corpus produces a bit-identical dictionary
- [ ] Induced over the whole pool, dev and test together, declared transductive: no question, no
      gold annotation and no split label takes part
- [ ] Each atom is an L2-normalized float32 vector of 384 dimensions, in the query's own space
- [ ] Every artifact records K, seed, sparsity parameter, iterations, `unit_set_hash`, embedding
      model and revision, and code version

**HU-2 - Matrix X with the meaning of a weight written down**
- [ ] `X` is the transform of the corpus against the dictionary, never a similarity computed
      afterwards and never an assignment from any other rule
- [ ] Every entry non-negative; `X` stored sparse
- [ ] Row `i` belongs to `unit_ids[i]`, validated on load exactly as the embedding cache is
- [ ] `weight_semantics` is written into the artifact itself: the non-negative coefficient of that
      atom in the reconstruction of the unit's embedding, on the scale of L2-normalized embeddings;
      not a probability; not summing to 1; not comparable across units without row normalization
- [ ] Both views available and named: `raw` (reconstruction scale) and `row_normalized`
- [ ] Sparsity calibrated to a declared target, achieved figure recorded per K
- [ ] **Rejection**: mean active concepts per unit below 3 fails the fit; it is not shipped
- [ ] Reconstruction error against the original embeddings recorded per K

**HU-3 - Artifacts persisted without pickle, not even indirectly**
- [ ] Dictionary and `X` persisted as `.npz` plus a JSON sidecar, following the Phase 1 pattern
- [ ] `joblib.dump` / `joblib.load` used nowhere; the fitted estimator is never serialized
- [ ] `numpy.load(..., allow_pickle=False)` on every read path of this phase, including the sparse
      matrix - which is why `scipy.sparse.save_npz` / `load_npz` are not used (decision D5)
- [ ] A test asserts the absence of `pickle`, `joblib.dump`, `joblib.load`, `allow_pickle=True`
      across the phase's source
- [ ] Artifact filename derives from the configuration key
- [ ] Loading validates the artifact against the pool it claims to describe, and aborts on mismatch

**HU-4 - Dictionary normalization and auditable deduplication**
- [ ] Atoms L2-normalized, so cosine between atoms is a dot product
- [ ] Near-duplicates detected above a declared, configurable cosine threshold, recorded with the
      artifact
- [ ] A merged group yields one replacement atom, and **`X` is recomputed** against the
      deduplicated dictionary - never by summing columns of the old `X`
- [ ] A merge log records every group: member atoms, pairwise similarities, resulting index. A
      versioned artifact, not console output
- [ ] Atom count before and after deduplication reported per K
- [ ] Removing more than a declared fraction of the dictionary is reported as a finding about K

**HU-5 - An inspectable, criticizable space**
- [ ] Active concepts per unit: mean, median, p5, p95, max
- [ ] Units per concept, plus the count of dead atoms
- [ ] Orphan units: all-zero rows of `X`, listed by unit id
- [ ] Top activating units per concept, so a concept reads as its evidence
- [ ] Concept co-activation: the concepts most frequently co-active with each concept
- [ ] Every diagnostic computed per K and written as a versioned artifact
- [ ] Reported for the pool as a whole. **No breakdown by split, nothing computed over test gold**

**HU-6 - Concept labelling and the project's first real secret**
- [ ] A concept is labelled from its own most strongly activating units
- [ ] Only K = 2,048 is labelled; the other three spaces are read through `top_units_per_concept`
- [ ] Labels are used only for reporting. A test asserts the retrieval path does not depend on them
- [ ] Labelling is a separate stage. Induction, `X`, dedup and every diagnostic run fully offline
      with no API key present
- [ ] Every call cached on disk, keyed by a hash of the exact prompt content. A second run over an
      unchanged dictionary makes zero API calls
- [ ] The artifact states that labelling is not reproducible and that the cache is what fixes it
- [ ] `ANTHROPIC_API_KEY` read from the environment via `.env`, never printed, logged, written into
      an artifact, included in a cache key, or committed. A `.env.example` carries the name only
- [ ] Absent the key, the stage exits with a clear message naming what is missing
- [ ] Model id, prompt template hash and units shown per concept recorded with the labels
- [ ] Estimated and actual cost of the run recorded

**HU-7 - Dictionary quality against a null baseline**
- [ ] Per-concept coherence: mean pairwise cosine between the embeddings of the units that activate
      it most, over a declared number of units recorded with the artifact
- [ ] Read against a **null baseline measured on this same pool** - the same statistic over random
      sets of units, with an explicit seed - reported as mean, standard deviation and z-score
- [ ] Per-concept alignment between the atom and its own evidence, which fails differently from
      coherence and is what separates a polysemous atom from a merely broad one
- [ ] Per-concept concentration of activation mass over those top units
- [ ] A concept with fewer active units than the declared minimum is undefined, never scored zero
- [ ] The concepts below the null mean are listed: that list is this project's junk concept
- [ ] Same matrix, same embeddings, same seed - same numbers, and the seed travels in the artifact
- [ ] **Nothing is pruned, merged or reweighted on the strength of a score**, here or by this code
- [ ] Computed per K, in the HU-5 artifact, reading the pool only

## Technical notes and decisions

Decisions D1, D2 and D5 were settled with measurements taken during planning, not by reasoning about
the library. The spike script is disposable and lives outside the repository.

### D1 - `positive_dict=False`, and the spec is amended to say so

The spec asks for `positive_dict=True` alongside `positive_code=True`. Measured on the actual cached
embeddings, that combination cannot work:

- **51.3% of the energy of the corpus embeddings lives in negative coordinates.** `bge-small-en-v1.5`
  vectors are L2-normalized but signed; 49.2% of all entries are negative and every one of the
  19,366 rows has at least one. With a non-negative dictionary *and* a non-negative code, the
  reconstruction `code @ atoms` is non-negative in every coordinate, so its error has a floor near
  0.51 no matter how many atoms are spent on it. That is NMF's assumption applied to data that
  violates it.
- A short fit (K = 512, 4,000 units, 3 passes, `alpha` 0.3) confirms it end to end:

  | `positive_dict` | relative reconstruction error | mean active per unit | dead atoms |
  |---|---:|---:|---:|
  | `True` | 0.825 | 1.59 | 286 / 512 |
  | `False` | 0.437 | 2.77 | 31 / 512 |

  The non-negative dictionary lands at **1.59 active concepts per unit - below the spec's own
  rejection floor of 3** - and kills 56% of its atoms. It reproduces exactly the one-hot regime that
  disqualified clustering in the first place.

What the hypothesis requires is **non-negative activations**, which is `positive_code=True`: that is
what gives co-activation, unit-to-unit similarity in concept space, and something for Phase 4 to
diffuse over. It is also what the prior art does - a ReLU SAE constrains the encoder output, never
the decoder. `positive_dict` was over-specification, and the founding decision in the master plan
names only `positive_code=True`.

**Done (task T0), approved by the author before Step 1**: HU-1 of `2.spec.md` and the Phase 2
bullet of the master plan now say `positive_dict=False` and carry the measurement, rather than
the code quietly doing something the spec forbids.

### D2 - `fit_algorithm="cd"` is forced, not chosen

scikit-learn 1.9.0 defaults to `fit_algorithm="lars"`, and LARS rejects the constraint outright:
`ValueError: Positive constraint not supported for 'lars' coding method.` So the fit uses coordinate
descent, and `transform_algorithm="lasso_cd"` for the same reason. Sparsity is therefore controlled
by an L1 penalty (`alpha`), not by a fixed number of non-zeros - which is why Step 5 exists.

### D3 - Calibrating `alpha`, and what the sparsity target is

With `alpha` fixed, achieved sparsity is an outcome rather than a setting, and it moves with K. The
declared target is **8 to 16 mean active concepts per unit**, with the spec's hard floor at 3.
Step 5 searches `alpha` per K on a seeded subsample of the pool until the mean lands in the band,
and the achieved figure plus the final `alpha` are recorded in the artifact.

The search reads **only unit embeddings** - no question, no gold, no split label - so it is not
tuning against an evaluation set. It is the same class of decision as choosing `k1` for BM25, made
before any retrieval exists to be measured. The spike's `alpha` of 0.3 gave 2.77 active per unit, so
the working range starts well below that.

### D4 - Cost, and what happens if the sweep does not fit in two hours

Measured: K = 512 over 4,000 units for 3 passes takes 4.1 s to fit and 0.3 s to code 2,000 units.
Coordinate descent works against a K x K Gram matrix, so cost grows faster than linearly in K -
K = 4,096 means a 16.7M-entry Gram (134 MB, fine) but a materially slower per-sample solve. The full
sweep at a realistic iteration count is expected to land inside the two-hour budget, with K = 4,096
dominating it.

Step 12 measures and prints the per-K wall time, and stops the sweep rather than running overnight.
If K = 4,096 alone blows the budget, the declared fallbacks, in order: raise `batch_size`, lower
`max_iter` with early stopping on `tol`, and only then induce the dictionary over a seeded subsample
of the pool while still coding the full corpus against it. The third would change what HU-1 promises
about the induction set, so it becomes deviation `2.1` if it is used - it is not taken silently.

### D10 - The induction `alpha` is a declared constant, the coding one is calibrated

Two different penalties, and conflating them would be a silent error. The
induction `alpha` shapes **which atoms are learned**; the coding `alpha` decides how
many of them activate per unit, and it is searched per K against the target band
(decision D3) because achieved sparsity moves with K.

Only the second can be calibrated cheaply: measuring the first would mean refitting
the dictionary once per candidate, at minutes per fit. So the induction penalty is a
declared constant, `INDUCTION_ALPHA = 0.05`, chosen below the spike's 0.3 - which
measured 2.77 mean active per unit at K = 512, well under the 8-16 band this phase
targets - and it travels inside the dictionary key, so a later change writes a new
artifact rather than redefining an existing one. It is not tuned against any
evaluation set, and no number in this phase depends on its being optimal.

### D5 - The sparse matrix is written by hand, not through `scipy.sparse.save_npz`

HU-3 requires `numpy.load(..., allow_pickle=False)` on every read path of this phase.
`scipy.sparse.load_npz` calls `np.load(file, **PICKLE_KWARGS)` - an internal constant this project
neither controls nor can assert on. Writing the four CSR components (`data`, `indices`, `indptr`,
`shape`) with `np.savez_compressed` and rebuilding them on load costs about ten lines, keeps the
`allow_pickle=False` call in our own source where the Step 11 guard can see it, and follows the
`EmbeddingCache` pattern instead of inventing a second one.

### D6 - `transform` must be batched

`transform` returns a dense array. For K = 4,096 that is 19,366 x 4,096 float64, roughly 634 MB in a
single allocation, for a result that is over 99% zeros. Step 6 codes in batches, converts each batch
to CSR and stacks, so peak memory is set by the batch rather than by the corpus.

### D7 - One stored view, one derived view

`raw` is what is persisted; `row_normalized` is a pure function over it, tested. Persisting both
would double the artifacts to verify and create two files that can silently disagree. HU-2 asks for
both views to be *available and named distinctly*, which a named function satisfies; the sidecar's
`view` field says what is in the file.

### D8 - Labelling: individual calls with a disk cache, not the Batches API

`claude-sonnet-5` is $2.00 / $10.00 per MTok. With ~10 evidence units per prompt at the corpus mean
of 124 tokens, the estimate is ~1.5K input and ~100 output tokens per concept: about **$6.1 input +
$2.0 output = $8.1** for 2,048 concepts. The Batches API would halve that to roughly $4.

The plan takes the individual calls anyway. The saving is a one-off $4, while the batch path adds
polling, 24-hour expiry, out-of-order results keyed by `custom_id` and a partial-failure story - and
it does **not** remove the need for the disk cache, which HU-6 requires regardless. If the measured
cost comes out materially above the estimate, Batches is the documented fallback.

Request shape: `thinking={"type": "disabled"}` (naming a concept from ten paragraphs does not need
reasoning, and it keeps output tokens predictable) and structured output via
`output_config={"format": ...}` so `{name, gloss}` parses without post-hoc string handling.
`temperature` is **not** sent - it is rejected with a 400 on Sonnet 5, which is exactly why HU-6
declares labelling non-reproducible and treats the cache as the thing that fixes the result.

The model choice is the spec's, not a default: the standing default for new Claude code is
`claude-opus-5`, and `2.spec.md` deliberately names `claude-sonnet-5` for a bulk, low-difficulty
labelling job. It is recorded in the artifact so a later relabelling stays comparable.

### D9 - Error handling on the labelling path

A most-specific-first chain, per the SDK's typed exceptions: `AuthenticationError` (bad key - abort,
never retry), `RateLimitError` (honour `retry-after`), `APIStatusError` with `status_code >= 500`
(retry), `APIConnectionError` (retry), anything else re-raised. The SDK already retries 429 and 5xx
twice with backoff; the cache means an aborted run resumes where it stopped instead of re-spending.

### The transductive induction, stated plainly

The dictionary is induced over the whole pool because that is the corpus being searched, exactly as
BM25 indexes the whole corpus. No question text, no gold annotation and no split label enters the
induction. This is declared in the artifact and will be declared again in the Phase 5 report; it is
a property of the design, not an oversight. Inducing over dev only would build the space from a
corpus different from the one retrieval traverses.

### D11 - The quality diagnostic is read against a null, and prunes nothing

Two decisions in one, both about what a coherence number is allowed to be used for.

**It is read against a null baseline.** `bge-small-en-v1.5` is anisotropic, and here is the measured
figure for this pool: over 200 random sets of 25 of the 19,366 units, seed 42, the mean pairwise
cosine is **0.4292 +/- 0.0073**. Two paragraphs of this corpus picked at random are not near
orthogonal; they are at 0.43. A concept scoring a raw 0.45 therefore looks moderately coherent and
is indistinguishable from noise, while the 0.31 that reads as merely "suspicious" is sixteen
standard deviations below random. The diagnostic reports the z-score against that baseline, and
without it the metric would look quantitative and decide nothing.

One caveat on reading the z-score: the mean of 300 pairs concentrates hard, so the null spread is
small and the scores are large by construction. It is a ranking device, not a significance test.

**It prunes nothing.** Dropping the least coherent concepts is tempting and would be a mistake here.
The atoms were fitted to reconstruct these very embeddings, so a coherence measured in that same
space is partly guaranteed by construction: it ranks concepts against each other, it does not
validate them. And an incoherent concept is not proven harmful to retrieval - it may be inert.
Removing it would change what Phase 3 retrieves over, on a threshold no measurement has justified.
The score is written down and read; whether to prune is a Phase 3 variant against dev recall, or a
Phase 5 ablation. Both are now written into the master plan.

A consequence worth stating: `compute_quality` takes the matrix, the embeddings and the atoms, and
returns numbers. It has no path that writes to any of the three.
