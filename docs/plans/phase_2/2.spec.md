# Spec Phase 2: Concept space - dictionary and matrix X

> Functional specification - WHAT to build and WHY.
> The HOW belongs in the phase plan (`2.0_phase_name.md`).
> Acceptance criteria are verified with `/7-verificar` at the end of the phase.

---

## Problem and objective

**Problem**: Phase 1 proved the failure mode this project exists to fix. On the dev split at 2,048 tokens, 12% of questions defeat both baselines, and the pattern is always the same: the retriever finds the entity the question names and never reaches the bridge entity the question does not name. The information needed for the second hop is frequently sitting inside the paragraph already retrieved - but nothing in the system can travel from that paragraph to the one it implies. A dense vector has 384 dimensions and none of them means anything on its own, so there is no surface to travel across.

**Objective**: build that surface. Represent the same 19,366 paragraphs in a second coordinate system whose dimensions are concepts induced from the corpus itself, and produce a sparse non-negative matrix `X = chunks x concepts` over which retrieval (Phase 3) and expansion (Phase 4) can operate. This phase delivers the representation and an honest inspection of it - not retrieval, and not evidence that it works.

**What this phase cannot prove**: nothing here measures recall. A concept space is not a retriever and cannot be compared to dense or BM25. Every diagnostic in this spec can come out clean and Phase 3 can still land below the baseline. The acceptance criteria below are therefore constructional and diagnostic, never evidential. The first evidence arrives in Phase 3.

## User stories

### HU-1: Dictionary induced by non-negative sparse coding

**As** the researcher,
**I want** the concept dictionary learned from the corpus embeddings by non-negative sparse coding, over a range of dictionary sizes,
**so that** the dimensions of the new space come from the corpus rather than from my assumptions, and so that the choice of K is made later against a metric that measures what matters.

**Acceptance criteria:**
- [x] The dictionary is induced with `MiniBatchDictionaryLearning` under `positive_code=True` and `positive_dict=False`, over the cached Phase 1 embeddings, with an explicit `random_state`. **`positive_dict=False` amends this criterion on measured evidence** (plan decision D1): 51.3% of the energy of the `bge-small-en-v1.5` embeddings lives in negative coordinates, so a non-negative dictionary combined with a non-negative code cannot reconstruct them - a short fit at K = 512 gave 1.59 mean active concepts per unit, *below the rejection floor of 3 stated in HU-2*, with 56% dead atoms and 0.83 relative reconstruction error, against 2.77 / 6% / 0.44 unconstrained. What the hypothesis needs is non-negative **activations**, which is `positive_code=True`; constraining the dictionary as well is what a ReLU SAE deliberately does not do, and the master plan's founding decision names only `positive_code=True`
- [x] The induction runs for **K in {512, 1024, 2048, 4096}**, producing four independent artifacts; none overwrites another
- [x] **This phase does not choose a K.** The choice is made in Phase 3 against gold recall on the dev split, and this spec records that deferral as deliberate
- [x] Two runs with the same K, the same seed and the same corpus produce a bit-identical dictionary
- [x] The dictionary is induced over the **whole pool**, dev and test together. This is transductive and is declared as such: no question, no gold annotation and no split label takes part in the induction, exactly as BM25 indexes the whole corpus. Inducing it over dev only would build the space from a corpus different from the one being searched
- [x] Each atom is an L2-normalized vector of 384 dimensions, living in the same space as the query embedding, so that Phase 3 maps question to concepts with a dot product and no textual intermediary
- [x] Every artifact records the configuration that produced it: K, seed, sparsity parameter, iterations, corpus `unit_set_hash`, embedding model and revision, code version

### HU-2: Matrix X with the meaning of a weight written down

**As** the researcher,
**I want** `X` to be the direct output of the coding, with the semantics of its values stated explicitly,
**so that** a weight of 0.73 means one specific thing everywhere in the project, and so that co-activation - the property expansion depends on - actually exists.

**Acceptance criteria:**
- [x] `X` is the transform of the corpus against the dictionary, not a similarity matrix computed afterwards and not an assignment produced by any other rule
- [x] Every entry of `X` is non-negative, and `X` is stored sparse
- [x] Row `i` of `X` corresponds to the unit at position `i` of a persisted `unit_ids` list, validated on load exactly as the embedding cache is
- [x] **The meaning of a weight is documented in the artifact itself** (§3 requires this explicitly: there is no universal meaning of 0.73). At minimum: that it is the non-negative coefficient of that atom in the reconstruction of the unit's embedding, measured on the scale of L2-normalized embeddings; that weights do not sum to 1 and are not probabilities; and that comparing raw weights across units is invalid without row normalization
- [x] Both views are available and named distinctly: the **raw** coefficients (reconstruction scale) and the **row-normalized** view (for comparing units to each other). Phase 3 declares which one it retrieves with
- [x] Sparsity is calibrated to a declared target of mean active concepts per unit, and the achieved figure is recorded per K
- [x] **Rejection criterion**: if the mean number of active concepts per unit falls below 3, the fit is declared failed and is not shipped. That is the one-hot regime that made clustering unusable - it destroys co-activation, unit-to-unit similarity in concept space, and expansion itself
- [x] Reconstruction error against the original embeddings is recorded per K, as evidence of how much of the corpus the space actually explains

### HU-3: Artifacts persisted without pickle, not even indirectly

**As** the researcher,
**I want** every artifact of this phase stored in a non-executing format,
**so that** loading a cached dictionary can never execute code, and so that artifacts stay readable by anything other than the exact library version that wrote them.

**Acceptance criteria:**
- [x] Dictionary and `X` are persisted as `.npz` plus a JSON sidecar, following the Phase 1 embedding cache pattern
- [x] **`joblib.dump` and `joblib.load` are not used anywhere.** They are the idiomatic scikit-learn route and they are pickle under another name: loading such a file executes code. The fitted estimator object is never serialized - only its learned array of atoms is
- [x] `numpy.load` is called with `allow_pickle=False` on every path that reads an artifact of this phase
- [x] A test asserts the absence of `pickle`, `joblib.dump`, `joblib.load` and `allow_pickle=True` across the phase's source, so the rule survives a later refactor rather than resting on reviewer memory
- [x] The artifact filename derives from the configuration key (K, seed, sparsity, corpus hash, model revision), so changing any parameter writes a new artifact instead of overwriting the previous one
- [x] Loading validates the artifact against the pool it claims to describe, and aborts on mismatch. Phase 1 established the rule: verify on load, do not merely record

### HU-4: Dictionary normalization and auditable deduplication

**As** the researcher,
**I want** near-duplicate atoms detected and merged under an explicit criterion, with a record of what was merged,
**so that** the space does not carry the same concept three times, and so that anyone can check the merge decisions instead of taking them on faith.

**Acceptance criteria:**
- [x] Atoms are L2-normalized, so that cosine between atoms is a dot product and the merge threshold means the same thing for every pair
- [x] Near-duplicate pairs are detected by cosine similarity above a **declared, configurable threshold**, and the chosen value is recorded with the artifact
- [x] Merging a group of atoms produces a single replacement atom, and **`X` is then recomputed by transforming the corpus against the deduplicated dictionary**. Summing the columns of the old `X` is not acceptable: the result would no longer be the output of any coding, and HU-2's weight semantics would stop holding
- [x] A merge log records every group: which atoms merged, their pairwise similarities, and the resulting atom index. It is a versioned artifact, not console output
- [x] The count of atoms before and after deduplication is reported per K
- [x] If deduplication removes more than a declared fraction of the dictionary, that is reported as a finding about K rather than silently absorbed - it is the signal that the dictionary is oversized for this corpus

### HU-5: An inspectable, criticizable space

**As** the researcher,
**I want** diagnostics that let me see what the space actually looks like,
**so that** I can judge it before Phase 3 does, and so that a bad space is caught here rather than blamed on retrieval later.

**Acceptance criteria:**
- [x] Distribution of active concepts per unit: mean, median, p5, p95, max
- [x] Distribution of units per concept, and the count of **dead atoms** - concepts activated by no unit, or by fewer than a declared minimum
- [x] Count of **orphan units** - units whose row of `X` is entirely zero and which are therefore unreachable through the concept space at all
- [x] For each concept, the units that activate it most strongly, so the concept can be read by a human as its evidence rather than as a number
- [x] Concept co-activation: for a concept, the concepts most frequently co-active with it. This is the §14 association graph and the substrate Phase 4 will diffuse over; if it is degenerate here, Phase 4 has nothing to travel across
- [x] Every diagnostic is computed per K and written as a versioned artifact, so the four spaces are comparable side by side
- [x] The diagnostics are reported for the pool as a whole. **No diagnostic is broken down by split, and none is computed over the test questions' gold units**: the test split is not looked at in this phase, not even descriptively

### HU-6: Concept labelling for interpretability, and the project's first real secret

**As** the researcher,
**I want** the atoms named by an LLM from the units that activate them, with every call cached on disk,
**so that** the concept map can be read and criticized - while retrieval never depends on a name, and the API key is handled as a real secret from the first day it exists.

**Acceptance criteria:**
- [x] A concept is labelled from **its own most strongly activating units**, never from a name invented without evidence
- [x] **Only one dictionary is labelled in this phase: K = 2,048.** The other three spaces are inspected through `top_units_per_concept` (HU-5), which needs no API call and reads the same evidence. If Phase 3 selects a different K, labelling that dictionary belongs to Phase 3 and is not a reason to relabel everything here
- [x] The label is used **only** for reporting and inspection. Nothing in retrieval, scoring or expansion ever reads it: the concept's embedding is its atom, per the founding decision. A test asserts that the retrieval path does not depend on the labels artifact
- [x] **Labelling is a separate stage that the rest of the phase never requires.** Inducing the dictionary, building `X` and computing every diagnostic all run fully offline, with no API key present
- [x] Every call is cached on disk, keyed by a hash of the exact prompt content (atom identity plus the units shown). A second run over an unchanged dictionary makes **zero** API calls
- [x] **Labelling is not reproducible, and the artifact says so.** Current models reject `temperature`, so an identical prompt may return a different label on a different day. The on-disk cache is therefore not an optimization but the thing that fixes the result: a dictionary is labelled once and that labelled artifact is what the report cites. This is admissible precisely because no metric depends on it - and it is a second reason the labels stay out of the retrieval path
- [x] `ANTHROPIC_API_KEY` is read from the environment, loaded from `.env`, and **never printed, logged, written into any artifact, included in a cache key, or committed**. `.gitignore` already excludes `.env`; this phase adds a `.env.example` carrying the variable name and no value
- [x] Absent the key, the labelling stage exits with a clear message naming what is missing. It never fails deep inside an HTTP client and never proceeds with a placeholder
- [x] The model id, the prompt template and the number of units shown per concept are recorded with the labels artifact, so a later relabelling can be compared against this one
- [x] The estimated and actual cost of a labelling run is recorded, since this is the first stage of the project that spends money


### HU-7: Dictionary quality measured against a null baseline

**As** the researcher,
**I want** a quantitative per-concept quality diagnostic, read against what random units of this same pool score,
**so that** a polysemous or junk concept is caught by a number here instead of by intuition later - and so that the master plan's promise of finding junk concepts is actually kept, because a dead or orphan count does not find one.

A concept activated by 400 units that have nothing to do with each other passes every criterion of HU-5: it is not dead, it is not orphan, and its ten evidence units look plausible one at a time. This story is the criterion that fails it.

**Acceptance criteria:**
- [x] For each concept, the **semantic coherence** of its evidence: the mean pairwise cosine between the embeddings of the units that activate it most strongly, over a declared number of units recorded with the artifact
- [x] **The coherence is reported against a null baseline measured on this same pool**: the same statistic over sets of units drawn at random with an explicit seed, reported as a mean, a standard deviation and a per-concept z-score. The raw cosine is not interpretable on its own: measured on this pool, 200 random sets of 25 units score **0.4292 +/- 0.0073**, so two unrelated paragraphs sit at 0.43 and an absolute value cannot separate a good concept from a bad one
- [x] For each concept, the **alignment with its own evidence**: the mean cosine between the atom and the units that activate it most. It fails differently from coherence - an atom sitting between two unrelated groups can be poorly aligned while each group is internally tight - and both numbers together are what distinguish a polysemous atom from a merely broad one
- [x] For each concept, the **concentration of its activation mass**: the share of the concept's total weight held by those top units. HU-5 counts the units that activate a concept; this measures how the weight is spread across them, which is what tells an over-general concept from a sharp one
- [x] Concepts with fewer active units than a declared minimum are reported as **undefined**, never as a coherence of zero. A pairwise mean over two units is a single pair, and a number that noisy would rank concepts by chance
- [x] The concepts scoring **below the null mean** are listed explicitly: that list is the operational definition of a junk concept in this project
- [x] The diagnostic is **reproducible**: same matrix, same embeddings and same seed produce the same numbers, and the seed travels in the artifact
- [x] **The diagnostic never changes the space.** No concept is pruned, merged, reweighted or reordered because of its score, in this phase or by this code. The number is written down and read; what to do about it is a Phase 3 decision made against dev recall, and it belongs to the master plan's Phase 3 and Phase 5 entries
- [x] Computed per K, in the same artifact as HU-5, so the four spaces are comparable on quality as well as on shape
- [x] Like every other diagnostic here, it reads the pool only: no question, no gold annotation, no split label

## Data contracts

### `ConceptDictionary` (`.npz` plus a JSON sidecar)

| Field | Type | Constraints |
|-------|------|-------------|
| atoms | float32[K, 384] | Row `j` is concept `j`; L2-normalized |
| k | int | Dictionary size as fitted |
| seed | int | `random_state` of the induction |
| sparsity_param | float | The value controlling code sparsity |
| unit_set_hash | str | The pool the dictionary was induced from |
| model / revision | str | Embedding model and pinned revision of the input vectors |
| merged_from | list[list[int]] \| null | Pre-merge atom indices per surviving atom, if deduplicated |
| code_version | str | Version of the code that produced it |

**Invariants:**
- Atoms are unit-norm and live in the embedding space, so a query maps to concepts by dot product.
- Same K, same seed, same corpus reproduces the file bit for bit.
- Never serialized through `pickle` or `joblib`; only the array is stored.

### `ConceptMatrix` (`.npz`, sparse, plus a JSON sidecar)

| Field | Type | Constraints |
|-------|------|-------------|
| X | sparse float32[N, K] | Non-negative; `N` = 19,366 |
| unit_ids | list[str] | Length N; row `i` belongs to `unit_ids[i]` |
| dictionary_key | str | The dictionary this X was coded against |
| weight_semantics | str | The written meaning of a value (HU-2) |
| view | str | `raw` or `row_normalized` |
| mean_active_per_unit | float | Achieved sparsity |
| reconstruction_error | float | Mean error against the original embeddings |

**Invariants:**
- `X` is the transform output against `dictionary_key`, never a separately computed score.
- Loading validates `unit_ids` against the pool and aborts on mismatch.
- A row of zeros is an orphan unit and is reported, never silently tolerated.

### `SpaceDiagnostics` (JSON, one per dictionary)

| Field | Type | Constraints |
|-------|------|-------------|
| dictionary_key | str | What is being described |
| active_per_unit | dict | mean, median, p5, p95, max |
| units_per_concept | dict | mean, median, p5, p95, max |
| dead_atoms | list[int] | Concepts below the minimum activation count |
| orphan_units | list[str] | Unit ids with an all-zero row |
| top_units_per_concept | dict | Concept index -> unit ids, ranked by weight |
| top_coactivations | dict | Concept index -> co-active concept indices |
| quality | object \| null | The HU-7 block. `null` only when the diagnostic is computed without embeddings |

`quality`, one object per dictionary:

| Field | Type | Constraints |
|-------|------|-------------|
| top_units / min_units | int | Units per concept the scores are measured over, and the minimum below which a concept is undefined |
| null_samples / seed | int | Random sets drawn for the baseline, and the seed that drew them |
| null_mean / null_sd | float | The pairwise cosine of random units of this pool: the reference every score is read against |
| coherence | dict | Concept index -> mean pairwise cosine of its top units |
| coherence_z | dict | Concept index -> `(coherence - null_mean) / null_sd` |
| atom_alignment | dict | Concept index -> mean cosine between the atom and its top units |
| top_mass_share | dict | Concept index -> share of the concept's total weight held by its top units |
| coherence_stats | dict | mean, median, p5, p95, max over the defined concepts |
| undefined_concepts | list[int] | Fewer active units than `min_units`; no score is invented for them |
| below_null_concepts | list[int] | Concepts scoring below `null_mean`: the junk list |

**Invariants:**
- Computed over the whole pool, never broken down by split.
- Written as an artifact, never only printed.
- The quality scores describe the space and never modify it: nothing is pruned, merged or reweighted
  on the strength of a score.

### `ConceptLabels` (JSON, one per dictionary)

| Field | Type | Constraints |
|-------|------|-------------|
| dictionary_key | str | The dictionary labelled |
| labels | dict | Concept index -> `{name, gloss, evidence_unit_ids}` |
| model | str | LLM model id used |
| prompt_hash | str | Hash of the prompt template |
| n_units_shown | int | Units shown per concept as evidence |
| created_at | str | ISO-8601 |
| cost | dict | Calls made, input/output tokens, spend |

**Invariants:**
- Contains no secret, no key fragment and no environment dump.
- Never read by retrieval, scoring or expansion code.
- Not reproducible by re-running; the artifact is the record.

## Constraints

- **Platform**: Windows on ARM64, CPU only, as in Phase 1. The induction runs over embeddings already cached on disk; nothing here re-embeds the corpus.
- **Compute budget**: the full sweep over the four K values must fit within roughly two hours on this machine. If a single fit exceeds that scale, the parameters are revisited rather than left to run overnight - a fit that costs a night is a design error, exactly as embedding was in Phase 1.
- **New dependencies (approved under the ASK FIRST rule)**: `anthropic` (the official SDK) and `python-dotenv`. Both are pure Python and safe on ARM64. They belong in an **optional dependency group**, so that reproducing the experiment's numbers never requires installing either of them - the labelling stage is the only thing that needs them. Note that `anthropic` 1.x builds on `httpx2` while this project already depends on `httpx`; they are separate packages and coexist, but the resolution is verified in the phase plan.
- **LLM model and cost**: labelling uses **`claude-sonnet-5`** over **one dictionary only, K = 2,048** - on the order of 7 USD at roughly ten evidence units per prompt. The model id is recorded in the labels artifact, so a later relabelling with a different model stays comparable to this one. The Batches API would halve the cost for work that is not latency-sensitive and is worth weighing in the plan against the extra complexity it brings for a single run of this size.
- **Determinism**: every stochastic step takes an explicit seed, and the numerical part of this phase is fully reproducible. The labelling stage is the single declared exception, and it sits outside every metric.
- **Security**: `.env` only, never printed or quoted. Artifacts are `.npz` and JSON; no `pickle`, no `joblib`, no `allow_pickle=True`. This phase adds the project's first real secret and its first outbound network call in the experiment path.
- **Phase 1 artifacts are frozen.** The pool, the embedding cache and the recorded metrics are inputs, not material to be modified. Nothing in this phase rewrites them or invalidates the cache.

## Anti-goals (what this phase does NOT do)

- **NO retrieval.** Nothing here answers a question or ranks a unit against a query. Query-to-concept mapping and concept-to-unit scoring are Phase 3 in their entirety.
- **NO expansion.** No diffusion, no iteration, no propagation over `X`. That is Phase 4.
- **NO choice of K.** The sweep is produced; the decision is Phase 3's, made against dev recall.
- **NO evaluation, and no comparison against the baselines.** A concept space is not a retriever; it cannot be measured in the Phase 1 harness and no number produced here is comparable to dense or BM25.
- **NO LLM in the construction of the space.** The LLM names atoms that already exist; it never proposes, extracts or filters a concept. Anything else would make it impossible to tell whether the concept space worked or the model was clever.
- **NO pruning on a diagnostic.** HU-7 scores every concept and removes none. Dropping the least coherent concepts would change what Phase 3 retrieves over, decided by a threshold no measurement has validated; it is a Phase 3 variant against dev recall, or a Phase 5 ablation.
- **NO clustering.** Not KMeans, not HDBSCAN, not as a shortcut. It is admissible only as an explicitly declared ablation, and that would be Phase 5.
- **NO tuning against test.** The test split is not read in this phase, not even for a descriptive statistic.
- **NO change to the embedding model or the indexing unit.** Both would invalidate the Phase 1 cache and make every recorded metric incomparable.

## Existing code context

- `src/concept_embeddings_rag/embeddings/cache.py` - the input to this phase. `EmbeddingCache.load` already validates vectors against a unit id list and reads with `allow_pickle=False`; the concept artifacts follow this pattern rather than inventing a second one.
- `src/concept_embeddings_rag/corpus/pool.py` - `IndexingUnit`, and `load_pool` re-deriving every id on load. The rows of `X` are these units, in this order.
- `src/concept_embeddings_rag/config.py` - every constant that decides what an experiment measures. The K sweep, the seed, the sparsity target and the merge threshold belong here, never inline.
- `src/concept_embeddings_rag/cli.py` - the staged pipeline. This phase adds stages after `embed`, each refusing to run when its input is missing and naming the stage to run first.
- `src/concept_embeddings_rag/retrieval/base.py` - the `Retriever` protocol that Phase 3 will implement over this space. Nothing in this phase implements it.
- `docs/plans/phase_1/1.results.md` - the baseline this space is ultimately meant to beat, and the failure analysis that motivates it.
