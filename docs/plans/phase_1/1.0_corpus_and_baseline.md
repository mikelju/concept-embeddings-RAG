# Phase 1: Corpus, indexing units and dense baseline

> Functional spec: `docs/plans/phase_1/1.spec.md`
> This plan implements the requirements defined in that spec.

## Objective

Build the measuring instrument before building the idea: a frozen corpus, two working baselines (dense and BM25) over a unified pool, and an evaluation harness that reports, at a fixed context budget, how much of the required knowledge each system retrieved. When this phase closes, the project has numbers to be judged against.

**HU-2 — Indexing units by complete meaning**

- [x] Stable, content-derived unit IDs, identical across runs
- [x] Sentence segmentation preserved so supporting facts map onto units
- [x] Every question's 2 gold paragraphs resolve to units in the pool; failure is an error, never a silent drop
- [x] Dev and test draw from the same pool

**HU-3 — Cached, swappable embedding backend**
- [x] Backend behind an interface: swapping the model touches no retrieval or evaluation code
- [x] Embeddings persisted as `.npz`, never `pickle`

- [x] A second run over an unchanged corpus recomputes zero embeddings
- [x] Row order validated against a persisted unit ID list; mismatch aborts

**HU-4 — Two working baselines**
- [x] Dense retrieval by cosine similarity over the pool
- [x] BM25 retrieval over the same pool and the same unit IDs
- [x] Both reproducible: same query, same ranking, seed recorded
- [x] Both behind the same interface
- [x] Retrieval always searches the full pool, never the question's own 10 candidates

**HU-5 — Evaluation harness at fixed context budget**
- [x] Context filled in rank order, skipping units that do not fit whole; never truncating

## Technical notes and decisions

**Unit IDs from content, not position.** `unit_id = sha1(title + "\n" + text)[:16]`. Deriving them from content means the same paragraph always gets the same ID, deduplication is free, and a corpus rebuilt from the manifest yields identical IDs. Position-based IDs would break the moment the subset changes.

**The split is derived from a hash, not from an RNG.** `sha1(qid)` decides which split a question belongs to. Python's `random` and numpy's RNG can change their stream across versions; a hash cannot. The seed still gates subset selection, and both are recorded.

**Tokenizer for budgeting: the `bge-small-en-v1.5` tokenizer**, already available through `transformers`. Deliberately not `tiktoken`: it would add a dependency to count something whose absolute value does not matter. What matters is that every system is measured with the same ruler, and that the ruler is named in the results.

**`.npz` plus a JSON sidecar, never `pickle`.** Loading a pickle executes code; a cache file is exactly the kind of artifact an attacker would target, and the audit in `/8-auditar` would flag it. `.npz` also lets the ID list be validated against the array before anything downstream trusts the alignment.

**New dependency: `bm25s`.** Adding dependencies requires confirmation per `CLAUDE.md`. Verified to have an ARM64 wheel. Chosen over `rank-bm25` for speed on pools of this size; both were available. If the answer is no, the fallback is implementing BM25 over scipy sparse matrices, which is roughly 40 lines and one more step in this plan.

**Tests must not touch the network or download models.** The download test runs against a local synthetic fixture with HotpotQA's structure (a handful of invented questions, clearly labelled as a fixture), and the backend test uses a fake backend returning deterministic vectors. Otherwise the suite would be slow, flaky and unusable offline.

**Known risk — the download URL.** HotpotQA is served from the authors' host, and that URL has moved before. Step 3 verifies it first. If it does not respond, this becomes deviation `1.1` and the mirror gets decided with the user rather than silently swapped: the corpus is the foundation of every number in the project.

**Open risk — pool size.** ~18,000 units is the estimate after deduplication; the real figure depends on how much the 2,000 questions overlap. If it comes out far below (say under 12,000), the search space may be too small for later phases to show anything, and the subset would need enlarging. Step 5 reports the real number.

- **`1.1_corpus_source.md`** - the official HotpotQA host (`curtis.ml.cmu.edu`) does not
  respond. The corpus is now assembled from the canonical HuggingFace dataset via its
  rows API, normalized back into the original HotpotQA shape and frozen with its hash.
  The spec is unaffected: every HU-1 criterion still holds.

## Notes added during implementation

**Both retrievers index `indexable_text` (title + paragraph), not the bare paragraph.**
Wikipedia titles carry the entity a multi-hop question usually has to bridge on, and if
one system saw the title while the other did not, the comparison would measure the input
rather than the method.

**Token counts live in the budget stage, not on `IndexingUnit`.** The spec sketched
`n_tokens` as a field of the unit, but that would couple corpus construction to the
tokenizer and force the model to be loaded merely to build the pool. Counts are computed
once during `embed` and persisted to `token_counts.json`. No acceptance criterion refers
to the field, so the contract is satisfied.

**Dense ties break by unit id.** Otherwise two runs could rank equal-scoring units
differently for reasons unrelated to relevance.

**BM25 keeps zero-scoring hits** in the tail of its ranking. Dropping them would raise
its apparent precision without changing recall, which would flatter the baseline.
