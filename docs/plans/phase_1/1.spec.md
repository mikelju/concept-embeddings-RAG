# Spec Phase 1: Corpus, indexing units and dense baseline

> Functional specification — WHAT to build and WHY.
> The HOW belongs in the phase plan (`1.0_phase_name.md`).
> Acceptance criteria are verified with `/7-verificar` at the end of the phase.

---

## Problem and objective

**Problem**: the project claims that navigating a concept space retrieves knowledge a conventional dense RAG never reaches. Right now that claim cannot be tested, refuted or even sized: there is no corpus, no retrieval, and above all no measuring instrument. Any number produced later would have nothing to be compared against.

**Objective**: a frozen corpus, two working baselines (dense and BM25) and an evaluation harness that measures, at a fixed context budget, how much of the knowledge required to answer each question was actually retrieved. When this phase closes, every later phase can be judged against a number that already exists.

---

## User stories

### HU-1: Frozen, reproducible corpus

**As** the researcher,
**I want** the benchmark subset downloaded once and frozen with its hash,
**so that** every measurement in the project refers to exactly the same data, today and in six months.

**Acceptance criteria:**
- [x] The HotpotQA *distractor* validation split is downloaded from its canonical source and stored under `data/`. *(Updated after verification: the authors' original host stopped responding, so the source is the canonical HuggingFace dataset - see deviation 1.1.)*
- [x] The downloaded file's SHA-256 is recorded in a manifest; a second run verifies the hash instead of downloading again
- [x] A subset of **2,000 questions** is selected with a fixed seed, and the selection is reproducible from the manifest alone
- [x] The subset is partitioned into **600 development** and **1,400 test** questions; the partition is recorded and stable across runs
- [x] The manifest records: source URL, hash, date, seed, subset size, split sizes, and the tool version that produced it

### HU-2: Indexing units by complete meaning

**As** the researcher,
**I want** every paragraph of the subset to become one indexing unit in a single unified pool,
**so that** retrieval has a real corpus to traverse and the units are semantic, not arbitrary slices.

**Acceptance criteria:**
- [x] All paragraphs from all selected questions form **one unified pool** (**19,366 units**, measured), deduplicated by content rather than by title, so two different paragraphs sharing a title stay distinct
- [x] A unit is exactly one benchmark paragraph: **it is never split, merged or truncated** by length
- [x] Every unit has a stable ID, derived from its content, identical across runs
- [x] Each unit keeps its sentence segmentation, so that annotated supporting facts map onto it
- [x] For every question, its 2 gold paragraphs resolve to units present in the pool; a question whose gold cannot be resolved is reported as an error, never silently dropped
- [x] Both dev and test questions draw from the same pool, so that a system cannot benefit from a smaller search space in one split

### HU-3: Cached, swappable embedding backend

**As** the researcher,
**I want** embeddings computed once and reused,
**so that** iterating on retrieval does not mean recomputing the expensive part every time.

**Acceptance criteria:**
- [x] The embedding backend sits behind an interface: replacing the model must not require touching retrieval or evaluation code
- [x] Embeddings persist to disk in a non-executing format (`.npz`), never `pickle`
- [x] The cache key derives from (model name, model revision, unit set hash, normalization); changing any of them yields a different artifact rather than overwriting the previous one
- [x] A second run over an unchanged corpus recomputes **zero** embeddings
- [x] The stored array's row order corresponds to a persisted list of unit IDs, so vectors can never be silently misaligned with their text

### HU-4: Two working baselines

**As** the researcher,
**I want** dense retrieval and BM25 running over the same pool,
**so that** later phases are compared against a defensible reference and not against a straw man.

**Acceptance criteria:**
- [x] Dense retrieval returns units ranked by cosine similarity against the query embedding
- [x] BM25 retrieval runs over the same pool with the same unit IDs
- [x] Both are reproducible: the same query returns the same ranking, run after run, with the seed recorded
- [x] Both expose the same interface, so the harness can evaluate them without knowing which is which
- [x] Retrieval never sees the question's own candidate list: it always searches the full pool

### HU-5: Evaluation harness at fixed context budget

**As** the researcher,
**I want** to measure how much of the required knowledge fits within a given token budget,
**so that** systems retrieving different numbers of chunks remain comparable.

**Acceptance criteria:**
- [x] Given a ranking, the harness fills the context in rank order until the budget is exhausted, **skipping** any unit that does not fit whole and continuing with the next; units are never truncated
- [x] The same filling rule and the same tokenizer apply to every system, and both are recorded in the results
- [x] Primary metrics, computed at budgets of **512, 1,024, 2,048 and 4,096 tokens**:
  - **Gold Paragraph Recall**: mean fraction of the 2 gold paragraphs present in the context
  - **Full Support Rate**: fraction of questions where **both** gold paragraphs are present — the one that actually decides whether the question is answerable
  - **Context Precision**: fraction of included units that are gold
- [x] Secondary metrics for comparability with the literature: Recall@K for K in {2, 5, 10}
- [x] Cost recorded per system: mean query latency and units included
- [x] Every result is written with the configuration that produced it (model, unit set hash, seed, budget, tokenizer, code version); a result without that provenance is not accepted
- [x] Metrics are reported **separately for dev and test**, and no tuning decision is ever made against test numbers

## Data contracts

### `CorpusManifest` (JSON, one per frozen corpus)

| Field | Type | Constraints |
|-------|------|-------------|
| dataset | str | `hotpotqa-distractor-dev` |
| source_url | str | Official download URL |
| sha256 | str | Hash of the downloaded file |
| downloaded_at | str | ISO-8601 date |
| seed | int | Seed for subset selection and split |
| n_questions | int | 2000 |
| split_sizes | dict | `{"dev": 600, "test": 1400}` |
| n_units | int | Size of the unified pool |
| unit_set_hash | str | Hash over sorted unit IDs — identifies the pool |

**Invariants:**
- The same manifest always reconstructs the same subset, the same split and the same pool.
- Nothing downstream may read the raw file without going through the manifest.

### `Question`

| Field | Type | Constraints |
|-------|------|-------------|
| qid | str | Benchmark `_id` |
| question | str | Non-empty |
| answer | str | Non-empty |
| gold_unit_ids | list[str] | Exactly 2, both present in the pool |
| supporting_facts | list[tuple[str, int]] | (unit_id, sentence_index) |
| split | str | `dev` or `test` |

**Invariants:**
- Every `gold_unit_ids` entry resolves to an existing unit; failure is an error, not a warning.
- A question belongs to exactly one split, decided by the manifest seed.

### `IndexingUnit`

| Field | Type | Constraints |
|-------|------|-------------|
| unit_id | str | Content-derived, stable across runs |
| title | str | Wikipedia article title |
| sentences | list[str] | Benchmark segmentation, preserved verbatim |
| text | str | Sentences joined; never truncated |
| indexable_text | str | `title. text` - what every retriever indexes, identically |

*Updated after verification:* `n_tokens` was specified as a field here but lives in the
budget stage instead (`token_counts.json`), because putting it on the unit would couple
corpus construction to the tokenizer and force loading a model merely to build the pool.
`indexable_text` was added so dense and BM25 provably index the same text.

**Invariants:**
- A unit is never split, merged or truncated.
- `unit_id` depends only on content, so the same paragraph always yields the same ID.

### `EmbeddingCache` (`.npz` plus a sidecar JSON)

| Field | Type | Constraints |
|-------|------|-------------|
| vectors | float32[N, D] | Row `i` corresponds to `unit_ids[i]` |
| unit_ids | list[str] | Length N, persisted alongside the array |
| model | str | Model name and revision |
| normalized | bool | Whether vectors are L2-normalized |

**Invariants:**
- Loading validates that `len(unit_ids) == vectors.shape[0]` and that the ID list matches the pool; a mismatch aborts rather than proceeding.
- No `pickle` anywhere in the cache path.

### `RunResult` (JSON, one per system and split)

| Field | Type | Constraints |
|-------|------|-------------|
| system | str | `dense`, `bm25` |
| split | str | `dev` or `test` |
| config | dict | Model, unit_set_hash, seed, tokenizer, code version |
| metrics | dict | Keyed by budget and by K |
| cost | dict | Mean latency, mean units included |
| created_at | str | ISO-8601 |

**Invariants:**
- A `RunResult` without complete `config` is invalid and is not written.
- Results are append-only: a new run never overwrites a previous one; it produces a new file.

## Constraints

- **Platform**: Windows on ARM64, CPU only. HuggingFace `datasets` is unavailable (no `pyarrow` wheel), so the corpus is downloaded as raw JSON — which also serves the required reproducibility.
- **Determinism**: every stochastic step takes an explicit seed. The same manifest plus the same code must reproduce the same numbers.
- **Security**: the downloaded JSON is external input — verify its hash before use. Cached artifacts use non-executing formats (`.npz`, JSON), never `pickle`.
- **Embedding model**: `bge-small-en-v1.5` (384 dimensions), pinned by revision. It sits behind the swappable interface, so changing it is a phase decision and not a code rewrite.
- **Tokenizer for budgeting**: a single tokenizer, declared in the results, applied identically to every system. What matters is not which one, but that it never changes between systems.
- **Scale**: ~18,000 units. Embedding them on this CPU takes minutes, not hours; anything that turns this into hours is a design error to be revisited.

## Anti-goals (what this phase does NOT do)

- **NO concepts**: no dictionary, no sparse coding, no matrix X. That is Phase 2 in its entirety.
- **NO expansion**: retrieval is one-shot. Iteration is Phase 4.
- **NO LLM anywhere**: not for labelling, not for reranking, not for judging. This phase must be runnable offline once the corpus is downloaded.
- **NO answer generation**: we measure whether the necessary knowledge was retrieved, not whether a model writes a good answer with it.
- **NO second benchmark**: MuSiQue belongs to Phase 5.
- **NO document hierarchy**: Phase 6, and only if the results justify it.
- **NO tuning against test**: the test split exists to be measured once, late, and never to be looked at while adjusting anything.
